# graphio-ontology-builder

업무 문서 여러 개를 읽어 **온톨로지를 설계하고** 서식 문서 하나로 정리한다. 산출물은 파일 셋이다 — 서식을 지킨 온톨로지 정의 문서, 무엇을 왜 그렇게 정했는지 적은 설계 리포트, 이 구조를 믿어도 되는지 검사한 결과를 남긴 검증 리포트.

**판단하는 일을 한다.** 무엇을 개념으로 둘지, 어떤 속성을 만들지, 어디를 이을지 정한다. 옮기기만 하는 자매 스킬과 다른 점이 여기다. 판단을 하므로 **근거를 남기는 것이 산출물의 절반**이다. 근거가 없으면 받는 사람이 맞는지 확인할 길이 없고, 확인할 수 없는 구조는 고칠 수도 없다.

| 단계 | 하는 일 | 누가 |
|---|---|---|
| 1 | 업무 문서 → 온톨로지 서식 문서 | **이 스킬** |
| 2 | 서식 문서 → graphio JSON | `graphio-ontology-converter` |
| 3 | JSON → 운영 환경 반입 | Export 스킬 |

이 스킬은 1단계에서 끝난다. JSON 을 만들지 않는다. 온톨로지의 내용은 여기서 전부 확정되고, 2단계는 형식만 바꾼다.

## 하지 않는 것

| 하지 않는 것 | 왜 |
|---|---|
| 컬럼 목록에서 거꾸로 개념을 뽑지 않는다 | 컬럼이 곧 속성은 아니다. 원천을 그대로 옮기면 구조는 생기지만 무엇을 뜻하는지 읽히지 않고 검색도 되지 않는다 |
| 검증질문이 요구하지 않는 것을 만들지 않는다 | 쓰이지 않는 개념은 질의 라우팅을 흐린다. 있으면 좋아 보이지만 정확도를 깎는다 |
| 확인되지 않은 값을 지어내지 않는다 | 채워 넣으면 구조는 완성된 것처럼 보이고 반입 후에 답이 틀린다. 틀린 답은 빈칸보다 나쁘다 |
| 판정 결과와 집계 결과를 속성으로 만들지 않는다 | 판정은 구조가 아니라 질의가 하는 일이다. 구조에 넣으면 기준이 바뀔 때마다 데이터를 다시 만들어야 한다. 원천이 이미 세어 컬럼으로 저장해 둔 값도 집계 결과다 — 누가 세었는지는 값의 성격을 바꾸지 않는다 |
| 원천에 없다는 이유로 개념·속성·관계를 빼지 않는다 | 무엇을 만들지는 질문이 정한다. 원천은 지금 무엇이 있는지를 알려줄 뿐이다. 없는 것은 빼는 대신 무엇이 필요한지 리포트에 적는다 |
| 뜻이 다른 컬럼으로 대신 답하지 않는다 | 값이 틀린 채로 동작한다. 비었다면 비었다고 보여야 고칠 수 있다 |
| 입력 문서를 고치지 않는다 | 입력 문서는 다른 사람의 산출물이다. 어긋난 자리는 리포트로 알린다 |
| 가이드의 규칙을 본문에 옮겨 적지 않는다 | 규칙은 가이드 파일에만 두고 설계할 때마다 편다. 기본 가이드가 스킬 안에 있어도 마찬가지다. 본문이 규칙을 외우고 있으면 `--style`·`--format` 으로 다른 가이드를 줘도 옛 규칙대로 만든다 |

마지막 줄이 이 스킬의 성격을 정한다. **설계 규칙은 스킬이 아니라 가이드 문서에 있다.** 스킬은 가이드의 어느 대목을 언제 펴 봐야 하는지만 안다.

## 0) 시작하기 전에

### 받는 것 — 네 자리

| 자리 | 무엇이 오나 | 개수 | 없으면 |
|---|---|---|---|
| **CQ** | 온톨로지가 답해야 하는 질문 목록 | 여럿 | 멈춘다 (아래) |
| **참고 문서** | 용어 사전, 원천 스키마, 비정형 자료 목록, 업무 이해서 등. 종류는 정해져 있지 않다 | 여럿, 없어도 됨 | 질문만으로 설계한다. `확인 필요`가 크게 늘어난다 |
| **스타일 가이드** | **검색이 잘 되게 내용을 정리하는 규칙.** 개념·속성·관계의 이름과 설명·별칭·질문예시·경고문을 어떻게 쓰는지 정한다. 설명은 그대로 임베딩되어 검색에 쓰인다 | 하나 | 스킬 기본을 쓴다 (아래) |
| **서식 가이드** | **JSON 으로 내보내기 위한 규칙.** 네 절 서식의 칸마다 무엇을 적어야 converter 가 Graphio JSON 으로 옮길 수 있는지 정한다 | 하나 | 스킬 기본을 쓴다 (아래) |

**CQ 와 참고 문서는 여러 개가 온다.** 여럿이 오면 하나로 합쳐 다루되 **어느 문서에서 왔는지를 함께 적어 둔다.** 문서가 다르면 질문 번호가 겹칠 수 있다. 같은 번호를 둘이 쓸 수 있고, 서로 어긋나는 말을 하기도 한다. 출처를 적어 두면 연결표에서 가려낼 수 있다.

어긋나는 자리를 만나면 **고르지 말고 양쪽을 리포트에 적는다.** 어느 쪽이 맞는지는 문서를 쓴 사람이 안다. 예외는 둘이다. 질문 본문과 질문 옆 칸이 어긋나면 **판정은 칸을 따른다** — 질문 옆 칸은 질문마다 붙어 설계에 조건을 거는 칸이고([`references/입력-문서-읽기.md`](references/입력-문서-읽기.md) 2장), 설계를 구속한다. 용어 사전과 스타일 가이드·결정 사항이 두 말이 같은 대상인지를 두고 갈리면 **판정은 가이드·결정 사항을 따른다** — 설계 규칙과 결정은 그쪽에 있다. 어긋났다는 사실은 두 경우 모두 그대로 리포트에 적는다.

**검증질문과 가이드가 어긋나기도 한다.** 검증질문이 답으로 요구한 값을 스타일 가이드가 만들지 못하게 막는 자리가 그렇다. 이때는 고를 것이 없다. 무엇을 만들지는 질문이 정하지만, **스타일 가이드가 막은 것은 만들지 않는다.** 스타일 가이드는 만들 것을 정하지 않고 막을 뿐이다. 요구한 값과 막은 규칙은 양쪽 다 리포트 「문서끼리 어긋난 자리」 절에 적는다. 적지 않으면 그 질문에 왜 답하지 못하는지 받는 사람이 알 길이 없다.

두 가이드는 **기본 문서가 있다.** 따로 주지 않으면 기본을 쓰고, `--style`·`--format` 으로 주면 **기본 대신 받은 문서만** 따른다.

| 가이드 | 기본 | 다른 문서를 주는 법 |
|---|---|---|
| 스타일 가이드 | 이 스킬의 [`assets/스타일-가이드.md`](assets/스타일-가이드.md) | `--style <경로>` |
| 서식 가이드 | 형제 스킬 `graphio-ontology-converter` 의 `assets/서식-작성-가이드.md` | `--format <경로>` |

**받은 문서와 기본을 섞지 않는다.** `--style` 을 받았으면 기본 스타일 가이드는 펴지 않는다. 두 문서의 규칙을 섞으면 어느 규칙을 따랐는지 리포트에서 되짚을 수 없다. 받은 가이드에 없는 규칙이 필요하면 기본에서 가져오지 말고 리포트에 적는다.

**서식 가이드는 converter 의 것이 원본이다.** converter 가 이 서식을 읽어 JSON 으로 옮기므로, 이 스킬이 사본을 두면 converter 의 서식이 바뀔 때 사본만 낡는다. 형제 스킬은 이 폴더와 나란히 있으므로 아래 중 실제로 있는 자리를 쓴다. **어디에도 없으면 `--format` 을 달라고 묻는다.** 짐작한 서식으로 만들지 않는다.

```
../graphio-ontology-converter/assets/서식-작성-가이드.md      이 스킬 폴더 기준 (설치·저장소 모두)
.claude/skills/graphio-ontology-converter/assets/...         프로젝트에 설치했을 때
~/.claude/skills/graphio-ontology-converter/assets/...       --user 로 설치했을 때
skills/graphio-ontology-converter/assets/...                 hub 저장소에서 바로 쓸 때
```

`--format` 으로 다른 서식 가이드를 받으면, 그 서식을 converter 가 읽을 수 있는지는 ⑨ 의 서식 검사가 가린다.

**입력 문서 폴더에서 가이드를 찾지 않는다.** 이름에 「가이드」 가 든 문서가 입력 폴더에 있어도 가이드 자리에 앉히지 않는다. 그 문서를 가이드로 쓰려면 `--style`·`--format` 으로 준다. 참고 문서로 받았으면 참고 문서로 다룬다.

사용자가 스타일 가이드를 `설계 가이드`·`디자인 가이드`로 부르기도 한다. 같은 자리다.

### 부르는 법

네 자리를 문장으로 말해도 되고, 아래 표기로 적어 줘도 된다. **둘 다 같게 받는다.**

```
/graphio-ontology-builder
  --cq      docs/검증질문.md
  --ref     docs/용어집.md docs/테이블-명세.md
  --out     outputs/
  --name    인사관리

# 기본 가이드 대신 다른 가이드를 쓸 때만 더한다
  --style   docs/우리팀-스타일-가이드.md
  --format  docs/우리팀-서식-가이드.md
```

| 표기 | 자리 | 여러 개 | 없으면 |
|---|---|---|---|
| `--cq` | CQ | 됨 | 멈춘다 |
| `--ref` | 참고 문서 | 됨 | 질문만으로 설계한다 |
| `--style` | 스타일 가이드 | 하나 | 스킬 기본 (`assets/스타일-가이드.md`) |
| `--format` | 서식 가이드 | 하나 | converter 의 서식 가이드. 없으면 묻는다 |
| `--out` | 산출물 폴더 | 하나 | 입력 문서와 같은 폴더 |
| `--name` | 산출물 이름 앞부분 | 하나 | 업무 영역에서 따온다 |

**이것은 명령줄 옵션이 아니다.** 읽어서 자리에 앉히는 표기 규약이고, 파서가 없다. 그래서 이렇게 다룬다.

- `--style` 을 `--design`·`--guide` 로 적어 와도 스타일 가이드 자리로 받는다. 표기가 아니라 뜻으로 읽는다
- 표기와 문장이 섞여 와도 받는다. `--cq docs/검증질문.md 로 온톨로지 만들어 줘` 같은 꼴이다
- **모르는 표기는 짐작하지 않고 묻는다.** 자리를 잘못 앉히면 그다음이 전부 어긋난다

표기로 받았든 문장으로 받았든 **①단계에서 자리를 되돌려 보여 준다.** 거기서 사용자가 바로잡는다.

### CQ 자리가 비면 멈춘다

검증질문을 받지 못하면 **설계를 시작하지 않는다.** 참고 문서가 아무리 많아도 마찬가지다.

무엇을 만들고 무엇을 빼는지 정하는 기준이 검증질문이기 때문이다. 기준이 없으면 남는 방법은 원천 컬럼을 그대로 옮기는 것뿐인데, 그것은 이 스킬이 하지 않기로 한 일이다. 만들어 놓고 "근거 없음"이라고 표시하는 것도 답이 아니다 — 표시가 너무 많으면 읽는 사람이 흘려 읽는다.

멈출 때는 이렇게 알린다.

```
검증질문 목록이 있는 문서가 필요합니다.

온톨로지에 무엇을 넣고 무엇을 뺄지 정하는 기준이 검증질문입니다.
"이 온톨로지가 답해야 하는 질문" 목록을 담은 문서를 주시면 이어서 설계합니다.

문서가 아직 없다면 질문 목록만 적어 주셔도 됩니다. 이런 꼴이면 충분합니다.
  - 어느 교육에 어떤 사원이 참석했는가
  - 어떤 사원이 낸 출장신청은 어느 근무지로 가는가
```

### 먼저 읽는다

작업을 시작하기 전에 [`references/입력-문서-읽기.md`](references/입력-문서-읽기.md) 를 읽는다. 역할을 가려내는 법과, 역할마다 무엇을 뽑아 쓰는지가 거기 있다.

## 1) 작업 순서

아홉 단계다. **한 번에 하나씩 만들고 그때마다 검사한다.** 열 개를 만들고 한꺼번에 검사하면 같은 실수가 열 개에 퍼진 뒤에 발견된다.

### ① 참고 문서의 역할을 가린다

CQ 는 사용자가 자리를 정해 주고, 두 가이드는 스킬 기본이거나 옵션으로 받은 문서라 가릴 것이 없다. 다만 **어느 쪽을 썼는지는 반드시 밝힌다.** **참고 문서만 역할을 가린다.** 종류가 정해져 있지 않고, 역할에 따라 뽑아 쓰는 자리가 다르기 때문이다. 판별하는 법은 [`references/입력-문서-읽기.md`](references/입력-문서-읽기.md) 에 있다.

**역할을 가리자마자 낸다.** 개념을 정하기 전이어야 사용자가 고칠 수 있다. 설계를 먼저 해 두고 내면 답이 오기 전에 판단이 굳어, 보여 주는 뜻이 없어진다.

가린 결과를 사용자에게 보여 주고 **답을 받은 뒤 ②로 간다.** 역할을 잘못 짚으면 그다음이 전부 어긋나는데, 사용자는 한 줄만 읽고 바로잡을 수 있다. 보여 주고 그대로 이어 가면 잘못 앉힌 자리가 아홉 단계를 타고 내려가, 문서가 다 나온 뒤에야 드러난다.

자리가 하나라도 비었거나 사용자가 부른 이름과 다르면 **여기서 되묻는다.** 사용자가 확인 없이 이어 가라고 했어도 이때는 되묻는다. 그 밖의 경우에 확인 없이 이어 가라고 했으면 결과를 보여 주고 이어 간다.

**경로를 함께 찍는다.** 파일 이름만 찍으면 이름이 같은 다른 폴더의 문서를 집었을 때 가려지지 않는다. 질문 건수는 머리말에 적힌 수가 아니라 **질문을 직접 세어** 적는다 — 표이면 행을, 목록이면 항목을 센다.

```
받은 문서를 이렇게 보았습니다. 틀린 곳이 있으면 알려 주세요.

  CQ          docs/검증질문.md               질문 18건 (상 11 · 중 7)
                                             필수 질문은 `상` 11건으로 보았습니다 — 문서가 가장 높게 매긴 등급
  스타일 가이드  assets/스타일-가이드.md                        스킬 기본
  서식 가이드    ../graphio-ontology-converter/assets/서식-작성-가이드.md   스킬 기본

  참고 문서는 아래와 같이 가렸습니다.

  용어 자료           docs/용어집.md
                     업무에서 쓰는 말과 뜻을 풀어 두었고, 같은 대상을 달리 부르는 말을 모아 두었다 (용어 자료 단서)
  정형 원천           docs/테이블-명세.md
                     테이블과 컬럼 목록이 있고, 테이블을 어느 컬럼으로 잇는지 적었다 (정형 원천 단서)
  업무 범위 · 용어 자료  docs/업무-소개.md
                     무엇을 하려는 일인지와 다루지 않는 범위를 적었다 (업무 범위 단서)
                     말과 뜻을 풀어 둔 표가 함께 있다 (용어 자료 단서)

이대로 진행할까요?
```

참고 문서의 개수와 종류는 정해져 있지 않다. 위는 예시일 뿐이다. **한 문서가 두 역할을 겸하면 겸한 대로 적고, 근거도 역할마다 적는다.**

**가린 근거를 함께 적는다.** 자리만 보여 주면 사용자는 맞는지 가릴 거리가 없다. 「용어 사전이라서」 처럼 문서 이름을 되풀이하는 것은 근거가 아니다. [`references/입력-문서-읽기.md`](references/입력-문서-읽기.md) 1장 역할별 단서 가운데 어느 것으로 갈랐는지와, 그 문서에서 실제로 본 것을 함께 적는다. **단서는 역할별 단서 표의 역할 이름으로 적는다** — 「(용어 자료 단서)」 처럼. 장 번호로 적으면 이 표가 리포트로 옮겨질 때 받는 사람이 펼 수 없는 번호가 남는다. 역할을 가리지 못한 문서가 있으면 「가리지 못함」으로 적고 무엇이 모자랐는지 밝힌다. 빈 칸으로 두면 빠뜨린 것인지 가리지 못한 것인지 알 수 없다.

**이 표는 그대로 리포트의 「문서 역할 판정」 절이 된다.** 근거는 가리는 이 자리에서 적는다. 리포트를 쓰면서 뒤늦게 적으면 이미 나온 설계에 맞춰 까닭을 지어내게 되고, 그러면 되짚는 데 쓸 수 없다. 사용자가 여기서 바로잡아 준 자리는 **누가 정했는지 함께** 리포트에 남긴다 — 스킬이 가린 것과 사용자가 정한 것은 믿을 수 있는 정도가 다르다.

### ② 질문에서 필요한 값을 모은다

검증질문 하나하나를 **조건으로 쓰는 값**과 **답으로 내보내는 값**으로 나눈다.

> 어느 교육에 어떤 사원이 참석했는가
> → 조건: 교육 · 답: 사원을 알아볼 수 있는 값

이 표가 설계 내내 기준이 된다. 개념·속성·관계는 모두 여기 있는 값에서 나오고, 여기 없는 것은 만들지 않는다. 나중에 설계 리포트 1절의 연결표가 되므로 **질문 번호와 그 질문이 어느 문서에서 왔는지**를 함께 적는다. 질문에 번호가 없으면 받은 차례대로 번호를 매겨 쓴다([`references/입력-문서-읽기.md`](references/입력-문서-읽기.md) 2장). CQ 문서가 여럿이면 번호만으로는 어느 질문인지 가려지지 않는다.

CQ 문서가 이미 이 분해를 해 두었으면 그대로 쓴다. 다시 만들지 않는다.

### ③ 개념을 정한다

②의 값들을 무엇의 집합인지로 묶는다. **원천 테이블 목록을 보고 정하지 않는다.** 묶고 난 뒤에 원천과 견주는 것이 순서다.

**상태를 말하는 꾸밈말은 개념이 아니라 조건이다.** 질문은 무엇을 답해야 하는지를 정하고, 개념의 모양은 업무 대상이 정한다. 「지연된 주문」을 묻는다고 「지연주문」을 두면 「반품된 주문」을 물을 때 또 하나가 생긴다. 「주문」 하나를 두고 꾸밈말을 가르는 데 필요한 값(납기·출하 시점)을 속성으로 둔다 — 「지연 여부」 같은 판정은 두지 않는다. 다른 대상과의 이어짐을 말하는 꾸밈말은 이 문단이 다루지 않는다. 관계 하나로 담을지 가운데 개념을 둘지는 ⑤ 에서 [`references/개념을-더-둘-때.md`](references/개념을-더-둘-때.md) 로 가린다.

개념으로 만들 것과 만들지 않을 것을 가르는 기준은 스타일 가이드에 있다. 가이드에서 개념 만들기 대목을 펴고 그 기준을 그대로 쓴다.

원천에 **두 테이블을 이어 주는 별도 테이블**이 있으면 그것은 다대다라는 신호다. 그 테이블이 개념 하나가 된다. **딸린 값이 없어도 그렇다** ([`references/개념을-더-둘-때.md`](references/개념을-더-둘-때.md) 1장·2장).

### ④ 개념마다 이름 → 속성을 정한다

개념 하나를 끝내고 다음으로 넘어간다. 순서가 중요하다.

1. **이름을 짓는다.** 스타일 가이드의 이름 짓기 대목을 편다. 원천 컬럼명을 이름으로 쓰지 않는 것이 대개 첫 규칙이다. 개념 이름은 [`references/개념-이름-짓기.md`](references/개념-이름-짓기.md) 도 편다 — 가이드가 허용하는 이름이 여럿일 때 하나를 고르는 차례가 있다
2. **속성을 붙인다.** ②에서 이 개념에 묶인 값만 대상이다

**고른 까닭은 그 자리에서 적어 둔다.** 설계 리포트 2.1 에 올릴 내용이다. 리포트를 쓰며 뒤늦게 적으면 이미 나온 이름에 맞춰 까닭을 지어낸다.

**설명은 여기서 쓰지 않는다.** ⑧ 첫머리에서 쓴다. 설명에는 데이터 구조를 가리키는 줄이 들어가는데 그 구조는 ⑦에서 정해진다. 설계안(⑥)에서 개념이 바뀌면 써 둔 설명도 버리게 된다.

스타일 가이드가 개념마다 설명까지 쓰고 검사하는 차례를 정해 두었어도, 설명과 그 검사 항목은 ⑧에서 짚는다. **만드는 차례는 이 스킬의 단계를 따르고, 가이드의 검사 항목은 그 대상이 만들어지는 단계에서 짚는다.** 가이드에는 무엇을 어떻게 만드는지를 묻고, 언제 만드는지는 스킬이 정한다.

### ⑤ 관계를 만든다

②의 질문 중 **답이 두 개념을 거쳐야 나오는 것**을 찾는다. 그 질문마다 관계 하나를 만든다.

두 개념을 잇는 값이 실제로 있는지 원천 문서에서 확인한다. **없어도 만든다** — 질문이 그 경로를 요구하기 때문이다. 대신 무엇이 있어야 이어지는지를 리포트 「추가로 필요한 메타타입」 절에 적는다.

**조인에 쓸 값이 원천에 없어도 속성은 만든다.** 규격이 양쪽 조인 속성을 요구하므로 속성이 없으면 관계를 만들 수 없다. 속성은 두고 매핑만 비운 뒤, 그 컬럼이 필요하다는 것을 리포트 4.1 에 적는다.

적지 않으면 그 관계는 반입은 되지만 언제나 비어 있다. **잘 된 것처럼 보이면서 동작하지 않는 것이 가장 나쁘다.** 적어 두면 비어 있는 이유와 채우는 방법이 함께 보인다.

원천 문서에 "연결이 없다"고 적힌 자리도 같다. 질문이 요구하지 않으면 만들지 않고, 요구하면 만든 뒤 잇는 값이 필요하다고 적는다.

**방향은 도착 쪽 조인 속성을 보고 정한다.** 도착 개념의 **식별 속성으로 조인하는 쪽**을 도착으로 잡는다. 대개 자식에서 부모로 향하는 모양이 된다.

**관계를 다 만들면 질문마다 답에 이르는 경로를 적는다.** 조건에서 답까지 어느 개념을 어느 관계로 거쳐 가는지와 홉 수를 리포트 1절에 남긴다. 쓰는 개념과 속성만 적으면 재료 목록이라, 그 재료로 정말 답이 나오는지 되짚을 수 없다. CQ 가 홉 수 조건을 정했으면 그것을 넘는 질문이 있는지 여기서 보고, **경로가 없는 질문은 「경로 없음 — 무엇이 모자란가」 로 적는다.** ⑥ 에서 사용자에게 보일 것이 그 줄이다.

```
점검이력 → 설비     도착 쪽 조인 속성이 설비의 식별 속성이다        좋다
설비 → 점검이력     도착 쪽 조인 속성이 점검이력의 식별 속성이 아니다   경고가 붙는다
```

식별 속성이 아닌 값으로 조인하면 그 값이 여러 개체에 반복되어 **관계가 의도보다 넓게 퍼진다.** 동작은 하므로 오류가 아니고, 검증기가 경고로 알린다.

경고가 붙는 방향이 맞을 때도 있다. 한쪽에 식별 속성이 아예 없는 경우가 그렇다. 그때는 그대로 두고 **리포트에 왜 그렇게 두었는지 적는다.** 적지 않으면 다음 사람이 실수로 본다.

**이것은 스타일 가이드가 방향을 정하지 않았을 때의 기본값이다.** 가이드가 방향 규칙을 두었으면 그쪽을 따른다. 다만 가이드의 **예시**는 규칙이 아니다 — 예시는 설명을 보여 주려고 업무가 흐르는 차례대로 적히는 일이 많아, 이 기본값과 반대로 보일 수 있다. 그때는 조인 속성이 도착 쪽의 식별 속성인지를 보고 정하고, **가이드 예시와 어긋났다는 것을 리포트에 적는다.**

**관계 하나로 풀리지 않는 자리가 있다.** 원인은 셋이고 가리는 축은 넷이다 — 다대다와 역할이 한 원인을 나눠 가진다. 이어짐 자체에 값이 딸리는데 관계가 속성을 가질 수 없을 때 — 다대다와 역할이 그렇다. 지나갈 마디가 없을 때 — 이을 값이 양쪽 어디에도 없거나, 같은 값을 여럿이 들고 있는데 그 값이 마디가 아닌 경우다. 그리고 원천이 한 칸에 값을 여럿 뭉쳐 둔 때 — 그 칸은 속성이 될 수 없어 펴야 한다. 판단 기준은 [`references/개념을-더-둘-때.md`](references/개념을-더-둘-때.md) 에 있다.

개념이 하나 늘어나므로 ③으로 돌아가 이름과 속성을 정하고 온다. **네 축 어느 것에도 걸리지 않으면 두지 않는다** — 질의가 한 단계 더 거치기 때문이다.

### ⑥ 설계안을 확인받는다

**개념과 관계의 설계는 여기까지다.** 무엇을 개념으로 두고 어디를 이을지는 ③~⑤에서 정해졌다. 정의 문서를 쓰기 전에 **설계안을 보여 주고 답을 받은 뒤 ⑦로 간다.** 판단이 사용자의 생각과 다르면 지금 바로잡는 것이 가장 싸다. 정의 문서를 다 쓴 뒤에 드러나면 수백 줄을 다시 쓰게 된다.

설계안은 **리포트의 요약본**이다. ③~⑤에서 정한 것과, 그 구조로 ②의 질문에 답할 수 있는지만 짧게 적는다. 설명·데이터 구조·매핑은 설계안에 넣지 않는다.

| 적을 것 | 리포트에서 이어지는 절 |
|---|---|
| 개념 — 이름과 근거 질문 | 2절 |
| 관계 — 출발 → 도착, 조인 속성, 근거 질문 | 3절 |
| 더 둔 개념과 두지 않은 중간 개념 — 판정한 조건 | 2절 · 6.1 |
| 경로가 없거나 CQ 가 정한 홉 수를 넘는 질문 — 무엇이 모자란가 | 1절 |
| 문서끼리 어긋나 판정할 쪽을 정한 자리 — ③~⑤에서 정한 것 | 8절 |

**여기서 판정하지 않는다.** `예`·`일부`·`아니오` 는 ⑨ 가 검증 리포트에 적는다. 이 단계는 ③~⑤ 의 결과만 가지고 있어 매핑도 서식도 아직 없다. 구조만 보고 판정하면 ⑦⑧ 을 지나며 값이 달라지고, 사용자는 두 판정 가운데 어느 것이 맞는지 알 수 없다.

**대신 경로를 보고 말한다.** 리포트 1절 연결표에서 **경로가 비었거나 CQ 가 정한 홉 수를 넘는 질문**을 골라, 무엇이 모자란지와 함께 보여 준다. 구조를 고칠지 질문을 낮출지는 사용자가 정한다. 경로는 ③~⑤ 에서 이미 정해졌으므로 이 단계에서 말할 수 있는 것이고, 데이터가 실제로 있는지는 ⑦ 을 지나야 안다.

```
설계안입니다. 바로잡을 곳이 있으면 알려 주세요. 답을 받은 뒤 정의 문서를 씁니다.

  개념 6          설비 (질문 번호) · 점검이력 (질문 번호) · 부품 (질문 번호) · …
  관계 7          점검이력 → 설비      조인 설비번호   (질문 번호)
                  설비부품구성 → 부품   조인 부품번호   (질문 번호) · …
  더 둔 개념       부품 — 판정한 조건 (개념을-더-둘-때의 어느 조건에 걸렸나)
  두지 않은 개념    공급사 — 공급사코드를 든 개념이 하나뿐이다
  경로가 모자란 질문  (질문 번호) — 경로 없음 · 무엇이 모자란가
                  (질문 번호) — 3홉 (CQ 통과 조건은 2홉 이내)
  판정할 쪽을 정한 자리  (질문 번호) 본문과 옆 칸이 서로 다른 것을 요구했다 — 칸을 따랐다

이대로 정의 문서를 쓸까요?
```

**바로잡을 곳을 받으면 ③~⑤로 돌아가 그 자리만 고치고, 고친 줄을 표시해 설계안을 다시 보여 준다.** 사용자가 확인 없이 이어 가라고 했으면 설계안은 그대로 보여 주고 이어 간다.

**확인받은 뒤에 설계를 바꾸게 되면 무엇을 왜 바꿨는지 설계 리포트 머리표의 「설계안 확인」 칸에 적는다.** ⑦에서 매핑하다가, ⑧의 서식 제약이나 ⑨의 검사 때문에 흔히 생긴다. 적지 않으면 읽는 사람은 확인받은 설계와 나온 설계가 같은 줄 안다. 개념이나 관계를 더하거나 빼야 하면 정의 문서를 넘기기 전에 그 자리만 다시 보여 준다.

### ⑦ 데이터 구조와 매핑을 만든다

원천 구조 문서가 있을 때만 한다. 없으면 이 단계와 다음 절을 통째로 건너뛴다 — 개념과 관계만 있는 온톨로지가 정상으로 만들어진다.

**원천 테이블 목록과 개수가 같을 이유가 없다.** 데이터 구조는 세 갈래에서 오고, 원천에 있어도 쓰지 않는 테이블은 빠지기 때문이다.

| 어디서 오나 | 어떻게 |
|---|---|
| 정형 원천 | 테이블이 그대로 데이터 구조가 된다 |
| 비정형 원천 | **문서 타입을 먼저 정하고** 그 모양대로 만든다. 정하는 규칙은 스타일 가이드에 있다 |
| 한 칸에 여러 값이 든 컬럼 | 개념으로 나눈 만큼 데이터 구조도 나뉜다 |

뒤의 두 갈래는 **대상 환경에 아직 없는 것을 가리키게 된다.** 문서 타입은 이 설계 단계에서 처음 정해지고, 뭉친 컬럼을 펼친 테이블은 전처리를 해야 생긴다. 정상이다 — 데이터 구조는 반입으로 만들어지지 않고 대상 환경에 먼저 있어야 하므로, **누가 언제 만드는지가 다음 단계의 일거리**가 된다.

그래서 없는 것을 적을 때는 두 자리에 함께 남긴다.

- 데이터 구조의 설명에 **아직 없다는 것과 무엇을 해야 생기는지**
- 리포트 「추가로 필요한 메타타입」 절에 **어느 개념이 쓰고, 어떻게 만들고, 누가 하는지**

이 둘이 없으면 받는 사람은 이미 있는 구조로 읽고 반입하다 막힌다. 검증기가 `GOS61014` 로 짚어 주지만 그것은 오류가 아니라 **사람이 이어서 할 일**이라, 짚어만 주고 누가 할지는 말해 주지 않는다.

**아직 없는 구조의 이름은 개념에서 따온다.** 그 데이터를 쓰는 개념 이름을 그대로 쓴다. 원천 테이블 이름에 공통으로 붙은 말이 있으면 새 테이블에도 **그 말을 붙인다** — 대상 환경에서 같은 묶음으로 보여야 찾기 쉽다. 문서 타입에는 붙이지 않는다. **컬럼 이름은 원천 관례를 따르고, 문서 타입은 `DOC_TYPE` 으로 적는다.** 정의 문서와 리포트에 같은 이름으로 적는다. 짓는 규칙은 [`references/서식으로-옮기기.md`](references/서식으로-옮기기.md) 2.1 에, 종류는 같은 문서 2.2 에 있다. ⑧보다 앞선 단계지만 이 두 절은 여기서 읽는다.

속성과 컬럼을 잇는다. 이름이 다른 것이 정상이다 — 속성 이름은 사람이 읽는 것이고 컬럼은 데이터를 찾는 것이라 서로 다른 층이다.

**원천에 그 뜻의 컬럼이 없으면 비슷한 컬럼에 잇지 않는다.** 매핑을 비우고 리포트 「추가로 필요한 메타타입」 절에 적는다. 뜻이 다른 값을 이어 두면 질의는 답을 내놓는데 그 답이 틀린다. 뜻이 같은지 가리는 차례는 [`references/검증-리포트-서식.md`](references/검증-리포트-서식.md) 3절에 있다 — 여기서 가린 결과가 그대로 검증 리포트 3절 표가 된다.

### ⑧ 설명을 쓰고 서식으로 옮긴다

**이 단계를 시작하기 전에 [`references/서식으로-옮기기.md`](references/서식으로-옮기기.md) 를 읽는다.** 두 가이드가 요구하는 것이 서로 맞지 않는 자리가 있다. 설명이 여러 줄인데 서식은 한 줄만 읽는 자리, 이름에 띄어쓰기를 하라는데 서식은 공백을 막는 자리가 그렇다. 모르고 옮기면 설명의 절반이 소리 없이 사라진다.

**먼저 설명을 쓴다.** 개념·속성·관계마다 스타일 가이드가 정한 구성 요소를 빠짐없이 넣는다. 속성은 스타일 가이드의 속성 유형을 먼저 정하고 그 유형의 형식으로 쓴다(서식으로-옮기기.md 4장). ⑦에서 데이터 구조가 정해졌으므로 그 구조를 가리키는 줄(`[SQL]` 같은 것)도 이제 채울 수 있다.

설명은 그대로 임베딩되어 검색에 쓰인다. 짧게 줄이면 검색이 안 되고, 없는 말을 채우면 엉뚱한 질의를 끌어온다.

가이드가 요구하는 항목 중 **입력 문서만으로는 알 수 없는 것이 있다.** 코드의 실제 저장값, 단위, 기본키, 대표 컬럼 같은 것들이다. 원천 자료가 적어 두었으면 그 값을 쓴다. 적어 두지 않았으면 실제 데이터를 확인해야 채울 수 있으므로 `확인 필요`라고 적고 리포트에 모은다. 짐작해서 채우지 않는다.

**원천이 그 값을 글자로 적어 두었을 때만 「적어 두었다」이다.** 값이 어떤 종류인지만 적어 둔 것, 곧 의미 분류(금액·시점·여부 같은 것)는 값을 적어 둔 것이 아니다. 의미 분류에서 단위·형식·저장값을 미루어 채우지 않는다. 의미 분류로 정할 수 있는 것은 속성 유형과 거기서 나오는 서식의 자료형뿐이다([`references/서식으로-옮기기.md`](references/서식으로-옮기기.md) 4장).

**스타일 가이드의 설명 예시에서 가져올 것은 설명 틀뿐이다.** 예시가 채워 둔 값 — 단위·형식·저장값·변환 배율 — 은 그 예시가 가정한 자료에서 나온 값이다. 원천이 같은 값을 적어 두지 않았으면 옮겨 적지 않는다.

**그다음 스타일 가이드의 산출물을 서식의 칸에 넣는다.** 어긋나는 자리는 위 문서대로 넘긴다.

### ⑨ 검사하고 리포트를 쓴다

여섯 가지를 확인한다. 앞의 둘은 스크립트가 하고, 뒤의 넷은 사람이 하는 일을 대신한다.

| 무엇을 | 어떻게 |
|---|---|
| 조용히 사라지는 자리가 있는가 | `scripts/check_design_doc.py` 를 돌린다 (아래 2.4) |
| 서식이 실제로 읽히는가 | `graphio-ontology-converter` 의 스크립트 둘로 돌려 본다 — 옮겨지는지, 옮긴 것이 Graphio 규격에 맞는지 (아래 2.4) |
| 가이드의 규칙을 지켰는가 | 가이드의 검사 항목 대목을 펴고 하나씩 짚는다 |
| 질문과 구조가 맞물리는가 | 설계 리포트 1절의 경로를 짚어 양쪽을 대조한다. 답에 이르지 못하는 질문과, 어느 질문도 쓰지 않는 개념을 찾는다 |
| **CQ 문서가 정한 통과 조건을 지켰는가** | CQ 문서가 구조가 지켜야 할 조건을 적어 둔 자리를 펴고 질문마다 짚는다. 경로 홉 수처럼 스크립트가 세지 않는 조건이 여기 있다. 홉 수는 설계 리포트 1절의 홉 수 칸과 맞대 본다. **질문마다 건 조건이 다르면 그 질문에 건 조건을 하나씩 짚고**, 지키지 못한 자리는 검증 리포트 2절에 질문별로 남긴다 |
| **뜻이 다른 컬럼으로 대신 답하지 않았는가** | 설계 리포트 1절의 쓰는 값마다(답과 조건 모두) 그 값을 담은 속성이 **매핑한 컬럼**을 맞대 본다. 속성 이름이 값과 같아도 컬럼을 본다. 뜻이 다르면 매핑을 비우고 설계 리포트 4.1 에 올렸는지 본다. **맞대 본 결과는 값마다 한 줄씩 검증 리포트 3절에 남긴다** — 머릿속으로만 짚으면 짚었는지 알 수 없다. 뜻을 가르는 법과 표의 칸은 [`references/검증-리포트-서식.md`](references/검증-리포트-서식.md) 3절에 있다 |

첫 줄이 따로 있는 이유가 있다. 변환 스크립트는 **서식 오류**를 잡지만, 서식은 맞는데 내용이 새어 나가는 자리는 잡지 못한다. 설명 줄에서 떨어져 나간 `[별칭]`, 조사 괄호가 남은 문장, 한쪽에만 달린 경고문 같은 것들이다. 오류가 나지 않아 아무도 모르고 넘어간다.

**여섯 가지를 모두 검증 리포트 1절에 한 줄씩 남긴다.** 하지 못한 검사도 줄을 남기고 까닭을 적는다. 결과를 남기지 않으면 통과한 문서와 검사하지 않은 문서가 똑같이 보인다.

검증 리포트 뼈대는 [`references/검증-리포트-서식.md`](references/검증-리포트-서식.md) 에 있다. 설계 리포트는 ①~⑧ 이 이미 채웠으므로 이 단계에서 새로 쓰지 않는다 — 검사하다 설계를 바꿨으면 그 자리만 고치고 머리표에 적는다.

## 2) 산출물

파일 세 개를 입력 문서와 같은 폴더에 만든다. 사용자가 위치를 지정하면 그것을 따른다.

| 파일 | 이름 | 답하는 질문 | 읽는 사람 |
|---|---|---|---|
| 온톨로지 정의 | `<이름>-온톨로지-정의.md` | 구조가 무엇인가 | `graphio-ontology-converter` 가 그대로 읽어 JSON 으로 옮긴다 |
| 설계 리포트 | `<이름>-온톨로지-설계-리포트.md` | **이 구조가 왜 이렇게 생겼나** | 사람이 읽고 판단이 맞는지 확인한다 |
| 검증 리포트 | `<이름>-온톨로지-검증-리포트.md` | **이 구조를 믿어도 되나** | 사람이 읽고 넘겨받을지 정한다 |

**설계 판단과 검사 결과를 한 문서에 담지 않는다.** 설계자가 스스로 매긴 판단과 검사로 나온 값이 섞이면 읽는 사람이 둘을 가려내지 못한다. 설계를 고칠 때 보는 문서와 넘겨받은 것을 믿어도 되는지 볼 때 보는 문서는 읽는 때도 읽는 사람도 다르다.

### 2.1 온톨로지 정의 문서

서식 작성 가이드가 정한 네 절을 지킨다. 절 제목은 가이드가 정한 그대로 쓴다 — 한 글자만 달라도 읽히지 않는다.

**맨 앞에 규모를 적는다.** 서식 밖 절이라 변환에 영향을 주지 않으면서, 받는 사람이 첫 화면에서 무엇이 얼마나 들어 있는지 안다. 500줄짜리 문서를 처음부터 읽지 않아도 되게 하는 것이 목적이다.

```markdown
# (이름) 온톨로지 정의

## 규모

| 항목 | 값 |
|---|---|
| 개념 | 9 |
| 속성 | 42 |
| 관계 | 11 |
...
```

**손으로 세지 않는다.** 아래 2.3 의 `--stats` 로 뽑아 그대로 붙인다. 세어서 적으면 틀리고, 틀린 줄 아무도 모른다.

서식이 담지 못하는 것은 **버리지 말고 서식 밖 절에 남긴다.** 네 절이 아닌 `##` 절은 변환할 때 읽히지 않는다. 배경·미확정 항목·검토 기록을 함께 두어도 결과가 달라지지 않는다. 왜 그렇게 정했는지 아는 사람은 설계자뿐이라, 남기지 않으면 그 판단이 사라진다.

### 2.2 설계 리포트

정의 문서가 답하지 못하는 것에 답한다.

| 절 | 답하는 질문 |
|---|---|
| 문서 역할 판정 | 어느 문서를 무슨 역할로 보았고, **무엇을 보고 그렇게 갈랐는가** |
| 1. 연결표 | 어느 질문이 어느 값을 쓰고, 그 값이 어느 개념·속성·관계에 담겼는가 |
| 2. 만든 개념 | **왜 이것을 하나의 개념으로 두었는가** (`개념으로 둔 까닭`) |
| 2.1 이름을 지은 근거 | **왜 이 이름인가.** 입력 문서의 어느 말을 어느 규칙으로 골랐는가 |
| 2.2 질문이 요구하지 않았는데 둔 속성 | 규격이 요구해서 둔 속성은 무엇이고 무엇이 요구했는가 |
| 3. 만든 관계 | 두 개념을 잇는 값이 실제로 있는가. 없으면 무엇이 필요한가 |
| 4 · 4.1 추가로 필요한 메타타입 | 데이터로 동작하려면 무엇을 더 만들어야 하는가 |
| 5. 확인 필요 | 무엇을 아직 모르는가. 누가 언제 채우는가 |
| 6 · 6.1 만들지 않은 것 | 문서에 있었는데 왜 넣지 않았는가 |
| 7. 서식이 담지 못한 것 | 설계했는데 서식에 자리가 없어 밖으로 뺀 것은 무엇인가 |
| 8. 문서끼리 어긋난 자리 | 입력 문서가 서로 다른 말을 한 자리는 어디인가 |

**받는 사람은 이 리포트만 본다.** 스킬의 참고 문서는 볼 수 없고 입력 문서도 옆에 펴 두지 않는다. 그래서 절마다 머리에 무엇을 적은 절인지 설명하는 인용문을 두고, 칸에는 번호 대신 번호가 가리키는 내용을 적는다. 설명과 적는 법은 [`references/설계-리포트-서식.md`](references/설계-리포트-서식.md) 에 있다.

**결과만 적힌 칸은 이 문서에 둘 까닭이 없다.** 무엇을 만들었는지는 정의 문서가 이미 답한다. 이 리포트의 칸은 대부분 「무엇을 보고 그렇게 정했나」 를 받는 자리이고, 그 칸이 비면 판단하지 않았거나 판단을 적지 않은 것이다.

**연결표가 리포트의 값을 만든다.** 이것이 있어야 "왜 이 개념이 있는가"를 질문 쪽에서 되짚을 수 있고, 검증 리포트가 맞댈 원본이 생긴다.

### 2.3 검증 리포트

정의 문서를 믿어도 되는지에 답한다. **⑨ 단계가 통째로 쓴다.**

| 절 | 답하는 질문 |
|---|---|
| 0. 만들어진 것 | 무엇이 얼마나 나왔는가. `--stats` 로 뽑아 붙인다 |
| 1. 돌린 검사 여섯 | **여섯 검사를 실제로 했는가.** 무엇을 읽고 무엇이 걸렸는가 |
| 2. 질문별 판정 | 질문마다 구조가 답하는가. 답하지 못하면 무엇이 빠졌는가 |
| 3. 매핑한 컬럼을 맞대 본 결과 | 뜻이 다른 컬럼으로 대신 답하지 않았는가 |
| 4. 다음에 할 일 | 사람이 이어서 무엇을 해야 하는가 |

**검사했다는 것을 남긴다.** 앞의 세 검사는 지금까지 결과를 남길 자리가 없어서, 통과한 문서와 검사하지 않은 문서가 똑같이 보였다. 여섯 줄을 지우지 않고, 하지 못한 검사도 까닭과 함께 남긴다.

뼈대는 [`references/검증-리포트-서식.md`](references/검증-리포트-서식.md) 에 있다.

### 2.4 두 가지를 돌려 확인한다

**먼저 이 스킬의 검사기를 돌린다.** 오류 없이 사라지는 자리를 찾고, 통계를 함께 낸다.

```bash
python3 scripts/check_design_doc.py <온톨로지-정의.md>
```

통계만 Markdown 표로 뽑아 정의 문서 맨 앞과 검증 리포트 0절에 붙인다.

```bash
python3 scripts/check_design_doc.py <온톨로지-정의.md> --stats
```

가이드가 정한 경고 기호가 `⚠` 가 아니면 알려 준다. 모르고 돌리면 경고문을 못 찾아 그냥 지나간다.

```bash
python3 scripts/check_design_doc.py <온톨로지-정의.md> --warn-mark ※
```

**그다음 자매 스킬의 스크립트로 서식을 확인한다.** 자매 스킬은 이 스킬 폴더와 나란히 있다. `<converter>` 를 실제로 있는 자리로 바꿔 쓴다 — `../graphio-ontology-converter`, `.claude/skills/graphio-ontology-converter`, `~/.claude/skills/graphio-ontology-converter`, hub 저장소면 `skills/graphio-ontology-converter` 다.

```bash
python3 <converter>/scripts/build_graphio_json.py \
  <온톨로지-정의.md> -o /tmp/검사용.json
python3 <converter>/scripts/validate_graphio_json.py /tmp/검사용.json
```

**나온 JSON 은 산출물이 아니다.** 서식이 읽히는지 보려고 돌린 것이므로 임시 자리에 만들고 버린다. JSON 을 만드는 일은 자매 스킬이 따로 한다.

오류가 나오면 **정의 문서를 고친다.** 오류가 짚은 줄을 고쳐 다시 돌린다.

**경고와 보류는 고치는 대상이 아니다.** 규격 검사는 결과를 오류·경고·보류 세 단계로 낸다. 경고는 규격은 통과했지만 의도를 확인하라는 것이라, 의도한 것인지 짚어 검증 리포트 1절에 적는다. 보류는 파일만으로 끝낼 수 없어 대상 환경에서 사람이 마무리할 일이라 검증 리포트 1절과 4절에 함께 올린다. 적지 않으면 넘겨받는 사람은 반입이 왜 막히는지 모른다. 스크립트가 없으면 이 검사를 건너뛰고 검증 리포트 1절 둘째 줄에 "하지 못함 — 자매 스킬 없음" 이라 적는다.

## 3) 가장 자주 빗나가는 자리

설계가 틀리는 방식은 몇 가지로 정해져 있다. 만들기 전에 한 번, 리포트를 쓰기 전에 한 번 짚는다.

| 빗나감 | 어떻게 알아보나 | 왜 생기나 |
|---|---|---|
| 원천을 그대로 옮겼다 | 개념 수가 테이블 수와 같고 속성 이름이 컬럼명과 같다 | 원천 문서가 가장 구체적이라 거기서 시작하고 싶어진다. 시작점은 질문이다 |
| 질문이 쓰지 않는 것을 만들었다 | 연결표에 질문 번호가 비어 있는 행이 있다 | 원천에 있으니 넣어 두자는 판단이다. 쓰이지 않는 개념은 검색을 흐린다 |
| 설명이 짧다 | 한 줄로 끝나고 무엇의 정답인지 적혀 있지 않다 | 설명을 이름의 풀어쓰기로 여긴 것이다. 설명은 검색의 기준점이다 |
| 헷갈리는 개념에 경고가 한쪽만 있다 | A 에는 "B 를 보라"가 있는데 B 에는 없다 | 만들면서 한 방향만 생각한 것이다. 반대 방향 질의에서 그대로 틀린다 |
| 모르는 값을 채웠다 | 코드 저장값이나 단위가 그럴듯하게 적혀 있는데 원천 문서에 근거가 없다 | 빈칸이 미완성으로 보여서다. 틀린 값이 빈칸보다 나쁘다 |
| 설계안을 확인받지 않고 정의 문서를 썼다 | 리포트 머리표의 「설계안 확인」 칸이 비었거나, 확인 뒤 바꾼 설계가 적혀 있지 않다 | 설계와 문서 쓰기를 한 번에 하는 편이 빨라 보여서다. 판단이 틀리면 수백 줄을 다시 쓴다 |
| 잇는 값이 없는데 적어 두지 않았다 | 리포트 「추가로 필요한 메타타입」에 그 관계에 필요한 값이 없다 | 업무상 이어져 보이면 이을 수 있다고 여긴 것이다. 적지 않으면 비어 있는 관계가 잘 된 것처럼 보인다 |

마지막으로 하나. **스타일 가이드와 서식 가이드를 실제로 펴 봤는지 돌아본다.** `--style`·`--format` 으로 다른 가이드가 오면 규칙이 기본과 다르다. 기억으로 만들면 받은 가이드의 규칙을 어기고, 어긴 자리는 검사에도 걸리지 않는다. 검사 항목 역시 가이드 안에 있기 때문이다.
