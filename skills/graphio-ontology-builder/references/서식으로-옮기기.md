# 서식으로 옮기기

설계한 것을 서식의 칸에 넣는 일을 다룬다.

옮기기가 따로 한 절을 차지하는 이유는 **두 가이드가 서로 다른 것을 요구하는 자리가 있기 때문**이다. 스타일 가이드는 설명에 무엇을 담을지 정하고, 서식 가이드는 그것을 담는 그릇의 모양을 정한다. 담을 것이 그릇보다 클 때가 있다.

모르고 옮기면 **설명의 절반이 소리 없이 사라진다.** 오류도 나지 않고 파일도 만들어져서 알아차릴 방법이 없다. 이 문서는 그 자리들을 미리 짚는다.

## 1. 옮기기 전에 정할 것

**서식 가이드를 먼저 편다.** 이 문서는 어긋남이 생기는 자리를 가르치지만, 각 칸의 규칙은 서식 가이드가 정한다. 서식이 바뀌면 여기 적힌 예시도 맞지 않을 수 있다. **두 문서가 다르면 서식 가이드가 맞다.**

어긋날 때의 원칙은 하나다.

> **그릇을 먼저 맞춘다. 담을 것을 조정하되 뜻을 잃지 않게 한다. 그래도 안 들어가면 서식 밖 절에 남긴다.**

서식 제약을 어기면 문서가 읽히지 않거나 내용이 잘려 나간다. 그래서 **형식은 서식 가이드를 따른다.** 다만 **조정은 형식만 바꾸는 일이지 내용을 줄이는 일이 아니다.** 줄이면 스타일 가이드가 그것을 넣으라고 한 이유가 함께 사라진다.

**막는 것과 권하는 것을 가른다.** 서식 가이드에는 「이렇게 하면 읽기 쉽다」고 **권한** 것이 있다. 그것이 스타일 가이드의 규칙과 부딪치면 **스타일 가이드를 따른다.** 권고는 그릇의 제약이 아니기 때문이다.

| 어떤 자리 | 무엇을 따르나 | 예 |
|---|---|---|
| 서식이 막는다 | 서식 가이드 | 개념 이름에 공백을 쓸 수 없으면 공백을 쓰지 않는다 |
| 서식이 권하고 스타일 가이드가 막는다 | 스타일 가이드 | 관계 이름을 `사원_부서` 꼴로 권해도, 스타일 가이드가 밑줄을 막으면 밑줄을 쓰지 않는다 |

권고의 **뜻**은 대개 다른 방법으로도 지킬 수 있다. 위 예에서 양끝을 담아 구분하기 쉽게 하라는 뜻은 `사원의 부서`처럼 밑줄 없이도 지켜진다(여기서 보는 것은 밑줄뿐이다. 이름에 하는 일을 넣을지는 3.3 이 따로 정한다). 이름을 실행마다 다르게 지으면 같은 설계를 두 번 돌렸을 때 관계 이름이 하나도 겹치지 않는다.

## 2. 어디에 무엇이 들어가나

스타일 가이드가 만들라고 한 것과 서식의 칸을 잇는 표다. 칸 이름은 서식 가이드가 정한 것을 쓴다.

| 설계 산출 | 서식의 자리 | 주의 |
|---|---|---|
| 개념 이름 | 개념 제목 | 이름 형식 제약이 있다 (3.3) |
| 개념 설명 전체 | 개념의 설명 줄 | 여러 줄이면 한 줄로 합친다 (3.1) |
| 속성 이름 | 속성 표의 이름 칸 | 대개 형식 제약이 없다. 띄어쓰기를 그대로 쓸 수 있다 |
| 속성 유형 | 속성 표의 자료형 칸 | 유형을 자료형으로 옮긴다 (4장) |
| 속성 설명 | 속성 표의 설명 칸 | 표 안이라 세로줄을 쓸 수 없다 (3.2) |
| 식별 속성·대표 표시 속성 | 속성 표의 해당 칸 | 개수 제약이 있다 (3.5) |
| 관계 이름·출발·도착·조인 속성·방향 | 관계 표의 각 칸 | 조인 속성은 양쪽 개념에 실제로 있어야 한다 |
| 관계 설명과 조인 명세 | 관계 표의 설명 칸 | 여러 줄이면 한 줄로 합친다. 세로줄도 쓸 수 없다 |
| 원천 테이블·컬럼 | 데이터 구조 절 | 대상 환경에 등록된 이름과 같아야 한다. 아직 없는 구조는 2.1 로 짓고 종류는 2.2 로 정한다 |
| 속성과 컬럼의 짝 | 매핑 절 | 양쪽 이름이 실제로 있어야 한다 |
| 담지 못한 것 | 서식 밖 절 | 5장 |

### 2.1 아직 없는 데이터 구조의 이름

전처리를 해야 생기는 테이블과 이 설계에서 처음 정하는 문서 타입은 **대상 환경에 아직 없다.** 이름을 정해 둔 문서도 없으므로 설계가 짓는다.

**그 데이터를 쓰는 개념의 이름을 그대로 쓴다.**

**새 테이블은 원천 테이블과 같은 묶음으로 보이게 짓는다.** 대상 환경에서 나란히 보여야 찾기 쉽기 때문이다. 원천 테이블 이름에 **공통으로 붙은 말**이 있으면 새 테이블 이름에도 같은 자리에 붙인다. 공통으로 붙은 말은 아래로 가린다.

| 물음 | 어떻게 |
|---|---|
| 무엇을 말로 보나 | 이름의 맨 앞이나 맨 뒤에서 구분 기호(`_`·`-`)로 끊기는 조각 하나. 구분 기호 없이 이어 쓴 이름에서는 찾지 않는다 |
| 몇이 같아야 하나 | 원천 테이블이 둘 이상이고 **모두** 같아야 한다. 하나뿐이거나 일부만 같으면 관례로 보지 않고 붙이지 않는다 — 어느 쪽을 따를지 실행마다 달라진다 |
| 앞과 뒤가 모두 같으면 | 둘 다 붙인다 |
| 구별하는 말(아래)도 붙여야 하면 | 구별하는 말을 개념 이름 바로 뒤에 붙이고, 공통으로 붙은 말은 그 바깥에 둔다 — `EQ_부품마스터`, `부품마스터_TB` |

**문서 타입 이름에는 붙이지 않는다.** 원천 테이블의 묶음이 아니기 때문이다.

| 개념 | 데이터 구조 이름 |
|---|---|
| 재고부품 | 원천 테이블 이름이 모두 `EQ_` 로 시작하면 `EQ_재고부품`, 모두 `_TB` 로 끝나면 `재고부품_TB` |
| 정비공정 | 문서 타입이면 붙이지 않고 `정비공정` |

**만드는 방법을 이름에 넣지 않는다.** `_펼침`·`_분리` 같은 말은 그때 한 일이지 그 데이터가 무엇인지가 아니다. 개념과 이름이 다르면 읽는 사람이 둘을 잇지 못하고, 실행마다 다른 이름이 나온다.

**새로 지은 이름이 이미 있는 원천 테이블과 같으면 구별하는 말을 뒤에 붙인다.** 그대로 두면 다른 데이터를 담은 두 구조가 대상 환경에서 한 이름으로 부딪힌다. 붙이는 말은 **그 데이터가 무엇인지**를 말해야 한다. 만드는 방법을 말하면 위 문단에 걸린다.

| 새로 짓는 구조 | 어떻게 하나 |
|---|---|
| 흩어진 코드와 이름을 모아 만드는 구조 | 「마스터」 를 붙인다. [`개념을-더-둘-때.md`](개념을-더-둘-때.md) 4장이 이런 구조를 마스터라 부른다. 개념이 `부품` 인데 원천의 `EQ_부품` 이 다른 데이터를 담고 있으면 `EQ_부품마스터` 다 |
| 그 밖의 구조 | 먼저 그 원천 테이블이 같은 데이터를 이미 담고 있는지 본다. 원천 자료가 그 테이블에 무엇이 담겼다고 적었는지를 새 구조가 담으려는 것과 견준다. 뭉친 칸을 편 구조면 [`개념을-더-둘-때.md`](개념을-더-둘-때.md) 5장 「이미 펼쳐진 테이블이 원천에 있으면」 을 따른다. 담고 있으면 새로 짓지 않고 그 테이블을 쓴다. 다른 데이터면 그 데이터가 무엇인지 말하는 낱말을 붙이고, 정해 둔 말이 없어 고른 것이라는 사실을 설계 리포트 4절 「어떻게 만드나」 칸에 함께 적는다 |

**개념 이름은 바꾸지 않는다.** 사람이 읽는 이름을 데이터 사정으로 바꾸면 업무에서 부르는 말과 갈린다. 붙인 말과 까닭은 설계 리포트 4절 「어떻게 만드나」 칸에 적는다.

**새로 짓지 않고 원천 테이블을 쓰기로 했으면 기록을 맞춘다.** 정의 문서의 데이터 구조 절과 매핑 절에 그 원천 테이블 이름을 적고, 설계 리포트 4절에 올려 둔 그 구조의 줄을 지운다. 설계안을 확인받은 뒤에 바꾼 것이면 머리표 「설계안 확인」 칸에 무엇을 왜 바꿨는지 적는다.

**테이블의 컬럼 이름은 원천 관례를 따른다.** 적재 담당자가 이 이름 그대로 만들기 때문이다. 기존 메타타입에 더하는 컬럼(리포트 4.1)도 같다. 여기서 원천은 정형 원천 문서가 적은 적재 테이블이다. 그 위의 명세(원천 시스템의 항목 이름 같은 것)는 따르지 않는다.

| 어떤 컬럼 | 이름 | 예 |
|---|---|---|
| 원천 적재 테이블에 같은 값의 컬럼이 있다 (조인 키, 다른 테이블에서 옮기거나 모아 오는 값, 뭉친 칸에서 꺼냈지만 다른 테이블에 같은 컬럼이 있는 값) | 그 컬럼 이름을 한 글자도 바꾸지 않는다 | `설비관리번호`, `부품관리번호` |
| 그 값만 담은 컬럼이 원천 어디에도 없다 (결합 값에서 떼어 낸 값, 원천에 없어 밖에서 받는 값) | 속성 이름을 원천 꼴로 적는다 | `누적 가동시간` → `누적가동시간`, `교체 시점` → `교체시점` |

조인 키가 원천과 같은 이름이면 두 구조를 잇는 자리가 바로 읽힌다.

**원천 꼴은 낱말을 잇는 방식 하나만 본다.** 붙여 쓰기·밑줄·띄어쓰기처럼 낱말을 잇는 방식 가운데 원천 컬럼 이름에 가장 많이 쓰인 것을 따른다. 몇 개가 다르게 적혀 있어도 관례가 갈린 것으로 보지 않는다. **낱말은 바꾸지 않는다** — `교체 시점` 은 `교체시점` 이지 `교체일시` 가 아니다. 이미 있는 컬럼은 이 꼴에 맞추지 않고 원천에 적힌 그대로 둔다. 원천 컬럼 이름이 영문처럼 속성 이름과 다른 글자로 적혀 있으면 아래 문단을 따른다.

그 값만 담은 컬럼(표 둘째 줄)인데 원천 컬럼 이름이 영문처럼 속성 이름과 다른 글자로 적혀 있으면, 잇는 방식도 따르지 않고 속성 이름을 그대로 쓴다. 컬럼은 리포트 4절이나 4.1 에 그대로 올리고, 원천 꼴의 이름을 누가 정할지는 5절에 따로 올린다. 이름을 지어내지 않는다.

원천 컬럼 이름은 데이터 구조 절의 `컬럼` 칸에 적는 이름이다. 새로 적는 컬럼의 `원천 컬럼명` 칸에는 원천 컬럼 하나를 그대로 옮길 때만 그 이름을 적고, 나머지는 비운다.

**문서 타입의 사용자 정의 프로퍼티 이름은 그 값을 담는 속성 이름과 같게 적는다.** 문서 타입은 원천 테이블이 아니라 설계가 선언하는 구조라서 따를 원천 관례가 없다. 원천 컬럼명을 가져다 쓴 것이 아니므로, 속성 이름이 원천 컬럼명과 같은지 보는 가이드 검사에는 걸리지 않는 것으로 본다.

정의 문서와 리포트에 **같은 이름**으로 적는다. 대상 환경에는 이 이름으로 만들어져야 반입된다.

### 2.2 아직 없는 데이터 구조의 종류

아직 없는 구조는 어느 종류로 만들지도 설계가 정한다. 종류가 갈리면 컬럼 구성까지 달라진다.

| 무엇에서 나오나 | 종류 | 컬럼에 적는 것 |
|---|---|---|
| 원천 테이블을 나누거나 모아 만드는 테이블 | `CUSTOM` | 2.1 로 지은 컬럼 |
| 문서에서 뽑는 문서 타입 | `DOC_TYPE` | 스타일 가이드가 문서 타입에 두라고 한 사용자 정의 프로퍼티와, 매핑 절이 가리키는 기본 프로퍼티 |

**문서 타입은 `DOC_TYPE` 으로 적는다.** 문서 타입은 질문이 조건이나 답으로 쓰는 항목을 골라 선언한 것이고, 그 탐색·출력 속성에서 파생되는 종류가 `DOC_TYPE` 이다. 조각 본문이나 임베딩처럼 문서 타입에 기본으로 있는 프로퍼티는 저절로 생긴다. 그래서 매핑에 쓰는 것만 옮겨 적는다.

**종류는 서식이 막는 자리가 아니라 설계가 고르는 자리다.** 1절의 「두 문서가 다르면 서식 가이드가 맞다」로 뒤집지 않는다. 기본 프로퍼티를 매핑했으면 그 프로퍼티가 대상 환경의 이 구조에 실제로 있는지 리포트 5절에 올린다.

대상 환경에 이미 있는 구조는 등록된 종류를 그대로 쓴다.

## 3. 어긋나는 자리 다섯

### 3.1 여러 줄 설명이 한 줄로 들어간다

**가장 위험한 자리다.** 설명이 소리 없이 사라지는 곳이 여기다.

스타일 가이드는 대개 설명을 여러 줄로 정한다. 정의하는 문장을 쓰고, 그 아래 원천 정보를 적고, 별칭을 적고, 질문 예시를 적는 식이다.

그런데 서식의 설명 줄은 **한 줄만 읽는다.** 둘째 줄부터는 오류도 없이 그냥 버려진다.

```markdown
- 설명: 배송주문은 ... 담는 데이터다. ... 질문의 정답 테이블이다.
[SQL] logi.delivery_order | PK: ...          ← 사라진다
[별칭] 주문, 배송 건, 출고 주문                ← 사라진다
[질문예시] 어제 접수된 배송주문은 무엇인가       ← 사라진다
```

**한 줄로 이어 붙인다.** 표기 기호는 그대로 두고 줄바꿈만 없앤다.

```markdown
- 설명: 배송주문은 ... 담는 데이터다. ... 질문의 정답 테이블이다. [SQL] logi.delivery_order | PK: ... [별칭] 주문, 배송 건, 출고 주문 [질문예시] 어제 접수된 배송주문은 무엇인가
```

이어 붙여도 뜻은 그대로다. 설명은 통째로 임베딩되어 검색에 쓰이므로 **한 덩어리 글이 되는 편이 오히려 맞다.** 줄바꿈은 사람이 읽기 좋으라고 넣은 것이지 뜻을 나누는 것이 아니다.

주의할 점 둘.

- **표기 기호를 바꾸지 않는다.** 대괄호와 기호는 나중에 사람이 훑어볼 때 구획을 짚어 주는 표지다. 이어 붙이면서 지우면 한 문단이 되어 읽을 수 없다
- **설명 줄에서는 세로줄을 써도 된다.** 표 밖이라 칸이 나뉘지 않는다. 원천 정보에 세로줄이 들어가는 형식이면 그대로 둔다

### 3.2 표 안에서는 세로줄을 쓸 수 없다

속성 설명과 관계 설명은 표 안에 들어간다. 표는 세로줄로 칸을 나누므로 **설명에 세로줄이 들어가면 그 자리에서 칸이 쪼개진다.** 표가 통째로 어긋나고, 그 뒤 줄이 전부 밀린다.

빠져나갈 길이 없다. 표 안에서는 다른 기호를 쓴다.

| 쓰려던 것 | 표 안에서 |
|---|---|
| 값을 나열하는 세로줄 | 쉼표나 가운뎃점 |
| 구획을 나누는 세로줄 | 마침표로 문장을 끊는다 |

경고 기호나 대괄호는 그대로 써도 된다. 칸을 나누지 않기 때문이다.

### 3.3 개념 이름에 띄어쓰기를 쓸 수 없다

스타일 가이드는 대개 이름에 띄어쓰기를 요구한다. 사람이 읽는 이름이기 때문이다. 그런데 **개념 이름에는 형식 제약이 있다.** 흔한 제약은 이렇다.

- 영문이나 한글로 시작한다
- 그다음은 영문·숫자·한글·밑줄만 쓴다
- 공백·하이픈·마침표·괄호를 쓸 수 없다
- 길이 제한이 있다

**개념 이름만 걸린다.** 속성 이름은 대개 제약이 없어 띄어쓰기를 그대로 쓸 수 있다. 두 자리의 규칙이 다르다는 것을 알아 두면 불필요하게 속성 이름까지 붙여 쓰지 않는다.

| 자리 | 띄어쓰기 |
|---|---|
| 개념 이름 | 쓸 수 없다. 붙여 쓴다 |
| 속성 이름 | 쓸 수 있다. 스타일 가이드대로 띄어 쓴다 |
| 관계 이름 | 서식 가이드를 확인한다. 서식이 `사원_부서` 꼴을 권하면 양끝을 담는다 — 스타일 가이드가 밑줄을 막지 않으면 그 꼴 그대로, 막으면 밑줄 없이 담는다 (1절). 무슨 말로 담을지는 아래 문단이 정한다 |
| 설명 본문 | 제약이 없다 |

붙여 쓴다고 뜻이 사라지지는 않는다. `배송지변경이력` 은 붙여 써도 읽힌다. 개념 이름에 밑줄은 두 가이드 가운데 하나가 밑줄로 이으라고 정했을 때만 쓴다. 읽기 어렵다는 이유로 고르면 실행마다 갈린다.

**관계 이름에는 양끝을 담는다.** 가이드 예시가 한쪽 끝만 담았으면 빠진 끝을 붙인다. 스타일 가이드가 「무엇을 하는지」를 요구하면 그 위에 하는 일을 얹는다.

**하는 일을 담을 말은 차례로 찾는다. 지어내지 않는다.** 그리고 **그 말이 이 관계의 두 끝을 잇는 말일 때만 쓴다** — 출발 개념 이름에 든 동작 말이라도 다른 관계를 가리키면 쓰지 않고 다음 차례로 간다.

| 차례 | 어디서 고르나 | 예 |
|---|---|---|
| ① | 출발 개념 이름에 이미 든 동작 말 | `점검이력` 의 「점검」 → `점검이력이 점검한 설비` |
| ② | 근거 질문이 두 개념 사이를 적은 말 | 질문이 「공장이 운영하는 설비」라고 적었으면 「운영」 |
| ③ | 둘 다 없다 | 양끝만 담는다 (`점검교체부품의 부품`) |

질문이 적은 말의 **방향이 관계와 반대면 뒤집지 않는다.** 뒤집으려면 없는 말이 들기 때문이다 — ③으로 간다.

**조인 속성 이름에서는 고르지 않는다.** 스타일 가이드가 조인 키 이름을 관계 이름에 쓰지 못하게 막는 일이 많다. **역할을 가르는 관계도 양끝만 담는다** — 역할 명사가 무엇을 하는 자리인지 이미 말하기 때문이다(`구매주문의 공급사`, [`개념을-더-둘-때.md`](개념을-더-둘-때.md) 3장).

차례를 정해 두는 까닭은 하나다. 없는 말을 지어내면 같은 관계에 실행마다 다른 낱말이 붙는다.

**이름을 줄이지 않는다.** 길어서 붙여 쓰기 어렵다고 `이력` 으로 줄이면 무엇의 이력인지 사라진다. 서식이 막는 것은 공백이지 길이가 아니다.

### 3.4 템플릿의 조사를 앞말에 맞춘다

가이드의 설명 템플릿에는 `{개념}이(가)`, `{개념}은(는)`, `{개념}을(를)` 처럼 조사를 둘 다 적어 둔 자리가 있다. 어느 쪽이 올지 템플릿을 쓸 때는 알 수 없기 때문이다.

**값을 넣을 때 하나를 고른다.** 괄호째 옮기면 `설비이(가) 아니라` 처럼 읽히지 않는 문장이 된다.

| 앞말 | 고르는 것 |
|---|---|
| 받침이 있다 (점검이력, 주문서) | 이, 은, 을, 과 |
| 받침이 없다 (설비, 부품) | 가, 는, 를, 와 |

설명은 사람이 읽고 검색에도 쓰이는 글이다. 기호가 섞이면 두 쪽 다 나빠진다.

### 3.5 개수가 정해진 칸이 있다

대표 표시 속성은 개념마다 **정확히 하나**여야 하는 것이 보통이다. 없으면 규격에 걸려 적용이 막히고, 둘이면 무엇으로 보여 줄지 정해지지 않는다.

식별 속성은 대개 **하나까지**다. 없어도 된다.

여기서 자주 걸리는 자리가 **복합키**다. 두 값을 합쳐야 한 건이 가려지는 경우인데, 식별 속성이 하나까지라 담을 수 없다. 식별 표시를 비우고 두 속성은 그대로 둔다. 관계는 식별 속성을 요구하지 않으므로 조인은 그대로 된다. 그리고 **왜 비웠는지 서식 밖 절에 적는다.**

## 4. 자료형 정하기

서식은 정해진 자료형 중 하나를 요구한다.

**원천 자료에 자료형이 적혀 있으면 그것을 서식의 자료형으로 옮긴다.** 글자 자료형은 `TEXT`, 정수는 `INTEGER` 처럼 뜻이 같은 것으로 옮긴다. 서식 가이드의 자료형 목록에 맞는 것이 없으면 아래 「흔한 대응」 표의 의미 분류로 돌아가 정하고, 그렇게 정했다는 것을 설계 리포트 5절에 올린다. 자료형이 적혀 있어도 속성 유형은 아래처럼 정한다 — 유형이 설명 형식을 정하기 때문이다.

자료형이 적혀 있지 않은 자료도 많다. 대신 값이 어떤 종류인지를 말로 적어 둔 의미 분류만 있다. 아래는 그때 쓴다.

### 두 단계로 옮긴다

의미 분류를 바로 자료형으로 바꾸지 않는다. **스타일 가이드가 정한 속성 유형을 거친다.**

```
원천의 의미 분류  →  스타일 가이드의 속성 유형  →  서식의 자료형
   "시점"              시점형                      DATETIME
```

가운데를 거치는 이유는 속성 유형이 설명 형식도 함께 정하기 때문이다. 유형을 정해야 그 유형에 맞는 설명을 쓸 수 있다. 자료형만 정하면 설명이 비어 버린다.

### 흔한 대응

서식 가이드가 정한 자료형 목록을 확인하고 옮긴다. 아래는 흔한 대응이고 확정이 아니다.

| 의미 분류 | 자료형 | 확인할 것 |
|---|---|---|
| 시점·일시·날짜 | `DATETIME` | 문자열로 저장된 날짜면 `TEXT` 다. **형식은 이 표로 정해지지 않는다** |
| 금액·수량 | `INTEGER` 또는 `FLOAT8` | 소수가 있는지 확인한다. **단위는 이 표로 정해지지 않는다** |
| 비율·율 | `FLOAT8` | |
| 여부 | `BOOLEAN` 또는 `TEXT` | `Y`·`N` 문자로 저장된 것을 확인했으면 `TEXT` 다. **저장값은 이 표로 정해지지 않는다** |
| 식별자·번호·코드·명칭·주소·본문 | `TEXT` | |
| 한 칸에 여러 값 | — | 속성으로 만들지 않는다. 개념으로 나눌지 판단한다 |

### 근거가 약하면 설계 리포트 5절에 적는다

자료형은 **틀려도 문서가 만들어진다.** 오류가 나지 않으니 아무도 모르고 지나가고, 반입한 뒤 비교가 어긋나서야 드러난다.

그래서 추정한 자리는 설계 리포트 5절에 모은다.

| 자주 흔들리는 자리 | 왜 |
|---|---|
| 여부 항목 | `Y`·`N` 문자인지 참·거짓인지 원천을 봐야 안다 |
| 금액 | 소수가 있는지 원천을 봐야 안다 |
| 기간 | 시작과 끝 두 값인지 한 문자열인지 다르다 |
| 날짜를 문자열로 저장한 것 | 형식만 보고는 가려지지 않는다 |

### 판별할 수 없다는 뜻의 자료형을 함부로 쓰지 않는다

서식에 `UNKNOWN` 같은 값이 있더라도 **원천을 아직 못 봐서 비워 두는 자리로 쓰지 않는다.** 받는 사람은 그것을 판별한 결과로 읽는다. "확인하지 못했다"는 설계 리포트 5절에 적을 말이지 자료형 칸에 적을 말이 아니다.

가장 그럴듯한 자료형을 적고, 근거가 약하다는 것을 설계 리포트 5절에 적는다. 「흔한 대응」 표에 자료형이 둘 적힌 줄이면 앞의 것이 가장 그럴듯한 자료형이다. 그 자료형을 적은 속성의 설명에 `확인 필요` 가 있으면 5절의 같은 줄 「무엇을 모르나」 칸에 함께 적는다.

### 자료형을 골랐다고 설명이 채워지는 것은 아니다

이 장은 **자료형 칸 하나**를 정한다. 설명 안의 값은 다른 규칙을 받는다.

| 채울 자리 | 모를 때 |
|---|---|
| 서식의 자료형 칸 | 앞에서 고른 자료형을 그대로 둔다. 확인하지 못했다는 이유로 `TEXT` 로 바꿔 두지 않는다 |
| 설명 안의 값 — 단위·형식·저장값 같은 것 | `확인 필요` 라고 적는다 |

자료형은 의미 분류에서 고를 수 있지만, 단위와 형식은 원천이 글자로 적어 두어야 안다. 스타일 가이드의 설명 틀이 두 값을 한 문장에 묶어 두었어도 **모르는 칸에는 `확인 필요` 를 넣어 문장을 끝까지 쓴다.** 자료형을 골랐다는 이유로 같은 문장의 다른 빈칸까지 채우지 않는다. 설명에 자료형을 적는 자리는 모르는 칸이 아니다 — 자료형 칸에 적은 것과 같은 자료형을 적는다.

## 5. 서식이 담지 못하는 것

설계하면서 정한 것 중 서식에 자리가 없는 것이 나온다. **버리지 않는다.** 네 절이 아닌 절은 변환할 때 읽히지 않으므로 같은 문서에 그대로 두어도 결과가 달라지지 않는다.

| 담지 못하는 것 | 어떻게 하나 |
|---|---|
| 복합키 | 식별 표시를 비우고 두 속성은 그대로 둔다. 이유를 밖에 적는다 |
| 계산해서 얻는 값 | 원천에 컬럼이 있으면 속성으로, 화면에서 계산하면 적지 않고 밖에 남긴다 |
| 관계에 딸린 값 | 관계는 속성을 가질 수 없다. 가운데 개념을 두고 그 속성으로 적는다 |
| 자기 자신을 가리키는 계층 | 상위 식별자를 속성으로만 적는다 |
| 속성의 값 목록 | 속성 설명에 적는다 |
| 필수 여부·기본값·길이 제한 | 속성 설명에 적는다 |
| 질문에 답할 수 있는지 확인한 결과 | 밖에 남긴다. 구조가 맞는지 확인하는 근거가 된다 |
| 확정하지 못한 것 | 밖에 남긴다 |

**밖에 남긴 것은 리포트에도 적는다.** 정의 문서를 받는 사람과 리포트를 읽는 사람이 다를 수 있다.

### 왜 남기는 것이 중요한가

왜 그렇게 정했는지 아는 사람은 설계자뿐이다. 남기지 않으면 그 판단은 사라지고, 다음 사람이 같은 자리에서 같은 고민을 다시 한다. 더 나쁜 경우에는 "빠뜨린 것"으로 보고 되돌려 놓는다.

## 6. 옮긴 뒤 확인

옮기고 나서 **반드시 두 스크립트를 돌려 본다.** 사람 눈으로는 사라진 줄이 보이지 않는다.

먼저 이 스킬의 검사기다. 오류 없이 새어 나가는 자리를 찾는다 — 떨어져 나간 설명 줄,
남아 있는 조사 괄호, 한쪽에만 달린 경고문, 칸 수가 어긋난 표.

```bash
python3 scripts/check_design_doc.py <온톨로지-정의.md>
python3 scripts/check_design_doc.py <온톨로지-정의.md> --warn-mark ※   # 경고 기호가 다르면
```

그다음 자매 스킬의 변환·검증 스크립트로 서식을 확인한다. `<converter>` 는 이 스킬 폴더와 나란히 있는 `graphio-ontology-converter` 폴더다 — 실제 자리는 SKILL.md 의 `0) 시작하기 전에` 에 적혀 있다.

```bash
python3 <converter>/scripts/build_graphio_json.py \
  <온톨로지-정의.md> -o /tmp/검사용.json
python3 <converter>/scripts/validate_graphio_json.py /tmp/검사용.json
```

나온 파일은 검사용이라 버린다. 산출물이 아니다.

### 눈으로 확인할 것

스크립트가 잡지 못하는 것이 있다. 내용이 사라졌는지는 기계가 알 수 없다.

- [ ] 개념 설명 줄에 스타일 가이드가 요구한 구성 요소가 **모두** 들어 있는가
- [ ] 별칭과 질문예시가 설명 줄 안에 있는가. 아래로 떨어져 나가지 않았는가
- [ ] 속성 설명과 관계 설명에 세로줄이 없는가
- [ ] 표의 칸 수가 머리글과 맞는가
- [ ] 헷갈리는 개념 쌍의 **양쪽 모두**에 경고가 있는가
- [ ] 템플릿의 `이(가)` 같은 조사 괄호가 그대로 남지 않았는가
- [ ] 이름을 줄이면서 뜻이 빠지지 않았는가
- [ ] 서식이 담지 못한 것이 밖에 남아 있는가

### 스크립트가 없으면

자매 스킬이 없는 환경이면 서식 검사를 건너뛴다. 이 스킬의 검사기는 그대로 돌아간다. 대신 검증 리포트 1절 둘째 줄에 **"하지 못함 — 자매 스킬 없음"** 이라 적는다. 검사한 문서와 하지 않은 문서는 믿을 수 있는 정도가 다르고, 받는 사람이 그것을 알아야 한다.
