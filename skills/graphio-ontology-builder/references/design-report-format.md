# 설계 리포트 서식

설계 리포트는 **정의 문서가 답하지 못하는 것에 답한다.** 정의 문서에는 결과만 있고 판단이 없다. 왜 이 개념을 만들었는지, 무엇을 일부러 만들지 않았는지, 무엇을 아직 모르는지는 리포트에만 있다.

판단을 남기지 않으면 받는 사람은 결과가 맞는지 확인할 수 없다. 확인할 수 없는 구조는 고칠 수도 없어서, 결국 처음부터 다시 만들게 된다.

**결과마다 그렇게 정한 근거를 함께 적는다.** 무엇을 만들었는지만 적힌 표는 정의 문서가 이미 답하는 것이라 여기 실을 까닭이 없다. 이 문서의 칸은 대부분 「무엇을 보고 그렇게 정했나」 를 받는 곳이다.

**검사 결과는 여기 적지 않는다.** 구조가 CQ에 답하는지, 서식대로 읽히는지는 [`verification-report-format.md`](verification-report-format.md) 가 받는다. 설계자가 스스로 매긴 판단과 검사로 나온 값을 한 문서에 섞으면 읽는 사람이 둘을 가려내지 못한다.

**문서의 꼴과 문체는 [`report-conventions.md`](report-conventions.md) 를 따른다.** 해당 없는 절은 지우지 않고 「해당 없음」 한 줄로 남긴다. 절을 지우면 읽는 사람이 빠뜨린 것으로 읽는다. 「해당 없음」은 확인했는데 없다는 뜻이라 다르다.

## 뼈대

뼈대는 [`../assets/design-report-skeleton.md`](../assets/design-report-skeleton.md) 에 있다. **그 파일을 복사해 자리표시만 채운다.** 개조식 문장과 표는 그대로 옮긴다 — 받는 사람은 누구나 이 리포트를 처음 읽고, 스킬의 참고 문서도 볼 수 없다. 절 제목만으로는 무엇을 적은 절인지 알 수 없으므로 1. 개요와 절 첫머리 설명을 빼지 않는다.

**자리표시는 괄호로 적은 설명이다** — 「(경로)」·「(확인 결과)」·「n건」·「YYYY-MM-DD」 같은 것. 채워서 바꾼다. 본문 문장 속의 괄호(「개념(Object Type)」·「(예: 사원, 부서, 휴가신청)」)는 자리표시가 아니라 그대로 둔다.

**뼈대와 이 문서를 나눠 둔 까닭이 있다.** 뼈대 파일에는 산출물에 들어갈 말만 있고, 무엇을 어떻게 채우는지는 아래 「절마다 적을 것」 에만 있다. 한 파일에 섞여 있으면 뼈대를 복사할 때 지시문도 산출물에 옮겨진다.

자리표시를 채울 때 빠뜨리기 쉬운 것:

- 2절 「설계안 확인 후 변경」 이 「해당 없음」 이면 표 아래 `※ 변경` 줄을 두지 않는다. 「외부 수정」 과 `※ 외부 수정` 줄, 「스킬 수정」 과 `※ 스킬 수정` 줄도 같다. `※ CQ 변경` 줄은 CQ 문서가 앞 차수와 달라진 차수와, ⑥ 에서 CQ 증분 반영을 한 차수에만 둔다
- 문서 정보 표의 「차수」·「스킬 판본」 행은 1차에도 채운다. 1차의 「앞 차수 설계 리포트」 는 「해당 없음」 이다. 「리포트 판」 행은 ⑥ 앞에 「설계 단계」로 적고 ⑨ 걸음 4 끝에 「검증 뒤」로 바꾼다. 설계 수정 차수의 N차는 설계 단계를 거쳐 ⑨ 걸음 4 끝에 「검증 뒤」가 된다. 검증만 모드의 N차는 「검증 뒤」다
- 3절 역할 판정 표는 ① 에서 가린 역할 배정을 그대로 남기고, 판정 근거 칸을 비우지 않는다
- 3절 입력 문서 기재 사항 표의 구분은 `확정 가정`·`결정 사항`·`미제공 역할` 가운데 하나다. 해당하는 것이 없으면 표 대신 「해당 없음」 한 줄

## 절마다 적을 것

### 모든 절에 — 이 리포트만 보고 알 수 있게 적는다

리포트를 받는 사람은 스킬의 참고 문서를 볼 수 없고, 입력 문서를 옆에 펴 두지도 않는다. **칸에 번호나 규칙 이름만 적으면 읽히지 않는다.** 판단을 적었어도 읽는 사람이 되짚을 수 없으면 적지 않은 것과 같다.

| 잘못된 예 | 올바른 예 |
|---|---|
| 개념을 더 둘 때 3장 첫 신호 | 역할에 딸린 값을 묻는 CQ 없음 |
| ① 그 값을 든 개념이 둘 이상인가 | '여러 개념이 같은 값을 가지나 그 값이 개념이 아님' 미충족. 직급코드를 가진 개념이 1건뿐임 |
| CQ-53 이 부록으로 빠졌다 | 부서별 초과 근무 시간 CQ(CQ-53)가 이번 범위에서 제외됨(CQ 문서 부록) |
| 가정 A-3 이 있다 | CQ 문서 가정 '휴직 기간은 근속 기간에 넣지 않음'(가정 A-3) |
| TB_직급 | 직급 목록 테이블(`TB_직급`) |

규칙은 셋이다.

1. **스킬 참고 문서의 장 번호는 적지 않는다.** 「개념을 더 둘 때 3장」 은 리포트 밖에 있어 받는 사람이 펼 수 없다. 그 장이 정한 조건을 말로 적는다. 개념을 더 두는 조건은 1.4 의 네 조건 이름으로 부른다.
2. **입력 문서의 번호는 괄호 안 출처로 둔다.** CQ·가정·결정·절 번호는 찾아갈 주소일 뿐 근거가 아니다. 본문에는 번호가 가리키는 내용을 적는다 — CQ면 무엇을 묻는지, 가정이면 무엇을 가정했는지.
3. **원천의 테이블·컬럼 이름은 뜻과 함께 적는다.** 식별자만 적으면 원천 스키마를 모르는 사람은 무엇인지 모른다.

**같은 번호가 한 절에 여러 번 나오면 처음 한 번만 풀어 적는다.** 매번 풀면 표가 오히려 읽기 어려워진다.

**리포트 안에 풀이가 있는 번호는 써도 된다.** CQ 번호는 4절에서 내용이 풀리므로 다른 절에서 번호만 적어도 된다. 입력 문서를 약칭으로 부르려면, 그 약칭이 3절의 어느 문서인지 알 수 있어야 한다. 파일 이름에 약칭이 드러나지 않으면 판정 근거 칸에 이 리포트에서 그 문서를 무엇이라 부르는지 적어 둔다.

### 문서 정보 표의 차수와 스킬 판본

**「차수」 에는 이 리포트가 몇 번째 검증에 딸린 것인지 적는다.** 설계 전체를 수행한 리포트는 「1차」 다. 검증만 모드(①~⑧을 다시 하지 않고 고친 정의 문서로 검사·판정만 다시 하는 단계. 1차 설계의 ⑨와 다름)로 다시 맞춘 리포트는 파일 이름의 차수와 같게 「2차」·「3차」 로 적고, 「앞 차수 설계 리포트」 에 복사해 온 앞 차수 파일의 경로를 적는다. 수정 단계(`--fix`)에 이어 수행한 검증도 검증만 모드라 같다. 차수를 가르는 법과 파일 이름은 [`verification-procedure.md`](verification-procedure.md) 5.8에 있다.

**「스킬 판본」 에는 이 리포트를 쓴 스킬의 판본을 적는다.** 값은 `scripts/rule_catalog.py`의 `SKILL_VERSION`이다. 차수마다 판본이 다르면 판정 대조에서 규칙이 바뀐 것과 설계가 바뀐 것을 가르는 데 쓴다.

**「자료 등급」 에는 입력 목록 파일의 '자료 등급' 칸 값을 그대로 옮긴다.** 값은 「구조 정보만」·「원천 값 포함」 가운데 하나이고, 칸이 없으면 「구조 정보만」 이다. 등급은 실행 설정이 정하며 스킬이 스스로 정하지 않는다. 「구조 정보만」 이면 이 리포트에는 테이블·컬럼 이름, 코드 저장값, CQ 문장만 인용하고 원천 데이터의 행 값은 옮기지 않는다. 이 등급의 리포트는 관문 검사가 개인정보 꼴을 찾는다.

**입력 해시는 스크립트가 낸 값을 옮긴다.** 파일 바이트의 SHA-256 앞 12자이고, 모델이 따로 계산하지 않는다. 같은 값을 CQ 증분 반영 관문의 해시 다시 셈과 판정 뒤 CQ 변경 해시 비교가 함께 쓴다.

### 문서 정보 표의 리포트 판

**리포트 판은 둘이다.** 「설계 단계」 판은 정의 문서를 쓰기 전 ⑥ 에서 사용자에게 보이는 판이고, 「검증 뒤」 판은 ⑨ 걸음 4 끝에 남은 절을 채운 판이다. 단계가 끝날 때마다 그 단계가 채우는 절을 바로 파일에 적는다. 정의 문서를 다 쓴 뒤에 리포트를 처음 쓰면 근거를 뒤늦게 적게 되기 때문이다. 절마다 두 판에 무엇을 적는지는 아래 표에 있다.

**「정의 문서 작성 뒤 기재」 는 설계 단계 판에서만 쓰는 닫힌 값이다.** 절 전체가 비면 표 대신 이 한 줄을 두고, 칸 하나만 비면 그 칸에 적는다. 「해당 없음」 은 확인했는데 없다는 뜻이라 섞지 않는다. 빈 칸을 채우라는 표시를 산출물에 남기지 않는다는 규칙([`report-conventions.md`](report-conventions.md))의 예외다. 검증 뒤 판에 이 값이 남아 있으면 판정 앞 관문 검사가 멈춘다.

**검증 뒤 판으로 바꿀 때는 설계 판단을 새로 하지 않는다.** ⑦·⑧·⑨에서 설계가 바뀌는 수정은 이 리포트를 먼저 고친 뒤 정의 문서에 옮긴다. ⑨는 걸음 3에서 설계가 바뀌는 지적을 모아 이 리포트를 한 번에 고친다. 그래서 ⑨ 걸음 4 끝에는 두 문서가 같은지 확인하고 2절 건수만 정의 문서 규모 표(`--stats`)로 센다. 서식·설명 Error(DOC-01~03·05~07·11, CNV-01·SPC-01의 서식 갈래)는 정의 문서를 바로 고친다. DOC-04(대표 표시 속성 오류)는 5.1절 대표 표시 속성 칸을 먼저 고친 뒤 정의 문서에 옮긴다. 두 문서가 같은지는 `scripts/check_design_report.py --stage 검증뒤`가 개념·속성·관계 이름을 맞대 확인한다.

**2절 칸은 차수 갈래에 따라 다르게 채운다.** 1차는 「외부 수정」·「스킬 수정」 칸이 「해당 없음」 이고, `※ CQ 변경 n:` 줄은 ⑥ 에서 CQ 증분 반영을 했을 때만 둔다. 설계 수정 차수는 「설계안 확인」 칸에 다시 연 ⑥ 의 답을, 「스킬 수정」 칸에 그 차수의 정비 건수를 적는다. 정비만 하는 차수와 검증만 모드(`--verify`)는 「설계안 확인」 칸을 앞 차수 그대로 두고, 「외부 수정」 칸에는 정비 차이만 적는다.

### 2절의 「설계안 확인」

설계 단계 판을 보이기 전에는 「확인 대기」로 둔다. 스킬 ⑥단계에서 설계안을 보여 주고 받은 답을 「설계안 확인」 칸에 적는다. 멈춤 안에서 다시 보인 횟수와 답 갈래를 함께 적는다(「2026-10-07, 확인(2회. 대화 수정 1회)」). CQ 문서만 바뀌어 이 리포트만 고쳐 다시 보였으면 「확인(2회. CQ 증분 반영 1회)」 처럼 적는다. 입력 문서를 받았으나 증분 반영 조건에 걸려 ① 부터 다시 했으면 「입력 문서 추가 1회(CQ 증분 반영 안 함: 부합 조건 n)」 처럼 걸린 조건 번호를 적는다. **확인받은 뒤 설계를 바꿨으면 「설계안 확인 후 변경」 칸에 건수를 적고, 무엇을 왜 바꿨는지는 표 아래에 변경마다 `※ 변경 n:` 한 줄로 적는다.** 칸에 여러 건을 문장으로 이어 쓰면 요약표가 읽히지 않는다. 서식 제약이나 검사 때문에 바뀌는 일이 흔하다. 적지 않으면 읽는 사람은 확인받은 설계와 나온 설계가 같은 줄 안다. 바꾼 것이 없으면 「해당 없음」이라 적는다. 답을 기다리지 않고 ⑦ 로 가는 길은 사전 지시뿐이다. 사전 지시로 넘어갔으면 「설계안 확인」 칸에 「미확인 진행(사전 지시: 출처)」 로 적는다. 출처는 호출 글·멈춤 답·입력 목록 파일의 `run_directives` 칸 가운데 하나다. 답이 없으면 「확인 대기」 로 둔 채 기다린다. 물을 수 없는 실행과 일부 항목만 답한 경우도 같다. 받지 않은 답을 받은 것처럼 적지 않는다. 관문 검사가 이 칸과 12절 「정한 쪽」 의 답이 온 길을 맞댄다.

### 2절의 「외부 수정」

**앞 차수 뒤에 사람이 정의 문서를 고쳤으면 「외부 수정」 칸에 건수를 적고, 한 건마다 표 아래 `※ 외부 수정 n:` 한 줄을 둔다.** 검증만 모드가 설계 리포트를 다시 맞출 때만 채운다. 설계 전체를 수행한 1차는 「해당 없음」 이다.

**`※ 변경 n:` 과 섞지 않는다.** `※ 변경 n:` 은 설계안 확인 뒤 스킬이 바꾼 것이고, `※ 외부 수정 n:` 은 스킬 밖에서 사람이 바꾼 것이다. 둘을 한 주석에 두면 스킬의 판단과 사람의 판단이 가려지지 않는다. 검증만 모드는 「설계안 확인」 칸과 `※ 변경 n:` 주석을 앞 차수 그대로 둔다. 수정 단계가 고친 것은 아래 「스킬 수정」 에 따로 적는다.

- 한 줄에 바뀐 요소 하나를 적는다. 더함·뺌·이름 바뀜·컬럼 바뀜 가운데 무엇인지와 요소를 적는다(「※ 외부 수정 1: 개념 '교육이수' 더함」, 「※ 외부 수정 2: 관계 '사원의 부서'(사원 → 부서) 뺌」)
- 매핑은 속성마다 적는다. 매핑 › 속성의 더함·뺌은 끝에 어느 컬럼인지 붙인다. 꼴은 `※ 외부 수정 n: 매핑 '<개념> ← <데이터 구조>' › 속성 '<속성>' 더함(컬럼 '<컬럼>')`이고 뺌도 같은 꼴 `… 뺌(컬럼 '<컬럼>')`이다. 뺌의 컬럼은 앞 차수에 이어져 있던 컬럼이다(「※ 외부 수정 3: 매핑 '휴가신청 ← hr.TB_휴가신청내역' › 속성 '휴가 종류' 더함(컬럼 '휴가구분')」). 같은 속성의 매핑 컬럼만 바뀐 것은 '컬럼 바뀜'이다(「※ 외부 수정 4: 매핑 '휴가신청 ← hr.TB_휴가신청내역' › 속성 '신청자 이름' 컬럼 바뀜(앞 컬럼 '신청자명', 이번 컬럼 '신청자번호')」). 앞 차수 정의 문서의 매핑 행과 맞대 찾는다([`verification-procedure.md`](verification-procedure.md) 5.6 차례 3). 수정 단계는 이 줄로 사람이 이은 매핑을 알아본다
- 이름이 바뀐 요소는 스킬이 짐작해 짝짓지 않는다. 같은 이름이 없으면 뺌 한 건과 더함 한 건으로 적는다
- 사람이 더하거나 이름을 바꾼 요소를 수정 단계가 이어 고쳤으면 외부 수정으로 두고 같은 줄에 스킬이 고친 것도 적는다(「※ 외부 수정 3: 개념 '휴가사용' 더함. 스킬이 이어 설명의 조사 괄호를 받침에 맞게 고침(DOC-02, 1차 판정 Error-4)」)
- 요소 밖의 변화는 번호 없이 `※ 외부 수정 경고:` 한 줄씩 적고 건수에 넣지 않는다. 개념이 앞 차수보다 절반 넘게 바뀜, 앞 차수 정의 문서를 그 자리에서 고쳐 앞 차수 리포트와 맞지 않음이 그렇다. 경고 줄은 `※ 외부 수정 n:` 줄 뒤에 둔다. CQ 문서가 바뀐 것은 경고가 아니라 `※ CQ 변경 n:` 줄로 적는다
- 「외부 수정」 칸의 n건은 `※ 외부 수정 n:` 줄 수와 같다
- 사람이 고친 까닭은 적지 않는다. 스킬은 그 까닭을 모르고, 짐작해 적으면 지어낸 근거가 된다

**뒤 절의 근거 칸에는 닫힌 값 둘만 쓴다.** 사람이 더한 요소는 스킬이 판단한 것이 아니라 근거를 적을 수 없다.

| 값 | 쓰는 칸 |
|---|---|
| `외부 수정(근거 미기재)` | 5.1절 개념 설정 근거, 5.2절 명명 근거. 사람이 더하거나 이름을 바꾼 요소 |
| `외부 수정(근거 CQ 없음)` | 5.1절·6절·7절 근거 CQ. 사람이 더했는데 4절에서 그 요소를 쓰는 CQ가 없는 요소 |

- 근거 CQ는 사람이 더한 요소라도 4절 응답 경로로 계산할 수 있으면 채운다. 계산한 값이라 지어낸 것이 아니다
- 6절 연결 근거와 5.3절 추가 사유도 채운다. 잇는 값이 원천에 있는지, 어느 관계의 조인 속성인지는 사실이라 지어낸 것이 아니다
- 다시 맞추는 절과 처리는 [`verification-procedure.md`](verification-procedure.md) 5.7에 있다

### 2절의 「스킬 수정」

**수정 단계(`--fix`)가 판정을 보고 정의 문서를 고쳤으면 「스킬 수정」 칸에 건수를 적고, 한 건마다 표 아래 `※ 스킬 수정 n:` 한 줄을 둔다.** 정의 문서 끝 기록 절에 이번 차수 줄이 있을 때 채운다. 수정 단계에 이어 수행했든, 검증이 멈춘 뒤 `--verify`로 다시 불렀든 같다. 이번 차수 줄이 없으면 「해당 없음」 이다.

**「설계안 확인 후 변경」 은 1차 설계 중 ⑥ 확인 뒤 스킬이 바꾼 것이고, 「스킬 수정」 은 판정을 보고 수정 단계가 고친 것이다.** 둘을 한 칸에 두면 확인받은 설계를 스킬이 설계 중에 바꿨는지 판정 뒤에 고쳤는지 가려지지 않는다.

- 목록은 정의 문서 끝 `## 스킬 수정 기록` 절에서 이번 차수 표시가 붙은 줄을 가져온다([`fix-procedure.md`](fix-procedure.md) 6장). 기록 줄 하나가 `※ 스킬 수정 n:` 한 줄이다
- 줄에는 요소, 고친 내용, 규칙과 판정 지적 번호를 적는다(「※ 스킬 수정 1: 개념 '휴가신청' 설명의 조사 괄호를 받침에 맞게 고침(DOC-02, 1차 판정 Error-1)」, 「※ 스킬 수정 2: 관계 '교육이수의 사원'(교육이수 → 사원) 사용자 답에 따라 더함(CQS-01, 1차 판정 Error-3)」). 결정 필요를 사용자 답대로 고친 줄은 기록 줄처럼 '사용자 답에 따라'를 남긴다
- 줄은 기록 줄의 요소를 글자 그대로 앞에 두고, 끝 괄호에 규칙과 앞 차수 판정의 지적 번호를 '(DOC-02, 1차 판정 Error-1)'처럼 적는다. 외부 수정 줄로 옮긴 기록도 '스킬이 이어' 뒤에 같은 괄호를 적는다
- 사람이 더하거나 이름을 바꾼 요소를 이어 고친 기록 줄은 여기 적지 않고 `※ 외부 수정 n:` 줄에 함께 적는다
- 「스킬 수정」 칸의 n건은 `※ 스킬 수정 n:` 줄 수와 같다. 줄은 `※ 외부 수정` 줄 뒤에 둔다
- 수정 단계가 고친 요소는 근거를 스킬이 안다. 뒤 절의 근거 칸을 일반 설계 규칙대로 채우고 「외부 수정」 표기를 쓰지 않는다

### 2절의 「CQ 변경」

**CQ 문서가 앞 차수와 달라졌으면 바뀐 것 하나마다 표 아래 `※ CQ 변경 n:` 한 줄을 둔다.** 2절 표에 칸은 두지 않는다. 검증만 모드가 CQ 문서 해시로 바뀐 것을 알아챈다([`verification-procedure.md`](verification-procedure.md) 5.4).

- 한 줄에 바뀐 것 하나를 적는다. CQ 더함·뺌·문장 바뀜·등급 바뀜 가운데 무엇인지와 CQ 번호·짧은 내용을 적는다. 필수 CQ 기준이 바뀌었으면 그것도 한 줄로 적는다(「※ CQ 변경 1: CQ-55 더함(부서별 교육 이수 인원)」, 「※ CQ 변경 2: CQ-61 등급 바뀜(중 → 상)」)
- 뺀 CQ의 줄에는 그 CQ에 걸린 앞 판정 지적을 함께 적는다. 판정 대조는 이 지적을 해소로 세는데, 구조를 고쳐 풀린 것이 아니라 CQ가 빠진 것이다(「※ CQ 변경 3: CQ-51 뺌(휴가 사용 일수). 1차 판정 Error-2(CQS-01)는 이번 대조에서 해소로 셈해짐」)
- 줄은 `※ 스킬 수정` 줄 뒤에 둔다
- 뺀 CQ만 근거 CQ였던 요소는 행을 지우지 않고 5.1절·6절·7절 근거 CQ 칸에 닫힌 값 `CQ 변경(근거 CQ 없음)` 을 적는다. 사람이 더한 요소의 `외부 수정(근거 CQ 없음)` 과 가르기 위함이다
- 다시 맞추는 절은 [`verification-procedure.md`](verification-procedure.md) 5.7 'CQ가 바뀐 차수' 행에 있다

**⑥ 에서 CQ 증분 반영을 할 때는 아래 자리만 다시 맞춘다.** 설계 판단을 새로 하는 자리는 바뀐 CQ의 행뿐이다.

| 절 | 다시 맞출 자리 |
|---|---|
| 문서 정보 표 | 입력 해시와 CQ 건수 |
| 2절 | 건수와 `※ CQ 변경 n:` 줄 |
| 3절 | CQ 문서 행의 건수 |
| 4.1·4.3 | 더한 CQ의 행을 더하고, 뺀 CQ의 행을 지우고, 문장이나 등급이 바뀐 CQ의 행을 고친다. 4.1에는 경로 사실만 적는다 |
| 4.2 | 사용 CQ 칸 |
| 5.1·6·7.1·7.2 | 근거 CQ 칸 |
| 5.3 | 4.1절 사용 속성 칸과 가르는 기준으로 다시 본 조인 속성 행 |
| 9.1 | CQ 제외 행 |
| 9.2 | 적용 조건 칸이 가리키는 CQ |
| 11 | 기존 행의 CQ 번호만 |

**뺀 CQ만 근거 CQ였던 요소는 ⑥ 위층에 한 건씩 올리고 기본값은 「지움」 이다.** 남기려면 사람이 대화 수정으로 정한다.

### 2절의 건수

**2절의 건수는 뒤 절의 줄 수와 맞춘다.** 개념은 5.1, 관계는 6, 원천 대조는 4.2, 매핑 테이블 제안은 7.1, 문서 타입은 7.2, 확인 필요 사항은 8, 제외 항목은 9.1·9.2, 불일치는 11절의 줄 수, 사람 확인 없음은 12절에서 정한 쪽이 '기본값(사람 확인 없음)'인 줄 수다. 개념·관계 수는 정의 문서 규모 표(`--stats`)와도 같아야 한다. 설계 단계 판은 그때 있는 절의 줄 수로 적고, 검증 뒤 판에서 정의 문서 규모 표와 다시 맞춘다. **구조 꼴 적용은 4.3절 줄 수와 맞춘다.** 2절 「구조 꼴 적용」 행은 「CQ 조각 n건 중 꼴 적용 n건, 대상 하나의 값 n건, 맞는 꼴 없음 n건, 꼴 요소를 뺀 조각 n건」 꼴로 적는다.

### 3. 입력 문서 역할 판정 — 무엇을 보고 갈랐는지 적는다

① 이 가린 결과는 ① 출력 앞에 이 절의 초안으로 파일에 적고, 답을 받은 뒤 확정한다. **그런데 이 판정이 틀리면 뒤의 여덟 단계가 전부 어긋난다.** 읽는 사람이 「이 문서를 용어 자료로 본 것이 맞나」를 되짚으려면 무엇을 보고 그렇게 갈랐는지가 남아 있어야 한다. 역할만 적힌 표는 결과일 뿐이라 되짚을 거리가 없다.

**근거는 `reading-input-documents.md` 1장 역할별 단서 가운데 어느 것으로 갈랐는지와, 그 문서에서 실제로 본 것을 함께 적는다.** 단서 이름만 적으면 규칙 이름을 옮긴 것이고, 본 것만 적으면 어느 규칙으로 갈랐는지 알 수 없다. **단서는 역할별 단서 표의 역할 이름으로 적는다.** `reading-input-documents.md` 의 장 번호로 적으면 받는 사람이 펼 수 없는 번호가 된다.

| 잘못된 예 | 올바른 예 |
|---|---|
| 용어 사전이라서 | 업무 용어와 뜻, 같은 대상의 다른 이름 목록 수록(용어 자료 단서) |
| 스키마 문서 | 테이블·컬럼 목록과 테이블 간 연결 컬럼 기재(정형 원천 단서) |
| 업무 문서로 보임 | 업무 목적과 제외 범위 기재(업무 범위 단서) |

**CQ는 판정 근거 칸에 「사용자 지정」, 두 가이드는 「스킬 기본」 이나 「`--style` 지정」·「`--format` 지정」 이라고 적는다.** 가린 것이 아니라 받은 것이라, 같은 칸에 같은 무게로 적으면 무엇을 스킬이 판단했는지 가려지지 않는다. 가이드가 기본인지 받은 것인지 적지 않으면, 같은 입력으로 결과가 달라졌을 때 가이드가 달라서인지 가려낼 수 없다.

**비고 칸에는 판정 밖의 덧붙임만 적는다.** xlsx·docx·PDF를 텍스트나 Markdown 변환본으로 받았으면 「변환본(원본 xlsx)」 처럼 원본 형식을 적는다(`reading-input-documents.md` 받는 형식 절). 적을 것이 없으면 「-」 로 둔다. 판정 근거를 비고로 옮기지 않는다. 근거와 덧붙임을 한 칸에 섞으면 무엇으로 갈랐는지 되짚을 때 덧붙임을 걷어 내야 한다.

**입력 문서 기재 사항 표**에는 입력 문서가 스스로 밝힌 확정 가정·결정 사항과, 받지 않은 역할 때문에 비는 항목을 적는다. 셋은 어느 역할의 문서에서 나오든 설계에 걸리므로 역할 판정 표 옆에 둔다.

| 칸 | 기재 내용 |
|---|---|
| 구분 | `확정 가정` · `결정 사항` · `미제공 역할` 셋 중 하나 |
| 내용 | 확정 가정은 원문 그대로 옮긴다. 결정 사항은 고른 안을, 미제공 역할은 받지 않은 역할과 그 때문에 비는 항목(별칭·경고문·데이터 구조 등)을 적는다 |
| 출처 | 문서와 번호(「CQ 문서 가정 A-3」 처럼) |
| 반영 | 설계에 반영한 곳(「5.1절 No.2」 처럼) 또는 「리포트 기재만」. 미제공 역할이면 그 문서가 생겼을 때 채울 곳 |

세 경우는 빠뜨리기 쉬우니 따로 적는다.

| 상황 | 기재 내용 |
|---|---|
| 한 문서가 두 역할을 겸한다 | 역할 칸에 두 역할을 함께 적고, 근거도 역할마다 적는다 |
| 역할을 가리지 못했다 | 역할 칸에 「판정 불가」, 근거 칸에 무엇이 모자랐는지 적는다. **빈 칸으로 두지 않는다** |
| 사용자가 ① 에서 바로잡아 줬다 | 근거 칸에 「사용자 정정(무엇을 무엇으로)」 을 적는다. 스킬이 가린 것과 사용자가 정한 것은 믿을 수 있는 정도가 다르다 |

### 4.1 CQ-구조 연결표 — 설계 내내 기준이 되는 표

**CQ 하나가 한 줄이다.** 구조에서 시작하지 않고 CQ에서 시작하는 것이 중요하다. 개념·속성·관계는 모두 이 표에 있는 값에서 나오고, 여기 없는 것은 만들지 않는다.

② 가 모은 값 표가 이 표가 된다. **②의 값 표는 ② 끝에 이 절의 CQ·사용 값 칸으로 파일에 적고, ④·⑤가 나머지 칸을 채운다.** ⑥ 의 설계안과 ⑦ 의 매핑, 그리고 검증 리포트 6절이 모두 이 표를 원본으로 삼는다.

| 칸 | 기재 내용 |
|---|---|
| CQ | CQ 번호와 **짧은 내용**. 번호만 적으면 리포트의 다른 절에서 「CQ-51」 을 만난 사람이 무슨 CQ인지 찾을 곳이 없다. CQ 문서가 여럿이면 출처와 함께 적어야 가려진다. CQ에 번호가 없어 스킬이 매겼으면 그 번호(`Q1` …)를 쓴다 |
| 해시/등급 | CQ 문장의 해시(SHA-256 앞 12자)와 CQ 문서가 매긴 등급을 「a1b2c3d4e5f6/상」 처럼 빗금으로 이어 적는다. 등급이 없으면 빗금 뒤를 「-」 로 둔다. **이 칸은 관문 검사가 채운다.** 모델은 「(관문이 채움)」 만 적는다 |
| 사용 값 | ② 가 그 CQ에서 뽑은 값. 조건으로 쓰는 값과 답으로 내보내는 값을 가리지 않는다 |
| 사용 속성 | 그 값을 담은 `개념 · 속성`. 검증 리포트 6절이 이 칸을 원본으로 삼는다 |
| 응답 경로 | 조건에서 답까지 어느 개념을 어느 관계로 거쳐 가는지 |
| 홉 수 | 경로가 거치는 관계의 수. 한 개념 안에서 끝나면 `0홉` |

**해시/등급 칸은 스크립트가 쓰고, 나머지 칸은 모델이 쓴다.** 모델은 해시/등급 칸에 「(관문이 채움)」 만 적고 해시나 등급을 옮겨 적지 않는다. ⑥ 출력 앞 관문 검사(`scripts/check_design_report.py`)가 CQ 문서를 직접 읽어 그 칸을 채우고, 판정 앞과 판정 때 다시 셈해 이 칸과 다르면 종료 코드 1로 멈춘다.

**경로가 「응답 가능」 의 근거다.** 쓰는 개념과 속성만 적으면 재료 목록일 뿐이라, 그 재료로 정말 답이 나오는지 읽는 사람이 되짚을 수 없다. 경로를 적으면 어디서 끊기는지가 표에서 바로 보인다.

경로는 이렇게 적는다. 화살표 뒤 괄호에 거치는 관계 이름을 적는다. 관계 방향과 반대로 거쳐 가면 `←` 를 쓴다.

| 응답 경로 | 홉 수 |
|---|---|
| `휴가신청 · 휴가 종류` | 0홉 |
| `휴가신청 →(휴가신청의 사원) 사원 →(사원의 부서) 부서 · 부서명` | 2홉 |
| `부서 · 부서명 ←(사원의 부서) 사원 · 사원명` | 1홉 |

**CQ가 홉 수 조건을 정했으면 그 조건을 넘는 줄이 보이게 적는다.** 중간 개념을 하나 더 둘 때마다 경로가 길어지므로, ⑤ 에서 마디를 더할 때 이 칸을 함께 본다.

**응답 가능 여부는 여기서 판정하지 않는다.** `응답 가능`·`부분 응답`·`응답 불가` 는 ⑨ 가 검증 리포트 5절에 적는다. 이 절은 「경로가 이렇다」 까지 적고, 「그래서 답이 되는가」 는 검사한 뒤에 말한다. 설계하면서 스스로 매긴 점수와 검사로 나온 값을 한 문서에 두면 읽는 사람이 둘을 가려내지 못한다.

**경로가 비는 CQ는 빈 칸으로 두지 않는다.** 「경로 없음(사유: 부족 항목)」 이라고 적는다. 사유는 설계 누락·원천 선택 미채택·원천 확인 필요·원천 부재·규격 제약 가운데 하나다. 빈 칸은 적지 않은 것인지 경로가 없는 것인지 가려지지 않고, ⑥ 에서 사용자에게 보여 줄 것이 바로 이 줄이다.

**사용 값 칸을 비우지 않는다.** 검증 리포트 6절이 값마다 매핑한 컬럼을 맞대 보는데, 맞댈 원본이 이 칸이다. 비어 있으면 그 CQ는 검사에서 통째로 빠진다.

**사용 속성 칸에는 CQ가 쓰는 값을 담은 속성만 적는다.** 관계를 잇는 데만 쓰는 조인 속성은 응답 경로의 관계 이름으로 드러나므로 여기 적지 않고 5.3절에 둔다. 조인 속성이 곧 CQ가 묻는 값이면 여기에도 적는다.

**CQ 문서가 질문자나 질문 목적을 적은 칸을 두었으면 표 아래 ※ 주석으로 옮긴다** — 「※ CQ 문서 '누가' 칸: (CQ 번호별 질문자)」 처럼. 표에 칸을 더하지 않는다.

### 4.2 원천 대조표 — 답 요소마다 근거를 적는다

**답 요소 하나가 한 줄이다.** 같은 요소를 여러 CQ가 쓰면 한 줄에 모은다. 원천에만 있는 테이블 수는 표 위 한 줄로 적고 9.1절을 가리킨다.

| 칸 | 기재 내용 |
|---|---|
| No. | 1부터. 12절 결정 기록과 검증 리포트 5.2절이 이 번호로 가리킨다 |
| 답 요소 | 값 이름과 짧은 뜻 |
| 요소 종류 | 대상·값·잇는 값 |
| 사용 CQ | 그 요소를 쓰는 CQ 번호 모두 |
| 판정 | 있음·형태 다름·경유·없음·확인 필요 가운데 하나 |
| 근거 위치 | 있음이면 테이블.컬럼·연결 키·문서 항목과 원천 문서 절. 없음이면 없다고 본 근거(그 절의 문장, 또는 '컬럼 목록 전수에 없음'). 확인 필요면 무엇을 확인할지 |
| 처리 | 만듦·빼고 보고·빼고 보고(후보 미채택)·조인·매핑 테이블·연쇄 제외·규격 제약 가운데 하나. 「빼고 보고(후보 미채택)」 은 매핑 테이블 후보를 보였으나 채택하지 않아 뺀 요소다. 조인이면 연결 키, 매핑 테이블이면 MT-nn |
| 결정 No. | 12절 행 번호. 판정이 있음이면 「해당 없음」 |

**사람이 원천 위치를 짚어 판정을 다시 하면 판정 칸에 옛 판정과 새 판정을 함께 적는다** — 「있음(판정 정정: 확인 필요 → 있음)」 처럼. 근거 위치 칸에는 사람이 짚은 원천 위치를 적고, 12절에 고른 값이 「판정 정정」, 정한 쪽이 「사람」 인 행을 둔다. 결정 No. 칸에는 판정이 있음이어도 그 12절 행 번호를 적는다. 스킬이 처음 낸 판정과 사람이 바로잡은 판정은 믿을 수 있는 정도가 다르다. 판정 칸의 값은 괄호 앞 낱말로 가른다.

### 4.3 구조 꼴 적용표 — CQ 조각마다 고른 꼴을 적는다

**CQ 하나가 한 줄이다.** CQ 하나를 나눠 서로 다른 꼴로 답하면 조각마다 한 줄이고 조각 낱말을 괄호에 적는다. 꼴 이름과 꼴 요소, CQ 꼴 표지는 [`structure-patterns.md`](structure-patterns.md) 에 있다. 꼴 이름은 그 문서의 한국어 이름으로 적고 원래 이름은 적지 않는다.

| 칸 | 기재 내용 |
|---|---|
| No. | 1부터. 12절 결정 기록이 대안 꼴을 고른 행을 이 번호로 가리킨다 |
| CQ | CQ 번호와 짧은 내용. 나눴으면 조각 낱말을 괄호에 적는다 |
| CQ 꼴 표지 | 닫힌 목록 값(CQ 꼴·「대상 하나의 값」·「맞는 꼴 없음」)과 근거 낱말(질문 문장이나 답 요소의 원문 낱말) |
| 고른 꼴 | 꼴 이름. 표지가 「대상 하나의 값」 이면 「해당 없음(속성)」, 「맞는 꼴 없음」 이면 「맞는 꼴 없음」 |
| 맞춤 경우 | 같음·요소가 남음·넓음·좁음·일부 가운데 하나. 나눈 CQ는 「일부」 |
| 채운 꼴 요소 | 요소 이름과 근거 데이터 구조 |
| 뺀 꼴 요소 | 요소 이름, 4.2절 No., 미응답 사유. 없으면 「해당 없음」 |
| 내려간 꼴 | 꼴 요소가 비어 내려간 꼴. 없으면 「해당 없음」 |
| 대안 꼴 | ⑥ 에 함께 보인 꼴. 없으면 「해당 없음」 |
| 결정 No. | 12절 행 번호. 사람이 대안 꼴을 고르지 않았으면 「해당 없음」 |

**6절 `구조 꼴` 칸의 값은 이 표의 `고른 꼴` 에서 옮긴다.** 옮기는 법은 6절에 있다.

**뺀 꼴 요소가 있는 CQ는 응답 가능이 될 수 없다.** 뺀 꼴 요소가 가리키는 4.2절 행의 판정이 있음이면 설계 누락이다. 판정 스크립트가 두 가지를 맞댄다.

### 4.4 구조 꼴 선택 근거 — 꼴마다 고른 판단과 까닭을 적는다

**꼴마다, 또는 같은 판단으로 묶인 CQ 조각마다 글머리 묶음 하나를 둔다.** 묶음에는 아래 여섯 항목을 차례대로 적는다. 사람이 직접 설계하지 않은 구조라 판단과 까닭이 남아 있어야 사용자가 확인할 수 있다.

- 고른 꼴
- CQ 꼴 표지
- 4.2절 원천 판정
- 정한 단계(고르는 차례의 어느 단계에서 정했는지)
- 버린 대안과 까닭
- 줄인 꼴이면 뺀 요소

개조식으로 쓰고 종결은 「~함」·「~임」으로 한다. 표가 아닌 글로 적는다는 뜻이며 줄글 문단을 쓰지 않는다. 원래 이름은 적지 않는다.

### 5.1 개념 목록

`근거 CQ` 칸이 비면 안 된다. 비었다면 그 개념은 지운다. 검증만 모드는 예외다 — 사람이 더한 개념을 지우지 않고 근거 CQ를 「외부 수정(근거 CQ 없음)」 으로 둔다. CQ 문서에서 빠진 CQ만 근거 CQ였던 개념은 「CQ 변경(근거 CQ 없음)」 으로 둔다([`verification-procedure.md`](verification-procedure.md) 5.1).

CQ 본문이 아니라 **옆 칸이 요구해서 둔 개념**이면 번호 뒤에 그 사실을 괄호로 덧붙인다 — `CQ-번호(옆 칸 요구)` 처럼. 적지 않으면 다음 사람이 본문만 읽고 근거 없는 개념으로 보아 지운다.

`원천` 칸은 비우지 않는다. 이 개념의 데이터가 들어 있는 원천 테이블이나 원천 문서 종류와 4.2절 원천 대조표 No.를 적는다. 채택한 매핑 테이블이면 MT 번호를 적고 7.1절에, 문서 타입이면 7.2절에 올린다. 원천 칸을 채울 수 없으면 그 개념은 만들지 않는다.

**`개념 설정 근거` 칸에는 이것을 왜 하나의 개념으로 두었는지 적는다.** [`intermediate-concepts.md`](intermediate-concepts.md) 의 축 가운데 어느 것이 걸렸는지와, 그 문서에서 실제로 본 것을 함께 적는다 — 「'연결 자체에 값이 딸림' 해당. 딸린 값 `휴가일수`·`승인일자`」 처럼 적는다. 조건 이름만 적으면 규칙 이름을 옮긴 것이고, 본 것만 적으면 어느 조건으로 갈랐는지 알 수 없다.

이 칸은 9.2절과 짝이다. 9.2절은 **두지 않은** 중간 개념에 어느 조건이 미충족인지를 적는데, **둔** 개념에 같은 칸이 없으면 한쪽만 되짚을 수 있다.

**속성에서 갈라져 나온 개념이 아니면 「CQ 직접 요구」 라고 적는다.** CQ가 그 집합을 직접 물어서 만든 개념은 가를 판단이 없었다는 뜻이고, 그것도 근거다. 빈 칸으로 두면 판단을 적지 않은 것과 구분되지 않는다.

**대표 표시 속성 칸은 ⑦·⑧ 에서 채운다.** 설계 단계 판에는 이 칸에 「정의 문서 작성 뒤 기재」 를 적는다. 대표 표시 속성을 고르거나 바꾸면 이 칸을 먼저 고친 뒤 정의 문서에 옮긴다. 판정 뒤 정비(DOC-04 대표 표시 속성 오류)로 바꿀 때도 같은 차례이고 ⑥ 은 다시 열지 않는다.

### 5.2 명명 근거

**개념마다 한 줄씩 적는다.** 입력 문서에 있던 말과, 그 가운데 **어느 문서의 어느 말을 골랐는지, 앞선 말을 왜 건너뛰었는지** 적는다. 고르는 차례는 [`choosing-concept-names.md`](choosing-concept-names.md) 에 있지만, 리포트에는 그 차례의 번호나 이름이 아니라 **무엇을 보고 골랐는지를 말로** 적는다. 리포트를 받는 사람은 그 문서를 볼 수 없다.

같은 입력으로 다시 수행했을 때 이름이 달라지면 정의 문서를 받는 쪽은 다른 온톨로지로 읽는다. 무엇을 보고 그 이름을 지었는지 남아 있어야 다음 사람이 같은 판단을 되풀이할 수 있고, 바꿔야 할 때 무엇이 흔들리는지 안다.

| 잘못된 예 | 올바른 예 |
|---|---|
| 휴가신청이 자연스러워서 | 용어 사전 표제어 '휴가신청' 선택. CQ도 같은 표현 사용 |
| 가이드대로 · 차례 2 를 건너뛰고 차례 3 | 표제어 '사원번호'는 번호를 가리키므로 속성으로 두고, 개념은 CQ 표현 '사원' 사용 |
| 적당한 이름이 없어서 | 입력 문서가 이 대상을 코드와 이름으로만 지칭함. 표제어 '근무지코드'에서 '코드'를 떼어 '근무지'로 명명 |

**설계안 확인 뒤에 이름을 바꿨으면 그 사실도 이 표에 적는다.** 2절 ※ 변경 주석에는 무엇을 바꿨는지 적고, 바꾼 뒤의 명명 근거는 여기에 남긴다.

### 5.3 CQ 외 추가 속성

**CQ가 요구하지 않은 속성은 원칙적으로 만들지 않는다.** 그런데 규격이 요구해서 두어야 하는 곳이 있다. 관계의 조인 속성과 식별 속성이 그것이다.

이런 속성은 5.1절의 `근거 CQ` 로는 설명되지 않아서, 적어 두지 않으면 다음 사람이 근거 없는 속성으로 보아 지운다. 지우면 관계가 만들어지지 않는다.

| 칸 | 기재 내용 |
|---|---|
| 추가 사유 | 「관계 `휴가신청의 사원`의 조인 속성」 처럼, 이 속성이 없으면 무엇이 안 되는지 적는다 |
| 요구 근거 | 규격 · 서식 가이드 · 스타일 가이드 가운데 어느 것인지와 그 대목 |

**CQ도 규격도 요구하지 않은 속성이 남아 있으면 지운다.** 이 표는 예외를 적는 곳이지 만든 것을 모두 정당화하는 곳이 아니다. 검증만 모드는 사람이 더한 속성을 지우지 않는다. 검증 리포트의 CQS-05가 잡는다.

### 6. 관계 설계

`연결 근거` 칸에 **두 개념을 잇는 값이 실제로 있다는 근거**를 적는다. 원천 문서의 어느 대목인지 짚는다. 이 칸은 비울 수 없고 연결 키·잇는 테이블·채택한 매핑 테이블(MT-nn) 가운데 하나를 가리켜야 한다. 새 칸 `구조 꼴` 에는 그 관계가 [`structure-patterns.md`](structure-patterns.md) 의 어느 꼴(참여·역할·구성·절차·소속·대응·문서 등)인지 꼴 이름으로 적는다. `구조 꼴` 칸 값은 4.3절 `고른 꼴` 에서 옮긴다. 관계 하나가 여러 꼴에 쓰이면 꼴 이름을 ' · ' 로 잇는다. 4.3절에 없는 꼴 이름이 이 칸에 있으면 두 절이 어긋난 것이고 관문 검사가 짚는다.

**CQ가 요구해도 잇는 값이 없거나 있는지 모르면 관계를 만들지 않는다.** 잇는 값 없이 만든 관계는 반입 뒤 언제나 비어 있어 잘 된 것처럼 보이면서 동작하지 않는다. 만들지 않은 경로는 4.2절 원천 대조표와 검증 리포트 5.2절에 남는다.

CQ가 요구하지도 않는데 만든 관계는 다르다. 그것은 지운다. 검증만 모드는 사람이 더한 관계를 지우지 않는다. 근거 CQ를 「외부 수정(근거 CQ 없음)」 으로 두고 검증 리포트의 CQS-05가 잡는다. CQ 문서에서 빠진 CQ만 근거 CQ였던 관계는 「CQ 변경(근거 CQ 없음)」 으로 둔다.

### 7. 매핑 테이블 제안과 문서 타입

**대상 환경에 아직 없어 먼저 만들어야 하는 구조는 둘뿐이다** — 사람이 채택한 매핑 테이블과 원천 문서를 근거로 선언한 문서 타입. 둘 다 데이터는 이미 원천에 있다. 새 데이터가 있어야 채워지는 테이블·컬럼은 이 절에 적지 않는다. 판별 기준은 [`source-match.md`](source-match.md) 4장에 있다. 여기서 말하는 메타타입은 정의 문서의 「데이터 구조」와 같은 것이다.

#### 7.1 매핑 테이블 제안

**매핑 테이블 후보 하나가 한 줄이다.** 원천 대조 판정이 형태 다름이나 없음인 요소라도 기존 데이터만으로 이을 수 있으면 후보로 올린다. 채택하지 않은 후보도 행을 남긴다. 무엇을 채택하면 어느 CQ가 살아나는지 이 표에서 보여야 하기 때문이다.

| 칸 | 기재 내용 |
|---|---|
| No. | MT-01부터. 4.2절 처리 칸과 5.1절 원천 칸이 이 번호로 가리킨다 |
| 이름 | 매핑 테이블 이름. 짓는 법은 아래 「이름은 개념에서 따온다」 문단 |
| 꼴 | 식별자 대응표·목록 펼침표·키 결합표·문서-식별자 대응표 가운데 하나 |
| 재료 | 기존 테이블.컬럼, 또는 원천 문서가 밝힌 저장 경로 규칙과 그 절 |
| 생성 방법 | 어느 원천의 무엇에서 어떻게 행을 만드는지 |
| 근거 CQ | 채택하면 답할 수 있게 되는 CQ 번호 |
| 쓰는 요소 | 이 테이블로 잇거나 채우는 개념·속성·관계 |
| 데이터 확인 사항 | 만들기 전에 원천 데이터에서 확인할 것 |
| 결정 | 「채택(사람)」·「빼고 보고(사람)」·「빼고 보고(기본값, 사람 확인 없음)」 가운데 하나. 12절 행과 같아야 한다 |
| 만드는 곳 | 매핑 테이블을 만들 시스템. 정해지지 않았으면 「지정 필요」 |
| 조치 주체 | 만드는 일을 맡을 쪽. 정해지지 않았으면 「고객 원천 담당」 |

칸(컬럼) 목록은 채택했으면 정의 문서의 데이터 구조 절에 적고, 채택하지 않았으면 표 아래 `※ MT-nn 칸:` 주석으로 적는다.

`생성 방법` 칸이 이 절의 값이다. 「필요함」만 적으면 아무도 만들지 않는다. **어느 원천의 무엇에서 어떻게 만드는지**를 적는다. 없음을 확인한 근거나 대체 후보를 쓰지 않은 까닭처럼 설명이 길어지면 칸에는 만드는 법만 두 문장 이내로 적고 나머지는 표 아래 `※ MT-nn` 주석으로 옮긴다.

| 잘못된 예 | 올바른 예 |
|---|---|
| 전처리 필요 | 거래처 테이블의 재고부품목록 칸을 부품 1건이 1행이 되도록 분할 |

**이름은 개념에서 따온다.** 그 데이터를 쓰는 개념의 이름을 그대로 쓰고, 컬럼 이름은 원천 관례를 따른다. 짓는 규칙은 [`filling-document-format.md`](filling-document-format.md) 2.1 에 있다. `꼴` 칸 값은 7.1 칸 표에 있다. 정의 문서와 **같은 이름**이어야 한다 — 대상 환경에는 이 이름으로 만들어져야 반입된다.

**뜻이 다른 컬럼으로 대신 답하지 않는다.** 원천에 그 뜻의 컬럼이 없거나 있는지 모르면 비슷한 컬럼을 끌어다 쓰지 말고 속성을 만들지 않는다. 대신 쓰지 않은 컬럼과 그 까닭은 검증 리포트 5.2절 '대조한 원천 위치'에 적는다.

`근거 CQ` 칸이 비면 그 줄은 지운다. 어느 CQ도 쓰지 않는 값을 만들어 달라고 하는 셈이기 때문이다. 검증만 모드는 사람이 더한 요소의 줄을 지우지 않고 근거 CQ를 「외부 수정(근거 CQ 없음)」 으로 둔다. CQ 문서에서 빠진 CQ만 근거 CQ였던 줄도 지우지 않고 「CQ 변경(근거 CQ 없음)」 으로 둔다.

**조치 주체 칸을 비우지 않는다.** 정해지지 않았으면 7.1절은 `고객 원천 담당`, 7.2절은 `지정 필요` 로 적는다.

#### 7.2 문서 타입

**원천 문서를 근거로 선언하는 문서 타입 하나가 한 줄이다.** 원천 문서 목록에 그 문서 종류가 적혀 있을 때만 선언한다. 새 컬럼을 제안하는 자리는 두지 않는다. 원천에 없는 값은 4.2절에 판정과 함께 남는다.

| 칸 | 기재 내용 |
|---|---|
| No. | 1부터 |
| 이름 | 문서 타입 이름. 7.1절과 같은 규칙으로 짓는다 |
| 원천 문서 종류 | 원천 문서 목록에서 그 종류를 적은 문서와 절 |
| 사용자 정의 프로퍼티 | 문서에서 뽑아 프로퍼티로 둘 항목 |
| 근거 CQ | 이 문서 타입을 쓰는 CQ 번호 |
| 조치 주체 | 문서 타입을 만들 쪽. 정해지지 않았으면 「지정 필요」 |

**이 절은 정의 문서를 쓰는 ⑦ 에서 채운다.** 설계 단계 판에는 「정의 문서 작성 뒤 기재」 한 줄을 둔다. 문서 타입을 고르거나 바꾸면 이 절을 먼저 고친 뒤 정의 문서에 옮긴다. 판정 뒤 정비(스타일 가이드 문서 타입 프로퍼티 항목 C-16~C-18)로 바꿀 때도 같은 차례이고 ⑥ 은 다시 열지 않는다.

| 잘못된 예 | 올바른 예 |
|---|---|
| 문서 타입 필요 | 정비 문서의 공정 부분을 `정비공정` 문서 타입으로 선언 |

### 8. 확인 필요 사항

`확인 필요` 로 남긴 항목을 모두 모은다. 정의 문서 곳곳에 흩어져 있으면 아무도 다 찾지 못한다.

**4.2절과 가른다.** 요소가 원천에 있는지 자체를 모르는 것은 4.2절 판정 '확인 필요'이고 만들지 않는다. 여기는 만든 요소의 값(코드 저장값·단위·대표 컬럼)이나 뜻이 같은 후보 컬럼 가운데 어느 것을 쓸지 모르는 것만 적는다.

`확인 방법` 과 `확인 주체` 를 반드시 적는다. 「확인 필요」만 적으면 누구의 일인지 정해지지 않아 그대로 남는다. 주체가 정해지지 않았으면 `지정 필요` 로 적는다.

| 잘못된 예 | 올바른 예 |
|---|---|
| 확인 필요 | 실제 데이터에서 해당 컬럼 저장값 조회 |
| 나중에 확인 | 대상 환경 데이터 구조 목록에서 이름 확인 |

설계 단계에서 **채울 수 없는 것**이 있다. 코드의 실제 저장값, 단위, 기본키, 대표 컬럼 같은 값을 원천 자료가 적어 두지 않았으면 실제 데이터를 봐야 안다. 이것들이 여기 있는 것은 정상이므로 그렇게 적는다. 원천 자료가 적어 둔 값은 그대로 쓰고 여기 올리지 않는다. 빠뜨린 것과 구분되어야 한다.

### 9.1 일반 항목

**일부러 만들지 않은 것**을 적는다. 이 절이 없으면 받는 사람은 빠뜨린 것으로 읽고 되돌려 놓는다.

| 주요 유형 | 근거 출처 |
|---|---|
| 판정·집계 결과 | CQ 문서가 구조에 넣지 말라고 적어 둔 값 |
| 범위 밖 항목 | 업무 범위 자료가 다루지 않는다고 적은 범위 |
| CQ가 값을 쓰지 않아 만들지 않은 항목 | 연결표에 그 값을 쓰는 CQ가 없다 |
| CQ가 요구하지 않는 관계 | 연결표에 그 경로를 타는 CQ가 없다 |
| 뜻이 겹쳐 하나만 고른 컬럼 | 고른 근거 |

**CQ가 요구했는데 원천 근거가 없어 만들지 않은 요소는 여기가 아니라 4.2절에 적는다.** 여기는 원천에 있어도 일부러 만들지 않은 것(CQ 미사용·계산값·범위 밖)만 적는다. 둘을 섞으면 원천을 보강하면 살아나는 항목과 CQ가 요구하지 않아 뺀 항목이 가려지지 않는다.

### 9.2 미적용 중간 개념 — 비워 넘기지 않는다

**중간 개념을 두지 않기로 한 판단은 반드시 여기 적는다.** 없으면 「해당 없음」이라고 적는다.

원천 신호가 있는데 두지 않은 항목은 **다음 사람 눈에 빠뜨린 것으로 보인다.** 그래서 되살려 놓고, 되살린 뒤에야 왜 빼 두었는지를 다시 알게 된다. 적어 두면 그 왕복이 없다.

적는 차례가 정해져 있다. [`intermediate-concepts.md`](intermediate-concepts.md) 가 정한 조건을 **위에서부터 짚어 처음 충족하지 않은 것**을 적는다. 여러 이유를 늘어놓지 않는다 — 실행마다 다른 이유를 대면 판단이 흔들린 것으로 읽힌다.

| 칸 | 기재 내용 |
|---|---|
| 대상 | 두려다 만 개념의 이름과 **무엇을 모은 개념인지**. 예: 참석자명단(교육 1건의 참석자 전체를 묶은 모음) |
| 원천 신호 | 원천 데이터의 어떤 형태가 둘 만해 보이게 했나. 같은 코드를 가진 개념이 있으면 모두 적는다 |
| 미충족 조건 | 1.4 의 네 조건 가운데 이 항목에 해당하는 조건을 **이름으로** 적고, 왜 충족하지 않았는지 적는다. **처음 충족하지 않은 하나만**. 목록 테이블이나 여러 곳이 가리키는 코드면 '여러 개념이 같은 값을 가지나 그 값이 개념이 아님', 한 칸에 값이 여럿이면 '한 칸에 여러 값이 뭉쳐 있음' 처럼 형태마다 따질 조건이 정해져 있다 |
| 적용 조건 | 무엇이 생기면 다시 두나. 대개 CQ가 추가될 때다. 어떤 CQ인지 내용으로 적는다 |

**조건마다 짚는 차례가 있다.** 같은 값을 여럿이 가지는 조건이면 「그 값을 가진 개념이 2건 이상임」 을 먼저, 「그 값 하나에서 2건 이상의 개념으로 뻗어야 답이 나오는 CQ가 있음」 을 다음에 본다. 미충족 조건 칸에는 1.4 의 조건 이름과 충족하지 않은 세부 조건을 함께 적는다. 역할이면 「역할에 딸린 값이나 기간을 묻는 CQ가 있는가」, 뭉친 칸이면 「모음 자체에 딸린 값이 있는가」 를 본다. 차례와 세부는 [`intermediate-concepts.md`](intermediate-concepts.md) 에 있지만, **리포트에는 그 문서의 장 번호가 아니라 조건의 말을 적는다.**

「첫 조건」·「둘째 조건」 처럼 몇 번째인지로 부르는 말도 적지 않는다. 받는 사람은 무엇이 첫째인지 알 길이 없다.

같은 항목을 두 번 적어 보면 차이가 보인다.

| 구분 | 미충족 조건 | 적용 조건 |
|---|---|---|
| 잘못된 예 | 5장 [B] 해당 없음 — 모음에 딸린 값이 없다 | 질문이 추가되면 둔다 |
| 올바른 예 | '한 칸에 여러 값이 뭉쳐 있음'에 해당하여 참석자 개인은 '교육참석사원'으로 분리함. 모음 자체를 개념으로 둘 조건은 미충족. 모음에 딸린 값이 필요하나 원천 스키마 문서상 해당 칸에는 사원번호만 있고 명단 확정 시점을 묻는 CQ도 없음 | '이 교육의 참석자 명단은 언제 확정됐는가'처럼 모음 자체에 딸린 값을 묻는 CQ 추가 시 적용 |

**원천에 잇는 값이나 그 값을 든 테이블이 없으면 두지 않는다.** 미충족 조건 칸에 '원천 근거 없음'과 4.2절 No.를 적고, 적용 조건 칸에 원천에 무엇이 생기거나 어느 매핑 테이블을 채택하면 다시 두는지 적는다.

②의 판정은 [`intermediate-concepts.md`](intermediate-concepts.md) 4장이 정한다. CQ 옆 칸이 이어짐을 요구하는 항목은 그 칸을 따라 **개념을 두므로 여기 적을 것이 없다.** 본문과 칸이 서로 다른 것을 요구한다는 사실만 11절에 적는다.

### 10. 서식 미반영 항목

설계했는데 서식에 칸이 없어 밖으로 뺀 것이다. **반영 위치**를 적어야 찾을 수 있다.

### 11. 입력 문서 간 불일치

입력 문서가 서로 다른 말을 한 항목이다. **어느 쪽이 맞는지 정하지 않고 양쪽을 적는다.** 판단은 문서를 쓴 사람의 몫이다.

예외는 넷이다. 판정할 쪽이 정해져 있어 여기에는 기록만 남긴다.

- CQ 본문과 CQ 옆 칸이 어긋난 항목 — **판정은 칸을 따른다**
- 용어 사전과 스타일 가이드·결정 사항이 두 말이 같은 대상인지를 두고 갈린 항목 — **판정은 가이드·결정 사항을 따른다** ([`verification-report-format.md`](verification-report-format.md) 6절)
- CQ가 요구한 것을 스타일 가이드가 만들 것의 종류로 막은 항목 — **판정은 가이드를 따른다**
- 입력 문서의 결정 사항이 정해 둔 모양을 서식이 막은 항목 — **판정은 서식을 따른다** ([`intermediate-concepts.md`](intermediate-concepts.md) 4장)

처리 칸에는 「칸을 따름」·「가이드를 따름」 처럼 무엇을 따랐는지 적는다. 판정할 쪽이 정해지지 않은 채 남은 항목은 처리 칸에 「판정 보류(작성자 확인 필요)」 로 적는다 — 구조 판정에서 Warning으로 올라간다.

가이드의 예시와 어긋나 보인 항목도 여기 적는다. 예시는 규칙이 아니므로 판정할 것이 없다 — 어긋나 보였다는 것과 무엇을 보고 정했는지만 적는다.

같은 문서 안에서 건수가 맞지 않는 경우도 여기 적는다.

### 12. 결정 기록 — 멈춤에서 받은 답을 항목마다 적는다

**원천 확인과 설계안 확인에서 받은 항목 하나가 한 줄이다.** 사람이 고른 것과 사전 지시로 기본값을 쓴 것이 이 표에서 가려진다. ① 부터 다시 하거나 판정 뒤 설계를 고칠 때 지난 답을 이 표에서 다시 쓴다.

| 칸 | 기재 내용 |
|---|---|
| No. | 1부터 |
| 멈춤 | 「원천 확인」·「설계안 확인」. 스킬 단계 번호는 적지 않는다. '사람 수정' 행만 「⑥(N차)」로 적는다(N은 설계 수정 차수) |
| 대상 | 4.2절 No.와 답 요소, ③~⑤ 에서 새로 정한 요소, 4.3절 No.(대안 꼴을 고른 경우), 또는 입력 문서(경로·해시) |
| 선택지 | 보인 선택지 |
| 기본값 | 보인 기본값. 원천 확인은 「빼고 보고」 |
| 근거 | 판정과 근거 위치 요약 |
| 고른 값 | 적용한 선택지 |
| 앞 값 | 사람이 고치기 전 값. 「사람 수정」 행이 아니면 「해당 없음」 |
| 뒤 값 | 고친 뒤 값. 「사람 수정」 행이 아니면 「해당 없음」 |
| 연쇄 대상 | 이 수정 때문에 함께 바뀐 요소. 없으면 「해당 없음」 |
| 원문 요지 | 사람이 한 말의 요지. 120자 이내로 적고 말을 그대로 옮기지 않는다 |
| 정한 쪽 | 「사람」·「기본값(사람 확인 없음)」·「사람 수정」 가운데 하나. 뒤에 ' · ' 와 답이 온 길(채팅·버튼·답 파일·사전 지시·일괄)을 붙인다. 일괄은 ⑥ 답 「이상 없음」 으로 아래층을 한꺼번에 승인한 항목이다 |
| 적용 상태 | 「적용」·「적용 안 됨(대상이 사라짐)」·「적용 안 됨(입력 변경 필요)」 |

**설계안 확인에서 사람이 대화로 고친 것은 정한 쪽이 「사람 수정」 인 행으로 적는다.** 선택지·기본값 칸은 「해당 없음」, 고른 값 칸에 고친 내용, 근거 칸에 요청 요지와 갈래를 적는다. 고친 절의 근거 칸에는 「사람 수정(12절 No.n)」 을 적는다. 입력 문서를 바꿔야 풀리는 요청은 고치지 않고 적용 상태를 「적용 안 됨(입력 변경 필요)」 으로 둔다.

**① 부터 다시 할 때 지난 답은 대상이 그대로 남아 있을 때만 기본값으로 다시 쓴다.** 대상이 사라진 행은 적용 상태를 「적용 안 됨(대상이 사라짐)」 으로 고친다. 「사람 수정」 행은 예외로 No. 차례대로 다시 적용하고, 「다시 적용 n건 / 적용 안 됨 m건」 을 ⑥ 에 보인다.

판본은 따로 적지 않고 문서 정보 표의 스킬 판본으로 갈음한다.

**⑥ 에서 CQ 증분 반영을 했으면 증분 반영 행 하나를 둔다.** 대상은 「입력 문서(경로·해시 앞 → 뒤)」, 선택지는 「설계 리포트만 고침 / ① 부터 다시」 로 둔다. 근거 칸에는 스크립트가 센 결과와 스킬이 판단한 것을 갈라 적는다.

12절 '사람 수정' 행의 멈춤 칸에는 「⑥(N차)」 를 적는다. 회차 사본 이름은 `<이름>-온톨로지-설계-리포트-N차-r<n>.md`이며, 1차 생성도 `-1차-r1`부터 매긴다.

## 설계 리포트를 쓰면서 보이는 신호

리포트를 쓰다 보면 설계가 빗나간 것이 드러나는 곳이 있다. 리포트를 고치지 말고 **설계를 고친다.**

아래는 모두 **근거 칸이 비는 곳**이다. 근거를 적으려는데 적을 것이 없으면 그 판단을 하지 않은 것이다.

| 신호 | 의미 |
|---|---|
| 3절의 판정 근거 칸이 비었거나 「용어 사전이라서」 처럼 적혀 있다 | 가리지 않고 받아 적었다. 읽는 사람이 되짚을 수 없다 |
| 1. 개요나 절 첫머리 설명이 빠졌다 | 받는 사람은 절 제목만으로 무엇을 적은 절인지 모른다. 「중간 개념이 뭔데?」 같은 물음이 남는다 |
| 칸에 「3장 첫 신호」·「CQ-53」·「가정 A-3」 처럼 번호만 있다 | 스킬 참고 문서나 입력 문서를 펴야만 읽힌다. 번호가 가리키는 내용을 적는다 |
| 칸에 적은 낱말이 입력 문서에 없고, 그때까지 나온 산출물 어디에도 그 낱말이 무엇을 가리키는지 적은 곳이 없다 | 스킬 참고 문서나 가이드의 예시에서 온 말이다. 받는 사람은 그 문서를 볼 수 없다. 입력 문서의 말로 바꾸거나 지운다. 1.4 나 절 첫머리 설명, 표의 정의 칸, 정의 문서의 설명 줄이 그 낱말을 풀어 두었으면 해당하지 않는다 |
| 5.1절에 `근거 CQ` 가 빈 행이 있다 | CQ가 요구하지 않는 것을 만들었다. 규격이 요구한 것이면 5.3절에 적는다 |
| 5.1절의 `개념 설정 근거` 가 비었거나 조건 번호만 적혀 있다 | 왜 하나의 개념으로 두었는지 판단하지 않았거나, 판단을 적지 않았다 |
| 5.2절의 근거가 「자연스러워서」 처럼 적혀 있다 | 이름을 지은 규칙이 없다. 다시 수행하면 다른 이름이 나온다 |
| 4절의 `사용 값` 이 빈 CQ가 있다 | 그 CQ는 검증 리포트 6절의 검사에서 통째로 빠진다 |
| 4절의 `응답 경로` 가 비어 있다 | 경로가 없는 것인지 적지 않은 것인지 알 수 없다. 없으면 없다고 적는다 |
| 4절의 홉 수가 CQ 조건을 넘는 줄이 있다 | 중간 개념을 지나치게 두었거나 구조가 돌아간다. ⑥ 에서 사용자에게 보인다 |
| 6절의 `연결 근거` 가 원천 연결 키나 채택한 매핑 테이블을 가리키지 않는다 | 원천 근거 없이 관계를 만들었다. 지운다 |
| 데이터가 붙지 않은 개념이 있다 | 원천 근거 없이 개념을 만들었다. 정의 문서 검사가 DOC-12(매핑 없는 개념)로 짚는다 |
| 4.2절에 판정이 있음이 아닌데 처리가 '만듦'인 행이 있다 | 근거 없이 만들었다 |
| 8절이 아주 길다 | 참고 문서가 모자라거나, 설계 단계에서 알 수 없는 것을 억지로 만들었다. 고칠 것은 CQ가 요구하지 않는데 만든 것뿐이다. 그 밖의 줄은 검증 리포트 7.4절로 넘긴다. **값을 채워 8절을 줄이지 않는다** |
| 9.1절이 비어 있다 | 만들지 않기로 한 판단을 기록하지 않았다. 실제로 아무것도 빼지 않았다면 CQ가 요구하지 않는 것까지 만들었을 수 있다 |
| 2절 건수와 뒤 절의 줄 수가 다르다 | 한쪽을 고치고 다른 쪽을 두었다 |
| 인용 블록·줄표·조사 띄어쓰기가 보인다 | 옛 서식이다. [`report-conventions.md`](report-conventions.md) 6장으로 점검한다 |

설계안 확인에서 사용자가 그대로 두기로 한 항목은 신호로 보지 않는다. 설계안 확인에서 사람이 고친 요소(12절 '사람 수정')도 신호로 보지 않는다. 2절에 적힌 답을 따른다.

사람이 밖에서 고친 요소(2절 외부 수정)도 신호로 보지 않는다. 검증만 모드는 설계를 고치지 않고 리포트에 있는 그대로 적으며, 신호가 보이면 결과 보고에만 적는다([`verification-procedure.md`](verification-procedure.md) 5.1).
