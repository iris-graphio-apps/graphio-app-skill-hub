# 검증 수행

정의 문서를 검사하고 리포트를 쓴 뒤 구조를 확정해도 되는지 판정하는 절차다. 두 길이 이 문서를 함께 쓴다.

| 길 | 부르는 때 | 읽을 곳 |
|---|---|---|
| 일반 설계의 ⑨ | 스킬이 ①~⑧로 정의 문서를 다 쓴 뒤 | 1~4장 |
| 검증만 모드 | 사람이 구조 판정을 보고 밖에서 정비만 고친 정의 문서를 다시 검증할 때(`--verify`), 설계 수정 차수나 정비만 하는 차수(`--fix`)가 정의 문서를 다시 낸 뒤 | 5장. 검사와 판정 자체는 1~4장을 그대로 따른다. 설계를 바꾸는 외부 수정은 검사하지 않고 멈춘다(5장 머리, 5.4). 수정 단계의 절차는 [`fix-procedure.md`](fix-procedure.md)에 있다 |

**절차를 한 곳에만 둔다.** 두 길이 같은 검사를 저마다 적으면 한쪽만 고쳐져 검사가 어긋난다. [`../SKILL.md`](../SKILL.md) ⑨와 검증만 모드 문단은 이 문서를 가리키기만 한다.

**명령은 이 스킬 폴더(`SKILL.md`가 있는 폴더)에서 수행하는 꼴로 적었다.** 그래서 스크립트는 `scripts/…`로 적었다. 나란히 설치된 converter 스킬은 `../graphio-ontology-converter`다. hub 저장소 루트에서 수행하면 스크립트는 `skills/graphio-ontology-builder/scripts/…`, converter는 `skills/graphio-ontology-converter`로 바꿔 쓴다. 정의 문서·검증 리포트·원천 구조 문서·CQ 문서의 경로도 수행하는 폴더 기준의 상대 경로로 준다. 수집 조건 줄과 판정 문서에 경로가 그대로 남으므로 사용자 폴더 이름이 든 절대 경로는 쓰지 않는다.

## 1. 여섯 걸음

검사 여섯 가지를 하고 검증 리포트를 쓴다. 그 뒤에 구조를 확정해도 되는지 판정한다. 검사 결과를 적는 일과 그 결과에 등급을 매기는 일은 따로 한다. 여섯 검사가 각각 무엇을 보는지는 [`../SKILL.md`](../SKILL.md) ⑨에 있다.

| 차례 | 할 일 | 나오는 것 |
|---|---|---|
| 1 | 정의 문서를 완성한다(①~⑧). 맨 앞 규모 표(`--stats`)와 서식 밖 절까지 붙인다. 검증만 모드는 받은 문서의 사본에서 규모 표만 갱신한다 | 정의 문서 |
| 2 | 수집 스크립트로 스크립트 검사 둘을 한 번에 수행한다(2장) | 검증 리포트 4.1 No.1·No.2 행과 `※ No.2 자동 채움:` 주석, 4.2절 스크립트 행, 수집 조건 줄 |
| 3 | 스킬 검사 넷(No.3~6)과 설계 리포트 11절 확인을 한다 | 4.1 No.3~6 결과, 4.2절 스킬 행, 5절, 6절 |
| 4 | 검증 리포트의 나머지 절을 쓴다. 설계 리포트와 정의 문서가 같은지 확인하고 설계 리포트 2절 건수를 정의 문서 규모 표(`--stats`)로 센다. 설계 리포트의 리포트 판을 '검증 뒤'로 바꾸고 `scripts/check_design_report.py --stage 검증뒤`를 통과시킨다 | 검증 리포트, 설계 리포트 검증 뒤 판 |
| 5 | 판정 스크립트를 수행한다(3장) | 구조 판정 문서 |
| 6 | 판정을 검증 리포트 2절 '구조 판정' 칸에 옮긴다. 확정 불가면 두 길을 안내한다(4장) | 완성된 검증 리포트 |

- 2 뒤에 정의 문서를 고치면 다시 수집한다. 규모 표나 서식 밖 절만 고쳐도 같다. `--stats`로 규모 표를 먼저 갱신한 뒤 수집한다. 고친 내용에 맞춰 5·6절과 스킬 행도 다시 본다. 판정 스크립트가 수집 조건의 정의 문서 해시로 잡아 멈추기 때문이다
- 5 뒤에는 이번 차수 설계 리포트·정의 문서를 고치지 않는다. 고칠 것은 N+1차 이름 파일과 수정 요청서에만 쓴다. 이 규칙을 어기고 고쳤으면 판정 문서의 설계 리포트 해시와 수집 조건의 정의 문서 해시가 달라지므로 판정을 다시 수행한다(4장)
- 수집 스크립트나 판정 스크립트가 종료 코드 2(입력 쪽 멈춤)나 3(스킬 쪽 실패)으로 멈추면 검증 리포트와 판정 문서를 손으로 쓰지 않는다. 종료 코드 2면 표준 오류에 나온 까닭을 고쳐 다시 수행한다. 종료 코드 3은 까닭이 스킬 스크립트·규칙 목록 문서·converter 쪽에 있다는 뜻이라(변환표에 없는 코드나 메시지, 하위 스크립트 실패 같은 것) 입력을 고쳐도 풀리지 않는다. 스크립트를 고치지 말고 사용자에게 알리고 멈춘다. 가르는 법은 [`verification-report-format.md`](verification-report-format.md) 4.1절에 있다

검증 리포트 뼈대는 [`../assets/verification-report-skeleton.md`](../assets/verification-report-skeleton.md)에, 적는 법은 [`verification-report-format.md`](verification-report-format.md)에 있다. 판정 문서의 꼴은 [`structure-judgment-format.md`](structure-judgment-format.md)에 있다.

## 2. 스크립트 검사 둘

**이 스킬의 검사기는 변환 스크립트가 오류 없이 빠뜨리거나 잘못 옮기는 줄을 찾고 통계를 낸다.** 정의 문서를 쓰는 동안 혼자 돌려 본다. 여섯 걸음에서는 수집 스크립트가 대신 돌린다.

```bash
python3 scripts/check_design_doc.py <온톨로지-정의.md>
```

통계만 Markdown 표로 뽑아 정의 문서 맨 앞과 검증 리포트 3절(산출 규모)에 붙인다. 정의 문서 맨 앞의 표는 수집 전에 붙인다. 수집 뒤에 정의 문서를 고치면 이 명령으로 규모 표를 먼저 갱신한 뒤 다시 수집한다.

```bash
python3 scripts/check_design_doc.py <온톨로지-정의.md> --stats
```

가이드가 정한 경고 기호가 `⚠` 가 아니면 알려 준다. 모르고 돌리면 경고문을 못 찾아 그냥 지나간다.

```bash
python3 scripts/check_design_doc.py <온톨로지-정의.md> --warn-mark ※
```

원천 구조 문서를 받았으면 데이터 구조 이름이 거기 있는지 대조한다(DOC-08). 검사기를 혼자 돌릴 때는 하나라도 UTF-8 텍스트로 읽지 못하면 대조하지 않고 종료 코드 2로 멈춘다. 일부만 대조하면 읽지 못한 파일에만 있는 이름이 모두 경고로 올라가기 때문이다. 수집 스크립트는 멈추지 않는다. 텍스트가 아닌 문서를 수집 조건에 '대조 불가(형식)'로 적고 원천 구조 문서 대조를 하지 않는다. 그래서 수집할 때는 받은 원천 구조 문서를 형식과 상관없이 모두 `--source`로 준다.

```bash
python3 scripts/check_design_doc.py <온톨로지-정의.md> --source <원천 구조 문서> …
```

지적마다 규칙 번호(DOC-01~09, DOC-11)와 위치를 붙여 규칙 번호, 줄 번호, 발췌 차례로 낸다. 규칙의 이름과 등급은 [`rule-catalog.md`](rule-catalog.md)에 있다. '확인 필요' 표기(DOC-10)는 지적으로 내지 않고 `--stats` 통계로만 센다. `--json`을 주면 수집 스크립트가 읽는 꼴로 낸다. 판정 스크립트는 수집 스크립트를 거쳐 이 출력을 쓴다. 지적마다 규칙·경우·위치·줄·발췌·발췌 줄 칸이 있고, 앞 판의 칸(등급·자리·무엇·어떻게·종류)도 한동안 함께 둔다. 그 등급 칸은 앞 판의 오류·경고·확인 값이고 스킬 스크립트는 읽지 않는다. 지적의 등급은 규칙 번호로 정해진다. 칸의 뜻은 스크립트 머리 설명에 있다. 종료 코드는 0 오류 없음, 1 오류 있음, 2 문서를 읽지 못함(개념 없음 포함), 3 검사기가 예상하지 못한 오류, 4 출력 쓰기 실패(`--json` 표준 출력)이다.

**여섯 걸음에서는 수집 스크립트가 두 검사를 한 번에 수행한다.** 정의 문서 검사기와 자매 스킬의 변환 스크립트·규격 검사기를 돌린다. 결과는 검증 리포트 4.1 No.1·No.2 행과 4.2절 지적 목록 행으로 바꾼다. `<converter>` 는 converter 스킬 폴더다. 이 문서 첫머리의 기준대로 나란히 설치되어 있으면 `../graphio-ontology-converter`, hub 저장소 루트에서 수행하면 `skills/graphio-ontology-converter`다.

```bash
python3 scripts/collect_findings.py <온톨로지-정의.md> --converter <converter> [--source <원천 구조 문서> …] [--warn-mark ※] [--cq <CQ 문서> …]
# 자매 스킬이 없으면 --converter 대신 --spec-skipped
```

**CQ 문서를 파일로 받았으면 `--cq`로 준다.** 수집 조건 줄에 CQ 문서 해시가 남는다. 다음 차수에 CQ 문서가 바뀌었는지 이 해시로 알아챈다(5.4). 해시는 파일 바이트로 세므로 CQ 문서의 형식은 따지지 않는다. CQ를 파일 없이 문장으로 받았으면 주지 않는다. 수집 조건 줄에 'CQ 문서 없음'으로 적힌다.

출력을 붙이는 법과 멈췄을 때 할 일은 [`verification-report-format.md`](verification-report-format.md) 4.1·4.2절에 있다.

**변환 결과 JSON 은 산출물이 아니다.** 수집 스크립트가 서식이 읽히는지 보려고 임시 폴더에 만들고 버린다. JSON 을 만드는 일은 자매 스킬이 따로 한다.

Error가 나오면 **정의 문서를 고친다.** 서식·설명 Error(DOC-01~03·05~07·11, CNV-01·SPC-01의 서식 갈래)는 Error가 짚은 줄을 고쳐 다시 수집한다. 다만 정의 쪽 칸을 고치는 지적(DOC-04 대표 표시 속성, GDE-01 C-16~C-18 문서 타입)은 설계 리포트 5.1절 대표 표시 칸·7.2절을 먼저 고친 뒤 정의 문서에 옮기고, ⑥(설계안 확인 멈춤)은 다시 열지 않는다. 설계가 바뀌는 지적(개념·속성·관계 더함·뺌·이름, 관계 방향·조인 속성, 원천 선택, 구조 꼴)은 1장 차례 3에서 모아 설계 리포트를 한 번에 고친 뒤 정의 문서에 옮기고 다시 수집한다. 이때 멈춤을 더하지 않는다. 지적의 성격을 가르는 기준은 [`fix-procedure.md`](fix-procedure.md) 3장 성격 칸에 있다. 검증만 모드는 예외다(5.1). 설계안 확인에서 사람이 고친 요소(설계 리포트 12절 '사람 수정')가 짚힌 Error는 고치지 않고 판정에 남긴다.

**Warning과 Info는 고치는 대상이 아니다.** 규격 검사 결과는 검증 리포트에 Error·Warning·Info 세 단계로 적힌다. Warning은 규격은 통과했지만 의도를 확인하라는 것이라 의도한 것인지 짚는다. Info(규격 검사 보류)는 파일만으로 끝낼 수 없어 대상 환경에서 사람이 마무리할 일이라 검증 리포트 7.1절(대상 환경 조치)에도 올린다. 적지 않으면 인수 측은 반입이 왜 막히는지 모른다. 적는 곳은 [`verification-report-format.md`](verification-report-format.md) 4.1절 No.2에 있다. 자매 스킬이 없으면 `--spec-skipped`로 수집한다. 그러면 수집 스크립트가 No.2 결과를 '미수행', 지적 내용을 'converter 스킬 없음'으로 낸다.

## 3. 판정

검증 리포트를 다 쓴 뒤 판정 스크립트를 수행한다. 검증 리포트를 읽어 만들기 때문에 **순서를 바꾸지 않는다.**

```bash
python3 scripts/judge_structure.py \
  <온톨로지-정의.md> <온톨로지-검증-리포트.md> \
  --converter <converter> \
  --required-grade 필수 \
  --manual-checked \
  --design-report <이름>-온톨로지-설계-리포트.md \
  -o <이름>-온톨로지-구조-판정.md
# 수집 때 --spec-skipped·--source·--warn-mark·--cq 를 줬으면 같게 준다
# 검증만 모드는 --previous <앞 차수 구조 판정> 을 더한다(5.6)
# 판정 문서의 차수는 -o 파일 이름의 '-N차'에서 정해진다. N차면 -o <이름>-온톨로지-구조-판정-N차.md
```

`--required-grade` 에는 **CQ 문서가 쓴 등급 말을 그대로** 넘긴다. 검증 리포트 2절 '필수 CQ 기준' 칸에 적은 것과 같아야 한다. [`reading-input-documents.md`](reading-input-documents.md) 2장 '필수 질문' 차례 ③(등급이 없거나 높낮이를 가릴 수 없다)이면 옵션을 주지 않고, 그러면 모든 CQ를 필수로 본다. 차례 ①·②를 가르는 기준도 같은 장에 있다. 규격 검사 결과는 옵션으로 옮기지 않는다. 판정 스크립트가 수집 스크립트를 다시 수행해 검증 리포트와 맞대 보므로 수집할 때 준 `--converter`(또는 `--spec-skipped`)·`--source`·`--warn-mark`·`--cq`를 같게 준다. CQ 문서가 수집 뒤에 바뀌어도 멈춘다.

**스크립트가 세지 못하는 지적은 스킬이 검증 리포트 4.2절에 스킬 행으로 적는다.** 가이드 위반(GDE-01·02), 어느 CQ도 쓰지 않는 개념·속성·관계(CQS-05), 판정할 쪽이 정해지지 않은 입력 문서 간 불일치(INP-01)다. 설계 리포트 11절을 확인해 INP-01 행을 모두 적었으면 해당하는 것이 없어도 `--manual-checked`를 준다. 주지 않으면 판정 문서 5절(미수행 검사)에 입력 문서 간 불일치 확인이 남는다. CQ 등급 미확정은 검증 리포트 2절 '필수 CQ 기준'을 보고 스크립트가 올린다. **산출물을 손으로 고쳐 줄을 더하지 않는다.** 2절 건수와 No.가 어긋난다. 스킬 행 쓰는 법은 [`verification-report-format.md`](verification-report-format.md) 4.2절에 있다.

**입력을 읽지 못하면 스크립트는 판정 문서를 쓰지 않고 종료 코드 2로 멈춘다.** 검증 리포트의 표·판정값·위치가 서식과 다를 때, 수집한 뒤 정의 문서나 옵션이 바뀌어 수집 조건이 맞지 않을 때가 그렇다. `--required-grade` 가 5절 등급 칸이나 2절 '필수 CQ 기준'과 맞지 않을 때도 멈춘다. 검증 리포트 2절의 건수 칸과 4.1 No.3·No.6 결과를 판정 스크립트가 다시 센 값이 적힌 값과 다를 때도 멈춘다. 메시지대로 고쳐 다시 수행한다. 규칙 목록 문서 확인에 걸리거나 스크립트가 예상하지 못한 오류로 멈추면 스킬 쪽 실패라 종료 코드 3이다. 입력을 고쳐도 풀리지 않으므로 1장대로 사용자에게 알리고 멈춘다. **판정 문서를 손으로 쓰지 않는다.** 멈추는 경우와 고칠 곳은 [`structure-judgment-format.md`](structure-judgment-format.md) '판정하지 않고 멈추는 경우'에 있다.

**판정이 나오면 검증 리포트 2절 '구조 판정' 칸에 옮겨 적는다.** 판정과 문서 경로만 적고 까닭은 적지 않는다. 까닭은 판정 문서가 갖는다.

**Error가 있으면 사용자에게 알린다.** 구조를 고칠지 CQ를 필수에서 내릴지는 사용자가 정한다. 스스로 CQ의 등급을 낮춰 판정을 통과시키지 않는다.

결과 보고 첫머리에 이번 차수 산출물 네 경로를 이번 실행에서 실제로 파일을 쓴 차례대로 적는다.

## 4. 확정 불가 뒤 두 길

**판정이 확정 불가면 다음 차수 정의 문서 초안을 만들지 않고 수정 요청서도 만들지 않는다.** 두 길을 안내한다. 수정 요청서는 수정 단계, 적어 두기 호출, 설계를 바꾸는 외부 수정이나 판정 뒤 CQ 변경으로 멈춘 검증만 모드가 만든다(수정 단계·적어 두기 호출은 [`fix-procedure.md`](fix-procedure.md) 5장, 검증만 모드 멈춤은 5.4). 스킬이 수정 단계(`--fix`)로 설계를 고쳐 결과를 다시 내거나, 사람이 이번 차수 정의 문서를 `<이름>-온톨로지-정의-(N+1)차.md`로 복사해 정비만 직접 고친다. 일반 설계(1차)도 검증만 모드도 같다. 확정 가능이면 안내하지 않는다.

- 사람이 직접 고칠 때 이번 차수 파일을 그 자리에서 고치지 않고 사본으로 고치는 까닭: 그 자리에서 고치면 이번 차수 리포트와 정의 문서가 서로 맞지 않게 되고 원본은 되살릴 수 없다. 사본 이름은 5.8의 차수 규칙을 따른다
- 결과 보고에 두 길을 적는다. 두 길을 섞어도 된다. 다만 이번 차수 수집 조건 줄이 'CQ 문서 없음'이면(CQ를 파일 없이 받은 1차) 두 길을 안내하지 않는다. 수정 단계와 검증만 모드는 CQ 문서를 다시 읽어야 해 멈추므로(5.2), CQ를 파일로 주어 새 폴더로 설계 전체를 다시 수행하라고 안내한다
  - 스킬이 판정대로 고치게 하려면 `--fix`로 부른다("판정대로 고쳐 줘"). 판정 지적과 수정 요청서의 대기 행을 보고, 설계 변경은 설계 리포트를 먼저 고쳐 ⑥ 설계안 확인을 다시 연 뒤 정의 문서에 옮긴다. 설계 변경이 0건이면 정비만 한다. 검증까지 수행한다([`fix-procedure.md`](fix-procedure.md))
  - 사람이 고치려면 Error를 보고 이번 차수 정의 문서를 `<이름>-온톨로지-정의-(N+1)차.md`로 복사해 정비만 고친 뒤 `--verify <그 경로>`로 부른다. 정비는 설계 리포트의 설계 칸을 그대로 두고 정의 문서를 설계 리포트·가이드에 맞추는 수정이다. 개념·속성·관계를 더하거나 빼거나 이름을 바꾸는 설계 변경은 `--fix`로 부르거나, 적어 두기 호출로 수정 요청서 `-N차`에 '사람 요청' 행으로 적어 둔다. 설계를 바꾼 사본을 `--verify`로 주면 검사하지 않고 멈춘다(5.4)
- 사람이 만든 사본이 고쳐졌는지는 해시로 가린다. 사본 해시가 이번 차수 검증 리포트 수집 조건 줄의 정의 문서 해시와 다르면 고친 것이다. 해시를 따로 남기지 않는다(5.8)

## 5. 검증만 모드

사람이 구조 판정을 보고 정의 문서의 정비만 밖에서 고쳤거나, 설계 수정 차수·정비만 하는 차수(`--fix`)가 정의 문서를 다시 냈을 때 ①~⑧ 설계를 다시 하지 않고 검사와 판정만 다시 수행한다. 새 판정은 앞 판정의 지적 가운데 무엇이 풀렸고 무엇이 새로 생겼는지를 함께 보여 준다([`structure-judgment-format.md`](structure-judgment-format.md) '앞 판정 대조'). 수정 단계에 이어 수행할 때는 그 차수가 낸 정의 문서가 받은 정의 문서가 되고, 입력과 멈춤은 이 장을 그대로 따른다.

**설계를 바꾸는 외부 수정은 검사하지 않고 멈춘다.** 받은 정의 문서를 `scripts/check_design_report.py --stage 검증뒤 --external`로 설계 리포트와 맞댄다. 설계 리포트 5.1·6·7절 이름 집합과 `definition_index.py` 요소 표를 맞대고 관계 방향·조인 속성·구조 꼴도 본다. 멈춤 판단은 종료 코드가 아니라 `--json` 출력의 `design_diff[]`가 비었는지로 한다. 개념·관계의 더함·뺌·이름 바뀜, 관계 방향·조인 속성·구조 꼴 바뀜이 있으면 5.4대로 멈춘다. 속성 이름의 더함·뺌·바뀜과 설계 리포트 4.2절 근거 위치와 다른 매핑은 스크립트 맞대기가 보지 않으므로 5.6 차례 3에서 앞 차수 정의 문서와 대조해 가르고, 설계 변경이면 5.4대로 멈춘다. 정비 차이만 받는다. 0.3.0의 `--verify`는 구조 수정도 받았다(2026-09-29 사용자 결정). 0.4.0은 이를 정비만으로 좁힌다.

| 차례 | 하는 쪽 | 일 |
|---|---|---|
| 1 | 스킬(생성) | 설계 전체를 수행해 1차 산출물 네 문서를 냄. 확정 불가면 `--fix`를 안내함 |
| 2a | 스킬(수정, `--fix`) | 1차 판정 지적과 수정 요청서 대기 행을 보고 설계 변경은 설계 리포트를 먼저 고쳐 ⑥을 다시 연 뒤 2차 정의 문서에 옮김(설계 수정 차수). 설계 변경이 0건이면 정비만 함(정비만 하는 차수). 남은 일은 수정 요청서 1차에 남기고 이어서 3을 수행함([`fix-procedure.md`](fix-procedure.md)) |
| 2b | 사용자 | 1차 구조 판정을 보고 1차 정의 문서를 `-2차` 이름으로 복사해 정비만 고친 뒤 `--verify <그 경로>`로 부름. 설계 변경은 `--fix`로 부르거나 적어 두기 호출로 수정 요청서에 적어 둠. CQ 문서를 고치기도 함. 2a와 함께 써도 됨 |
| 3 | 스킬(검증만 모드) | 2a에 이어서, 또는 `--verify`로 부르면 고친 정의 문서로 2차 설계 리포트·검증 리포트·구조 판정을 냄 |
| 4 | 사용자 | 2차 판정 6절(앞 판정 대조)로 풀렸는지 확인. Error가 남으면 2a나 2b |

### 5.1 바꾸지 않는 것과 적용하지 않는 규칙

**바꾸지 않는 것이 있다.** 검사 여섯 가지, 판정 규칙(Error 0건이면 확정 가능), 규칙별 등급은 일반 설계와 같다. 수집·판정 스크립트가 멈추면 검증 리포트와 판정 문서를 손으로 쓰지 않는 것도, 확인되지 않은 것을 지어내지 않는 것도 같다.

**사람이 정한 구조를 스킬이 고치거나 지우지 않는다.** 일반 설계의 규칙 가운데 설계를 고치라는 규칙은 이 모드에서 적용하지 않는다. 고치는 대신 판정으로 알린다.

**이 절의 예외는 검증만 모드에만 적용한다.** 1차 설계의 ⑨와 수정 단계에는 적용하지 않는다. 수정 단계는 [`fix-procedure.md`](fix-procedure.md) 3장의 갈래대로 정의 문서를 고치고 지운다. 수정 단계에 이어 수행하는 검증도 검증만 모드라 이 절을 따른다. 고치는 일은 검증을 시작하기 전에 끝난다.

| 규칙 | 규칙이 있는 곳 | 검증만 모드의 처리 |
|---|---|---|
| Error가 나오면 정의 문서를 고친다 | 이 문서 2장 | 고치지 않음. 판정으로 알림 |
| 검사하다 설계를 바꿨으면 그 자리만 고친다 | `SKILL.md` ⑨ 끝 문단 | 설계를 바꾸지 않음 |
| 근거 CQ 칸이 비면 그 개념은 지운다 | design-report-format 5.1 | 규칙은 그대로 적용함. 요소를 더한 외부 수정은 5장 머리대로 검사 전에 멈추므로 이 경우가 생기지 않음 |
| CQ도 규격도 요구하지 않은 속성은 지운다 | design-report-format 5.3 | 지우지 않음. CQS-05가 잡음 |
| CQ가 요구하지 않는 관계는 지운다 | design-report-format 6절 | 지우지 않음. CQS-05가 잡음 |
| 근거 CQ가 빈 7.1·7.2절 행은 지운다 | design-report-format 7절 | 규칙은 그대로 적용함. 요소를 더한 외부 수정은 5장 머리대로 검사 전에 멈추므로 이 경우가 생기지 않음 |
| 리포트를 고치지 말고 설계를 고친다 | design-report-format '설계 리포트를 쓰면서 보이는 신호' | 설계를 고치지 않고 리포트에 있는 그대로 적음 |
| 검증 리포트를 고치지 말고 설계를 고친다 | verification-report-format '검증에서 보이는 신호' | 같음 |
| 대체 매핑이면 뜻이 같은 컬럼으로 고쳐 잇거나 속성을 지우고 응답 불가 CQ 보고에 올린다 | `SKILL.md` ⑨ 매핑 의미 검사 행, verification-report-format 6절, '검증에서 보이는 신호'의 대체 매핑 행 | 고치지 않음. MAP-01 Error로 판정에 남음 |

- 사람이 고친 요소는 두 서식의 신호표가 말하는 '설계가 빗나간 신호'로 보지 않는다. 신호가 보이면 결과 보고에 적기만 한다
- 정의 문서 사본에서 스킬이 손대는 곳은 규모 표(`--stats`) 하나뿐이다. 서식 밖 절이라 변환 결과가 바뀌지 않는다. 받은 원본 파일은 손대지 않는다. 다만 받은 파일이 이미 `-N차` 사본(작업본)이면 그 파일이 곧 N차 정의 문서이므로 5.6 차례 5의 규모 표 갱신만 한다

### 5.2 받는 것

**사용자가 주는 것은 고친 정의 문서 하나다.** 수정 단계에 이어 수행하면 스킬이 고친 초안이 그 자리에 온다. 나머지는 스킬이 앞 차수 산출물에서 찾아 읽는다. 같은 폴더에 앞 차수 산출물이 있고 거기 적힌 입력 문서 경로가 그대로 열리면 더 받을 것이 없다. 찾지 못한 것만 표기나 문장으로 묻는다.

| 읽는 문서 | 얻는 곳 | 없을 때 |
|---|---|---|
| 고친 정의 문서 | 사용자(`--verify`). 수정 단계에 이어 수행하면 스킬이 고친 초안 | 멈춤 |
| 앞 차수 설계 리포트 | 받은 정의 문서의 폴더(`--out`을 받았으면 그 폴더)에서 자동으로 찾음(5.3). 바꾸려면 `--prev-design` | 멈추고 경로를 물음. 설계 리포트 없이는 검증하지 않음 |
| 앞 차수 검증 리포트 | 같음. `--prev-report` | 멈추고 경로를 물음. 수집 옵션과 필수 CQ 기준이 여기에만 있음(5.5) |
| 앞 차수 구조 판정 | 같음. `--prev-judgment` | 멈추지 않음. 대조 없이 판정하고 판정 문서 6절에 '앞 판정 없음' 한 줄 |
| CQ 문서 | 앞 검증 리포트 문서 정보 표의 경로. 새로 주면(`--cq`) 그것 | 경로가 열리지 않으면 멈추고 경로를 물음. 1차에서 CQ를 파일 없이 문장으로 받았으면(수집 조건 줄 'CQ 문서 없음') 멈추고 전체 실행을 안내함. CQ가 바뀌었으면 검사하지 않고 멈춤. 설계 리포트를 다시 맞추지 않고, 번호별 문장 해시로 가린 바뀐 CQ마다 수정 요청서 `-(N-1)차`에 'CQ 변경(CQ 번호)' 행을 적음. 반영은 설계 수정 차수(`--fix`)가 ⑥을 거쳐 함(5.4). 원천·참고 문서·가이드가 바뀌었으면 새 폴더 재생성 안내 |
| 참고 문서(원천 구조 문서 등) | 앞 설계 리포트 3절, 앞 검증 리포트 문서 정보 표·수집 조건 줄의 경로. 새로 주면(`--ref`) 그것 | 경로가 열리지 않으면 멈추고 경로를 물음 |
| 스타일 가이드·서식 가이드 | 앞 검증 리포트 문서 정보 표. 스킬 기본이었으면 지금 스킬 기본. 새로 주면(`--style`·`--format`) 그것 | 경로가 열리지 않으면 멈추고 경로를 물음 |
| converter 스킬 | `SKILL.md` 0)의 찾는 차례 | 앞 차수가 `--spec-skipped`였으면 없어도 됨. 앞 차수에 있었는데 지금 없으면 서식 변환 검사가 미수행이 되고 앞 CNV·SPC 지적은 판정 대조에서 확인 불가가 됨 |

- 앞 차수 산출물에 적힌 경로는 앞 실행 폴더 기준의 상대 경로다. 지금 수행하는 폴더가 다르면 앞 산출물 폴더 기준으로 한 번 더 풀어 보고, 그래도 열리지 않으면 묻는다
- 사용자가 입력 문서를 새로 주면 결과 보고에 "앞 차수와 다른 입력을 씀"을 적는다. 참고 문서가 바뀌면 설계 판단(설계 리포트 3·6·11절)이 달라질 수 있는데 이 모드는 판단을 새로 하지 않으므로 그 점을 경고한다

### 5.3 표기와 자동 찾기

```
/graphio-ontology-builder --verify outputs/인사관리-온톨로지-정의-2차.md
```

| 표기 | 지정 대상 | 주지 않으면 |
|---|---|---|
| `--verify` | 고친 정의 문서 | 검증만 모드가 아님 |
| `--prev-design` | 앞 차수 설계 리포트 | 자동으로 찾음 |
| `--prev-report` | 앞 차수 검증 리포트 | 자동으로 찾음 |
| `--prev-judgment` | 앞 차수 구조 판정 | 자동으로 찾음 |

- 일반 설계의 표기 `--cq`·`--ref`·`--style`·`--format`도 함께 받는다. 주면 앞 차수에 적힌 경로 대신 그것을 쓴다
- `--out`은 앞 차수 산출물이 있는 폴더를 가리킬 때만 쓴다(받은 정의 문서가 다른 폴더에 있을 때). N차 산출물은 늘 앞 차수 산출물이 있는 폴더에 쓴다(5.8). 다른 폴더에 쓰면 다음 차수 자동 찾기가 짝을 찾지 못한다
- `--design`은 이미 스타일 가이드의 다른 이름이라 앞 차수 설계 리포트에 쓰지 않는다
- 표기 규약은 일반 설계와 같다. 파서가 없고 뜻으로 읽는다. "고친 온톨로지 검증만 해줘"처럼 문장으로 불러도 받는다

**앞 차수 산출물은 이렇게 찾는다.**

1. 폴더: `--out`을 받았으면 그 폴더, 아니면 받은 정의 문서가 있는 폴더에서 찾는다
2. 이름 앞부분: 받은 문서 이름이 `<이름>-온톨로지-정의.md`나 `<이름>-온톨로지-정의-N차.md` 꼴이면 그 `<이름>`으로 찾는다. 아니면 그 폴더에 설계 리포트가 한 벌(이름 앞부분 하나)만 있을 때 그것을 쓴다. 둘 다 아니면 `--prev-design`을 달라고 멈춘다
3. 파일: `<이름>-온톨로지-<종류>.md`와 `<이름>-온톨로지-<종류>-N차.md`만 본다. 종류는 정의·설계-리포트·검증-리포트·구조-판정이다. 차수 표기가 없으면 1차이고, 차수는 숫자로 비교한다(10차가 2차 뒤). 하위 폴더(`입력-사본/`·`보관/`·회차 사본)는 보지 않는다
4. 앞 차수: 구조 판정 파일이 있는 가장 높은 차수다. 판정이 없는 차수의 설계·검증 리포트는 앞 차수로 보지 않는다(5.8)

찾은 경로는 결과 보고 첫머리에 적는다. 확인받으려고 멈추지 않는다. 무엇이 바뀌었는지는 설계 리포트 2절과 판정 문서 6절이 보여 준다.

| 수집·판정 스크립트가 종료 코드 2(입력 쪽 멈춤)나 3(스킬 쪽 실패)으로 멈춤 | 스크립트 | 표준 오류의 까닭. 종료 코드 2이고 사람이 고친 정의 문서 때문이면 `-N차` 사본을 고쳐 다시 부르라고 안내. 종료 코드 3(스킬·규칙 목록·converter 쪽)이면 1장대로 사용자에게 알리고 멈춤 |
| 외부 수정에 설계를 바꾸는 차이가 있음(5장 머리) | 스킬(`scripts/check_design_report.py --stage 검증뒤 --external`의 `--json` `design_diff[]`와 앞 차수 정의 문서 대조, 5.6 차례 3) | 검사·판정을 하지 않음. 바뀐 자리를 앞 판정 차수의 수정 요청서(`<이름>-온톨로지-수정-요청-(N-1)차.md`)에 '사람 요청' 행 초안으로 씀. 대상 키·바꿀 내용은 차이에서 채우고 성격은 '설계 변경', 상태는 '해석 필요', 근거는 빈 칸. 이름 바뀜은 짝짓지 않고 뺌·더함 두 행으로 씀(5.6 차례 3 아래 첫 줄). 요청서가 없으면 [`../assets/fix-request-skeleton.md`](../assets/fix-request-skeleton.md)로 새로 만듦. 받은 파일이 N차 사본(작업본)이면 `<이름>-온톨로지-정의-N차-외부수정.md`로 이름을 바꿈. 받은 파일이 다른 파일(다른 폴더나 다른 이름)이면 원본은 두고 차례 2에서 만든 N차 사본을 `-N차-외부수정`으로 이름을 바꿈(5.1 '받은 원본 파일은 손대지 않는다', 5.8). 어느 쪽이든 N차 이름의 정의 문서는 남기지 않고 되돌림 사본도 만들지 않음. 사람이 근거를 채우고 지울 행을 지운 뒤 `--fix`를 부르라고 안내. `--fix` 뒤 정비를 다시 하려면 새 차수 정의 문서를 복사해 `--verify`로 부르라고 함께 안내 |
| N차 설계 리포트가 '확인 대기' 판으로 남아 있음(5.8) | 스킬(5.6 차례 2 복사 전 확인) | 덮어쓰지 않고 검사·판정을 하지 않음. 입력 해시가 같으면 `--fix`로 ⑥부터 이어 가라고, 다르면 그 파일을 치운 뒤 다시 부르라고 안내 |
| 판정 뒤 CQ 문서가 바뀜(아래 CQ 번호별 맞대기에 더함·뺌·문장 바뀜·등급 바뀜이 있음) | 스킬(`scripts/check_design_report.py --stage 검증뒤`) | 검사·판정을 하지 않음. 바뀐 CQ마다 수정 요청서 `-(N-1)차`에 'CQ 변경(CQ 번호)' 행을 씀. 반영은 `--fix`로 부르라고 안내. N차 이름의 정의 문서는 외부 수정 멈춤과 같이 `-N차-외부수정`으로 이름을 바꿔 남기지 않음(받은 파일이 그 이름이면 그 파일을, 아니면 차례 2 사본을) |

- 멈출 때 산출물을 손으로 쓰지 않는다. 설계를 바꾸는 외부 수정으로 멈출 때 스킬이 차이에서 채워 쓰는 수정 요청서 '사람 요청' 행 초안과 판정 뒤 CQ 변경으로 멈출 때 쓰는 'CQ 변경(CQ 번호)' 행은 예외다

**판정 뒤 CQ 문서가 바뀌었으면 검사하지 않고 멈춘다.** CQ를 더하거나 빼거나 문장·등급을 바꿨어도 같다. 설계 리포트를 바뀐 CQ로 다시 맞추지 않고, 바뀐 CQ마다 앞 판정 차수의 수정 요청서(`<이름>-온톨로지-수정-요청-(N-1)차.md`)에 'CQ 변경(CQ 번호)' 행을 적는다. 요청서가 없으면 [`../assets/fix-request-skeleton.md`](../assets/fix-request-skeleton.md)로 새로 만든다. 반영은 설계 수정 차수(`--fix`)가 ⑥ 설계안 확인을 거쳐 한다. 설계를 바꾸는 외부 수정 멈춤(5.4 표)과 같은 꼴이다.

- 바뀐 CQ는 `scripts/check_design_report.py --stage 검증뒤`가 가른다. 이 스크립트가 지금 CQ 문서에서 CQ 번호마다 문장 해시(SHA-256 앞 12자)와 등급을 셈해 앞 설계 리포트 4절 CQ 행의 '해시/등급' 칸과 맞대고 더함·뺌·문장 바뀜·등급 바뀜을 낸다. 4절의 그 칸은 관문 1이 채운 값이며 모델은 해시를 셈하거나 옮겨 적지 않는다. CQ 문서 사본은 남기지 않는다
- 해시는 CQ 행의 질문 문장과 등급만 셈하므로 질문 옆 칸(통과 조건·확정 가정·누가 왜 묻는지)만 바뀐 경우는 네 갈래에 들지 않고 반영하지 않는다. 옆 칸 변경이 설계에 영향을 주면 사람이 CQ 변경 행으로 요청한다
- 해시는 CQ 문서 바이트의 SHA-256 앞 12자다. CQ 문서가 하나면 `shasum -a 256 <CQ 문서>` 출력의 앞 12자와 맞댄다. 여럿이면 수집 스크립트가 파일마다의 해시를 묶어 셈하므로 맞대지 않고 CQ 문서를 늘 다시 읽는다. 앞 수집 조건 줄에 CQ 문서 해시가 없어도(0.2.0 산출물) 늘 다시 읽는다
- 지금 구조로 답하지 못하는 CQ는 검증 리포트 5절에서 응답 불가나 부분 응답이 되어 판정에 CQS-01~04로 나온다. 스킬이 고칠지 재생성할지는 수정 단계의 갈래가 정한다([`fix-procedure.md`](fix-procedure.md) 3장)
- 뺀 CQ의 지적은 판정 대조에서 해소로 셈해진다. 판정 스크립트는 앞 판정만 읽어 CQ 목록이 바뀐 것을 모른다. 그래서 뺀 CQ와 그 CQ에 걸린 앞 판정 지적을 `※ CQ 변경 n:` 줄과 결과 보고에 따로 적는다([`structure-judgment-format.md`](structure-judgment-format.md) '알려진 한계')
- 필수 여부가 바뀌어 생긴 대조 변화는 판정 대조가 기준 변경으로 가른다

### 5.5 앞 검증 리포트에서 되살리는 것

| 값 | 읽는 곳 | 쓰는 곳 |
|---|---|---|
| `--source` 목록, `--warn-mark`, converter 여부(`--spec-skipped`였는지) | 4.2절 표 아래 수집 조건 줄 | 수집·판정 옵션. 원천 경로는 앞 실행 폴더 기준이므로 앞 검증 리포트 문서 정보 표의 경로와 맞대 지금 폴더 기준으로 고쳐 씀 |
| converter 폴더 | 수집 조건 줄에 없음 | `SKILL.md` 0)의 찾는 차례대로 다시 찾음 |
| 원천 구조 문서 해시 | 수집 조건 줄 | 이번 해시와 다르면 결과 보고에 알림. 멈추지 않음 |
| CQ 문서 해시 | 수집 조건 줄(0.3.0부터) | 다르면 5.4의 CQ 번호별 맞대기로 바뀐 CQ를 가려 5.4대로 멈춤. 설계 리포트를 다시 맞추지 않음 |
| 필수 CQ 기준, `--required-grade` | 2절 '필수 CQ 기준' | 판정 옵션. 필수 등급이 바뀌었으면 새 CQ 문서의 등급으로 [`reading-input-documents.md`](reading-input-documents.md) 2장 차례대로 다시 정하고 설계 리포트 2절 `※ CQ 변경 n:` 줄에 적음 |
| INP-01 행 | 4.2절 지적 목록 | 11절이 바뀌지 않았으면 새 4.2절 스킬 행으로 옮기고 `--manual-checked`를 줌. CQ가 바뀌어 11절의 CQ 관련 행을 다시 맞췄으면(5.7) 11절을 다시 확인해 INP-01 행을 새로 적고 `--manual-checked`를 줌 |
| `※ No.2 Warning 확인:` 주석 | 4.1절 표 아래 | 같은 SPC-02 지적(지적 식별자로 맞댐)이 이번 4.2절에도 있으면 이번 No.로 바꿔 다시 적음. 줄 끝의 `(사용자 답)` 표시도 그대로 옮김. 수정 단계가 받은 '의도한 것' 답도 여기에 표시를 붙여 적음. 같은 지적의 주석이 표시 없이 있으면 그 줄에 표시를 붙임([`fix-procedure.md`](fix-procedure.md) 3·4장) |

- CQ 문서가 파일이면 이번 수집에도 `--cq`로 준다. 수집 조건 줄에 이번 해시가 남아 다음 차수가 쓴다
- 판정 옵션 `--design-report`는 앞 차수에서 되살리지 않는다. 이번 차수 설계 리포트 경로(`<이름>-온톨로지-설계-리포트-N차.md`)를 준다. 앞 차수 경로를 주면 판정 스크립트가 리포트 판과 파일 이름을 맞대 종료 코드 2로 멈춘다
- CQ가 바뀐 차수가 아니면 설계 리포트 11절은 이 모드에서 바뀌지 않는다. 그래서 INP-01 행은 앞 검증 리포트에서 그대로 옮긴다. 위치가 옛 꼴(0.2.0, 요소 위치)이면 그 행 참고 자료의 11절 No.로 `입력 문서 '설계 리포트' 11절 No.n` 꼴로 다시 쓴다. 옛 꼴 위치는 0.2.0 스킬이 쓴 검증 리포트에서 온다. 판정 문서 판본이 0.3.0이어도 1차 검증 리포트를 0.2.0 스킬이 썼으면 생긴다
- `--manual-checked`는 이번 실행에서 11절을 확인했다는 뜻이다. 앞 판정에 있었는지로 정하지 않는다. 11절을 짚어 옮긴 행이 빠짐없는지 확인한 뒤 준다

| 1 | 입력을 모으고 차수 N을 정한다. 5.4 멈춤 조건을 확인한다. 외부 설계 변경 멈춤은 차례 3에서 확인한다 | 산출물 경로, 되살린 옵션 |

CQ 문서가 바뀌었으면 바뀐 CQ도 찾는다(5.4) | 바뀐 자리 목록 |
| 4 | 설계 리포트 사본을 다시 맞춘다(5.7) | 설계 리포트 N차 |
| 5 | 정의 문서 사본의 규모 표를 `--stats`로 갱신한 뒤 1장의 여섯 걸음 가운데 2~6을 수행한다. 수집·판정 옵션은 5.5에서 되살린 값이다 | 검증 리포트 N차 |

- 차례 3에서 이름 바뀜은 스킬이 짐작해 짝짓지 않는다. 같은 이름이 없으면 뺀 것과 더한 것으로 적는다. 판정 대조도 이름을 바꾼 요소를 해소 1건과 신규 1건으로 센다
- 차례 3에서 정의 문서 끝에 `## 스킬 수정 기록` 절이 있으면 이번 차수 표시(`- N차 ·`)가 붙은 줄만 읽는다. 앞 차수 표시가 붙은 줄은 이력이라 읽지 않는다. 기록 줄의 꼴은 [`fix-procedure.md`](fix-procedure.md) 6장에 있다
  - 이번 차수 기록 줄은 스킬 수정이다. 앞 차수와 달라진 요소(더함·뺌·이름 바뀜·컬럼 바뀜) 가운데 그 변화를 이번 차수 기록 줄이 적고 있지 않은 것은 외부 수정이다
  - 사람이 요소를 더하거나 이름을 바꾼 외부 수정은 설계 변경이라 이 차례에서 멈춘다(5.4)
  - 절이 없거나 이번 차수 줄이 없으면 스킬 수정은 '해당 없음'이다
  - 기록 줄이 파일에 남으므로 검증이 멈춰 다시 부를 때도 스킬이 고친 것을 외부 수정으로 잘못 적지 않는다
- 차례 3에서 매핑 행을 맞대는 까닭: 설계 리포트 4·5·6·7절에는 속성마다의 매핑 컬럼이 없다. 사람이 같은 데이터 구조 안에서 매핑 컬럼만 바꾸면 요소의 더함·뺌·이름 바뀜으로는 드러나지 않는다. 외부 수정으로 적어 두어야 다음 수정 단계가 그 매핑을 사람이 이은 매핑으로 알아본다([`fix-procedure.md`](fix-procedure.md) 3장 MAP-01 행). 적는 꼴은 [`design-report-format.md`](design-report-format.md) '2절의 외부 수정'에 있다. 매핑 컬럼만 바꾼 외부 수정은 설계 리포트 4.2절 근거 위치대로면 정비이고, 근거 위치와 다르면 설계 변경이라 멈춘다
- 앞 구조 판정을 읽지 못했으면 `--previous`를 주지 않는다. 판정 문서 6절에 까닭 한 줄이 남고 판정은 이어 간다

```bash
python3 scripts/judge_structure.py \

# --source·--warn-mark·--cq·--spec-skipped 는 5.5에서 되살린 대로 준다
```

### 5.7 설계 리포트 다시 맞추기

설계 리포트 N차는 앞 차수 설계 리포트의 사본에서 시작한다. **정비와 외부 수정(정비 차이)이 바꾼 자리만 고친 정의 문서에 맞춰 다시 적고, 설계 판단을 새로 하지 않는다.** 설계 변경 자리(5.1·5.2·5.3·6·7.1절의 요소와 근거)는 고치지 않고 정의 문서와 어긋났는지 `scripts/check_design_report.py --stage 검증뒤`로 확인만 한다. 외부 수정에서 어긋나면 손으로 맞추지 않고 5.4대로 멈춘다. 설계 수정 차수나 정의 쪽 칸을 바꾼 정비 차수에 이어 수행하면 그 차수가 쓴 N차 설계 리포트를 받으므로(5.6 차례 2) 아래 표를 쓰지 않고 확인만 한다. 이때 그 차수가 쓴 설계 리포트와 정의 문서가 어긋나면 외부 수정이 아니라 설계 수정 차수의 관문 실패로 보고 종료 코드 1로 멈춘다. 수정 요청서 초안은 쓰지 않는다. 검증 리포트 4.1 No.4·No.6과 판정은 설계 리포트 4·5·6·7절을 원본으로 삼는다. 이 절들이 정의 문서와 어긋나면 검사가 정의 문서에 없는 구조를 기준으로 맞댄다.

| 절 | 처리 |
|---|---|
| 문서 정보 표 | 작성일은 다시 맞춘 날. '차수'는 N차, '앞 차수 설계 리포트'는 앞 차수 파일 경로, '스킬 판본'은 지금 판본. 정의 문서·검증 리포트 행은 N차 파일. '리포트 판'은 '검증 뒤'. 앞 차수에 행이 없으면 더함 |
| 1. 개요 | 뼈대 문구 그대로. 1.2·1.3에 '차수'·'외부 수정'·'스킬 수정' 풀이가 있음 |
| 2. 설계 결과 요약 | 건수를 새 구조로 고침. '외부 수정' 칸에 건수를 적고 표 아래 `※ 외부 수정 n:`을 한 건에 한 줄씩 둠. '스킬 수정' 칸에 건수를 적고 `※ 스킬 수정 n:`을 이번 차수 기록 줄 하나에 한 줄씩 둠. CQ 문서가 바뀌었으면 `※ CQ 변경 n:`을 바뀐 것 하나에 한 줄씩 둠. '설계안 확인' 칸과 `※ 변경 n:` 주석은 앞 차수 그대로 |
| 4. CQ-구조 연결표 | 사용 값·사용 속성·응답 경로·홉 수를 고친 구조로 다시 적음. CQ 문서가 바뀐 경우는 아래 'CQ가 바뀐 차수' 행(설계 수정 차수)이 다룸. 지금 구조로 경로가 없으면 '경로 없음(사유: 부족 항목)'. 12절 결정 기록은 앞 차수 그대로(검증만 모드는 ⑥을 열지 않음) |
| 5.1 개념 목록 | 개념 행은 고치지 않고 정의 문서의 개념 이름 집합과 같은지 확인만 함. 정의 쪽 칸인 대표 표시 속성은 정의 문서에서 옮겨 적음 |
| 5.2 명명 근거 | 고치지 않음. 이름이 바뀐 개념은 설계 변경이라 5.4대로 멈춤 |
| 5.3 CQ 외 추가 속성 | 고치지 않고 정의 문서의 속성과 같은지 확인만 함 |
| 6. 관계 설계 | 고치지 않고 정의 문서의 관계 이름·방향·조인 속성과 같은지 확인만 함 |
| 7.1 매핑 테이블 제안 | 고치지 않고 정의 문서의 데이터 구조와 같은지 확인만 함 |
| 7.2 문서 타입 | 정의 쪽 칸이라 정의 문서의 문서 타입 프로퍼티에서 옮겨 적음 |
| 8. 확인 필요 사항 | 바뀐 요소에 걸린 행만 고치거나 지움. 사람이 '확인 필요'를 채웠으면 그 행을 지움 |
| 9.1 일반 항목 | 사람이 되살린 요소의 행을 지움 |
| 9.2 미적용 중간 개념 | 사람이나 수정 단계가 더한 중간 개념의 행을 지움. 나머지는 그대로 |
| 10. 서식 미반영 항목 | 바뀐 요소에 걸린 행만 고치거나 지움 |
| 3·11절 | 그대로 둠. 입력 문서에 매인 절이라 이 모드에서 판단을 새로 하지 않음. 예외는 아래 'CQ가 바뀐 차수' 행(설계 수정 차수) |
| CQ가 바뀐 차수 | 검증만 모드는 쓰지 않음. 설계 수정 차수(요청서 CQ 변경 행이 있을 때, 설계 단계 판에서 ⑥에 보임)에서 문서 정보 표 'CQ 문서'의 CQ 건수, 3절 CQ 문서 행의 건수, 4절, 5.1·6·7.1·7.2절(문서 타입)의 근거 CQ, 9.1절의 CQ 제외 행, 11절의 CQ 관련 행(CQ 본문과 옆 칸이 어긋난 행 등)을 바뀐 CQ로 다시 맞춤. 뺀 CQ만 근거 CQ였던 요소는 다시 연 ⑥ 위층에 올리고 기본값은 '지움' |

- 2절 건수는 뒤 절의 줄 수, 정의 문서 규모 표와 같아야 한다. 다시 맞춘 뒤 이 일치부터 확인한다
- 요소를 더하거나 뺀 외부 수정은 설계 변경이라 이 절에 오지 않는다(5.4). 그래서 5.1·5.2·5.3·6·7.1절은 행을 더하거나 지우지 않는다. 근거 CQ만 빠진 요소는 설계 수정 차수에서 다시 연 ⑥ 위층에 올라 기본값 '지움'으로 정해진다(위 'CQ가 바뀐 차수' 행)
- `※ 외부 수정 n:`에는 사람이 고친 정비 한 건(5.6 차례 3이 찾은 매핑 컬럼 바뀜 등)과 대상 요소를 적는다. 앞 차수 정의 문서를 그 자리에서 고침 경고는 번호 없이 `※ 외부 수정 경고:` 줄로 남긴다. 스킬이 설계안 확인 뒤 바꾼 것은 `※ 변경 n:`, 수정 단계가 고친 것은 `※ 스킬 수정 n:`, CQ 문서가 바뀐 것은 `※ CQ 변경 n:`이라 섞지 않는다. 적는 꼴은 [`design-report-format.md`](design-report-format.md) '2절의 외부 수정'·'2절의 스킬 수정'·'2절의 CQ 변경'에 있다
- 설계 수정 차수가 고친 요소의 근거는 그 차수가 설계 리포트를 먼저 고치며 적었다. 이 절은 그 근거 칸을 고치지 않는다

### 5.8 차수와 산출물 이름

| 산출물 | 1차 | N차(N ≥ 2) |
|---|---|---|
| 정의 문서 | `<이름>-온톨로지-정의.md` | `<이름>-온톨로지-정의-N차.md`. 받은 문서의 사본 |
| 설계 리포트 | `<이름>-온톨로지-설계-리포트.md` | `<이름>-온톨로지-설계-리포트-N차.md` |
| 검증 리포트 | `<이름>-온톨로지-검증-리포트.md` | `<이름>-온톨로지-검증-리포트-N차.md` |
| 구조 판정 | `<이름>-온톨로지-구조-판정.md` | `<이름>-온톨로지-구조-판정-N차.md` |

- `<이름>`은 앞 설계 리포트 파일 이름에서 가져온다. 받은 정의 문서 이름이 이 규칙을 따르지 않아도 된다
- 산출물 폴더는 앞 차수 산출물이 있는 폴더다. `--out`을 받아도 바꾸지 않는다(5.3)
- N은 구조 판정이 있는 가장 높은 차수 + 1이다. 판정 없이 남은 N차 설계·검증 리포트는 다음 실행이 같은 N으로 덮어쓴다. 설계 리포트 N차는 늘 앞 차수에서 새로 복사한다. 예외는 '확인 대기' 판이다. 설계 수정 차수가 ⑥에서 멈춰 남긴 N차 설계 리포트(2절 '설계안 확인' 칸이 '확인 대기')는 덮어쓰지 않고 검증만 모드는 멈춘다(5.4). 입력 해시가 같으면 `--fix`로 다시 불러 ⑥부터 이어 가라고 안내하고, 다르면 그 파일을 치운 뒤 다시 부르라고 안내한다. 설계 수정 차수에 이어 수행하는 검증은 앞 차수에서 복사하지 않고 그 차수가 쓴 N차 설계 리포트를 받는다(5.6 차례 2)
- N차 정의 문서가 이미 있으면(스킬이 만든 초안이거나 멈춘 실행이 남긴 사본) 받은 파일이 그것이면 복사하지 않는다. 다른 파일이면 받은 파일로 덮어쓰고 결과 보고에 그 사실을 적는다
- 다만 스킬이 만든 초안이 만든 뒤 바뀌었으면(사람이나 수정 단계가 고쳐 둔 초안) 덮어쓰지 않고 멈춘다. 초안은 N-1차 정의 문서를 바이트 그대로 복사한 것이라, 초안 해시가 N-1차 검증 리포트 수집 조건 줄의 정의 문서 해시와 다르면 바뀐 것으로 본다
- 설계를 바꾸는 외부 수정이나 판정 뒤 CQ 변경으로 멈추면(5.4) 받은 외부 수정본을 `<이름>-온톨로지-정의-N차-외부수정.md`로 보존한다. 받은 파일이 N차 사본이면 이름을 바꾸고, 다른 파일이면 원본은 두고 차례 2에서 만든 N차 사본의 이름을 바꾼다. N차 이름의 정의 문서는 남기지 않고 N-1차 정의 문서의 되돌림 사본도 만들지 않는다. 그래서 멈춘 뒤 `--fix`를 바로 부를 수 있다([`fix-procedure.md`](fix-procedure.md) 7.1 차례 1). 이 이름은 5.3 차례 3의 이름 꼴(`-N차.md`)이 아니라 앞 차수 자동 찾기가 보지 않는다
- 사용자가 앞 차수 정의 문서를 그 자리에서 고쳐 보냈으면 앞 차수 원본은 되살릴 수 없다. 받은 경로가 앞 차수 정의 문서 경로와 같고 그 파일의 해시가 앞 차수 검증 리포트 수집 조건 줄의 정의 문서 해시와 다르면 설계 리포트 2절 `※ 외부 수정 경고:` 줄과 결과 보고에 "앞 차수 정의 문서가 고친 내용으로 바뀌어 앞 차수 리포트와 맞지 않음"을 남긴다. 해시가 같으면(CQ 문서만 바꾸고 정의 문서는 그대로 준 경우) 경고하지 않는다. 4장의 사본이 이 일을 줄인다
- 세 리포트 문서 정보 표에는 '차수'·'스킬 판본' 행이 있다. 1차에도 둔다
- 수정 요청서(`<이름>-온톨로지-수정-요청-N차.md`)는 수정 단계, 적어 두기 호출, 설계를 바꾸는 외부 수정이나 판정 뒤 CQ 변경으로 멈춘 검증만 모드가 만든다. N은 요청서를 만들 때 읽은 판정의 차수이고 1차에도 `-1차`를 붙인다(수정 단계·적어 두기 호출은 [`fix-procedure.md`](fix-procedure.md) 5장, 검증만 모드 멈춤은 5.4)

### 5.9 결과 보고

결과 보고와 실행 결과 파일(`<이름>-실행결과-N차.json`, mode는 `--verify`)은 [`run-result-format.md`](run-result-format.md)의 결과 보고 차례(산출물 표 → 판정 요약 세 줄 → 사람이 정할 일 → 다음 할 일 → 경고 한 줄)와 칸을 따른다. 종료 코드와 status는 [`stop-catalog.md`](stop-catalog.md) 표를 따른다. 수정 단계에 이어 수행했으면 그 차수의 결과 보고 하나로 합친다([`fix-procedure.md`](fix-procedure.md) 8장). 검증만 모드에만 있는 항목과 그 자리는 아래와 같다.

1. 산출물 표(차례 1): 이번 차수 산출물(정의 문서·설계 리포트·검증 리포트·구조 판정 N차)의 경로를 이번 실행에서 실제로 파일을 쓴 차례대로 적음. 찾은 경로와 되살린 옵션(앞 차수 산출물 셋, 입력 문서, `--source`·`--warn-mark`·converter 여부·`--required-grade`, 판정에 준 `--design-report`)을 표 아래에 적음
2. 판정 요약(차례 2): 확정 가능 또는 확정 불가, Error·Warning 건수, 대조 건수(해소·유지·신규·기준 변경·확인 불가), 바뀐 자리 요약(설계 리포트 2절 `※ 외부 수정`·`※ 스킬 수정` 주석의 요지. 사람이 고친 요소에서 신호표의 신호가 보였으면 함께 적음)
3. 사람이 정할 일(차례 3): 멈췄으면 까닭(설계를 바꾸는 외부 수정 또는 판정 뒤 CQ 변경), 수정 요청서 `-(N-1)차` 경로와 이번에 적은 행('사람 요청' 행 초안, 'CQ 변경(CQ 번호)' 행), `-N차-외부수정` 파일 경로
4. 다음 할 일(차례 4): 확정 불가나 멈춤이면 행동 코드 fix(스킬이 설계를 고쳐 결과를 다시 냄)·verify(이번 차수 정의 문서를 `<이름>-온톨로지-정의-(N+1)차.md`로 복사해 정비만 고친 뒤 `--verify <그 경로>`로 다시 부름)·queue_add(설계 변경을 수정 요청서에 적어 두기만 함) 가운데서 고름. 멈춤이면 `--fix` 뒤 정비를 다시 하려면 새 차수 정의 문서를 복사해 `--verify`로 부르라는 안내를 덧붙임
5. 경고(차례 5): 원천 구조 문서 해시가 바뀜, 앞 차수와 다른 입력을 씀, 앞 차수 정의 문서를 그 자리에서 고침, N차 정의 문서를 덮어씀. 해당하는 것만
