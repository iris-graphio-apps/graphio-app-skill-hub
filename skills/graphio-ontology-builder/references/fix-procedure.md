# 수정 수행

구조 판정의 지적을 읽고 정의 문서를 고치는 절차다. 판정이 확정 불가일 때 주로 부르고, 확정 가능이어도 "Warning도 고쳐"로 부를 수 있다. 판정과 수정 요청서에 모은 항목을 보고 설계를 고쳐 결과를 다시 낸다. 설계 변경은 설계 리포트를 먼저 고치고 다시 연 ⑥을 거쳐 ⑦~⑨로, 정비는 정의 문서 초안에서 고친 뒤 검증만 모드로 새 판정을 낸다. 사람이 정할 지적은 묻고, 입력 문서를 바꿔야 풀리는 지적은 알린다. 검증만 모드는 ①~⑧을 다시 하지 않고 고친 정의 문서로 검사와 판정만 다시 하는 단계이며, 1차 설계의 ⑨와 다르다.

**절차를 이 문서 한 곳에만 둔다.** [`../SKILL.md`](../SKILL.md)의 `--fix` 문단은 이 문서를 가리키기만 한다. 정비만 하는 차수에 한해 고친 뒤의 검사와 판정은 [`verification-procedure.md`](verification-procedure.md) 5장(검증만 모드)을 그대로 따르고, 이 문서에 다시 적지 않는다.

명령과 경로를 적는 꼴은 [`verification-procedure.md`](verification-procedure.md) 첫머리와 같다.

---

## 1. 흐름

스킬은 생성 → 검증 → 수정 → 검증으로 돈다. 수정 단계는 판정과 수정 요청서에 모은 요청을 보고 설계를 고쳐 결과를 다시 내는 단계다.

| 차례 | 하는 쪽 | 일 |
|---|---|---|
| 1 | 스킬(생성) | 설계 전체를 수행해 1차 산출물 네 문서를 냄. 확정 불가면 `--fix`를 안내함 |
| 2a-1 | 스킬(설계 수정 차수, `--fix`) | 1차 판정 지적과 수정 요청서 1차의 대기 행 가운데 설계 변경 성격(3장)이 1건 이상이거나 CQ 변경 행이 1건 이상일 때. 2차 설계 리포트를 먼저 고치고 다시 연 ⑥을 거쳐 ⑦~⑨로 정의 문서·검증 리포트·구조 판정 2차를 냄(7.1). 남은 결정 필요·입력 변경 필요는 수정 요청서 1차에 남김 |
| 2a-2 | 스킬(정비만 하는 차수, `--fix`) | 설계 변경 성격과 CQ 변경 행이 모두 0건일 때. 정비와 답을 받은 결정 필요를 2차 초안에 고침(7.2). 남은 결정 필요·입력 변경 필요는 수정 요청서 1차에 남김 |
| 2a-3 | 스킬(적어 두기) | 사람 요청만 받고 반영을 청하지 않은 호출. 수정 요청서 1차에 대기 행만 적고 차수를 돌리지 않음(2장) |
| 2b | 사용자(밖에서 수정) | 1차 정의 문서를 `-2차` 이름으로 복사해 정비 차이만 직접 고친 뒤 `--verify <그 경로>`로 부름. 설계를 바꾸는 수정은 수정 요청서의 사람 요청 행으로 적고 `--fix`로 부름. CQ 문서를 고쳤으면 `--fix`로 부름(3장) |
| 3 | 스킬(검증만 모드) | 2a-2에 이어서, 또는 `--verify`로 부르면 2차 정의 문서로 설계 리포트의 정비·외부 수정 자리만 다시 맞추고(설계 칸은 어긋났는지 확인만), 검사와 판정을 다시 수행함. 설계 리포트·검증 리포트·구조 판정 2차를 냄. 2a-1은 이 행 대신 7.1 차례 5(⑦~⑨)로 감 |
| 4 | 사용자 | 2차 판정 6절(앞 판정 대조)과 수정 요청서로 풀린 것과 남은 것을 확인함. Error가 남으면 2a나 2b |

- 한 번 부르면 한 차수만 돌고 결과를 보고한다. 새 판정이 다시 확정 불가여도 스스로 되풀이하지 않는다. 되풀이하면 사람이 한 차수의 판정과 수정 요청서를 보기 전에 다음 차수의 수정이 이어진다. 적어 두기 호출은 차수를 돌리지 않는다
- 사람이 초안을 직접 고치는 길(`--verify`)은 정비 차이만 받는다. 정비 차이만 있는 초안(사람이 N차 정의 문서를 `-N+1차` 이름으로 복사해 고친 것)을 두고 `--fix`로 부르면 정비만 하는 차수(7.2)는 그 초안 위에서 이어 고친다. 설계 수정 차수(7.1)는 N+1차 정의 문서가 이미 있으면 덮어쓰지 않고 멈춘다(관문 1 `check_definition_absent`). 그 초안을 `--verify`로 먼저 받거나 지운 뒤 다시 부른다
- **설계를 바꾸는 외부 수정이 든 초안이면 고치지 않고 멈춘다.** 설계 차이는 `scripts/check_design_report.py --stage 검증뒤 --external`(대상: N+1차 초안과 N차 설계 리포트. 설계 리포트 5.1·6·7절 이름 집합과 definition_index.py 요소 표를 맞대고 관계 방향·조인 속성·구조 꼴 차이도 봄)로 가린다. 멈출 때 바뀐 자리를 수정 요청서 `-N차`의 「사람 요청과 CQ 변경」 절에 사람 요청 행 초안(성격 '설계 변경', 상태 '해석 필요', 근거 빈 칸)으로 써 주고, 외부 수정본은 `-N+1차-외부수정` 이름으로 옮겨 보존한다. 정의 문서 N차는 그대로 둔다. 이 멈춤은 종료 코드 2로 끝나고 실행 결과 파일 status는 '입력 필요'다. 사람은 근거 칸을 채우고 반영하지 않을 행을 지운 뒤 `--fix`로 다시 부른다(5장)
- 스킬이 고치는 것은 N+1차 설계 리포트(설계 변경), N+1차 정의 문서(부분 수정), 수정 요청서다. CQ 문서·원천 구조 문서·참고 문서·가이드는 입력이라 고치지 않는다. 입력을 바꿔야 풀리는 지적은 알리기만 한다
- 검증만 모드의 예외 규칙(사람이 정한 구조를 고치거나 지우지 않음, [`verification-procedure.md`](verification-procedure.md) 5.1)은 검증만 모드에만 적용한다. 수정 단계는 3장의 성격과 갈래대로 고친다

## 2. 부르는 법

```
/graphio-ontology-builder --fix outputs/인사관리-온톨로지-구조-판정.md
```

| 표기 | 지정 대상 | 주지 않으면 |
|---|---|---|
| `--fix` | 고칠 구조 판정 | 수정 단계가 아님 |
| 표기 없음(판정 뒤 사람 요청 문장만) | 요청서 사람 요청 행에 상태 대기로 적고 끝남, 설계 리포트·정의 문서는 고치지 않음 | 해당 없음 |

- 판정 경로 없이 `--fix`만 주거나 문장으로만 부르면 판정이 있는 가장 높은 차수의 판정을 쓴다. 찾는 폴더는 실행 결과 파일·진행 상태 파일(`<이름>-진행.json`)·입력 목록 파일이 가리키는 폴더이고, 그런 파일이 없으면 `--out`으로 준 폴더다. 앞 대화 기록에는 기대지 않는다. 그 폴더에 설계 리포트가 한 벌(이름 앞부분 하나)만 있을 때 그 벌을 쓴다. 폴더를 모르거나 여러 벌이면 판정 경로를 묻는다
- 판정 경로를 주면 그 판정이 있는 폴더와 판정 파일 이름의 앞부분으로 찾는다. 파일을 고르고 차수를 가르는 법은 [`verification-procedure.md`](verification-procedure.md) 5.3과 같다
- 받는 판정은 판정이 있는 가장 높은 차수의 것뿐이다. 더 높은 차수의 판정이 있는 판정을 주면 멈추고 가장 높은 차수의 판정을 알린다. 옛 판정으로 고치면 이미 판정까지 있는 다음 차수 산출물을 덮어쓰게 된다
- 문장으로 불러도 받는다. "판정대로 고쳐 줘", "판정 Error 고쳐 줘", "수정 요청서에 답 적었어, 이어서 고쳐 줘"가 그렇다
- `--fix`가 받는 입력은 셋이다. 판정 지적(기본은 판정 N차 3.1의 Error, 수정 범위가 'Warning 포함'이면 3.2까지), 사람 요청(호출·채팅 문장, 수정 요청서에 사람이 직접 적은 행, 답 봉투의 대상 없는 `free_text` 행), CQ 변경(CQ 문서 해시를 N차 검증 리포트 수집 조건 줄과 맞대 알아챔, 3장). 사람 요청과 CQ 변경은 수정 범위와 상관없이 받는다
- **사람 요청만 받고 반영을 청하지 않은 호출은 적어 두기만 한다.** 해석한 내용을 고치기 전에 다시 보이는 되짚기를 낸 뒤 수정 요청서에 상태 '대기' 행으로 적고 끝낸다(칸은 5장). 차수를 돌리지 않고 설계 리포트·정의 문서는 고치지 않는다. 판정 뒤에 N차 파일을 고치지 않기 위함이다. 요청서가 없으면 뼈대로 `-N차` 요청서를 새로 만든다(5장). 반영은 `--fix`('판정대로 고쳐 줘'·'모은 것 반영해 줘')로 부를 때 대기 행과 판정 지적을 한 차수로 묶어 한다. 적어 두기 호출에는 새 표기가 없다. 판정 뒤 `--fix`·`--verify`·`--answers` 없이 문장으로 요청하면 그 호출이 적어 두기 호출이다. 요청인지 애매한 문장은 되묻는다([`design-report-review.md`](design-report-review.md) 답 해석 절)
- 수정 범위는 멈춤 질문 파일과 답 봉투의 범위 칸으로 정한다. 기본은 판정 3.1의 Error만 고친다. 범위 칸이 'Warning 포함'이면 3.2의 Warning까지 고친다. 호출 문장 "Warning도 고쳐"는 'Warning 포함'과 같은 값으로 읽는다. 기본으로 부르면 Warning은 고치지도 묻지도 않고, 그 가운데 스킬 수정 갈래의 건수만 결과 보고에 알린다. 수정 요청서에 새로 물을 결정 필요·입력 변경 필요는 수정 범위 안에서만 센다. 기본 호출이면 판정 3.1에서 나온 것만 적고, 3.2의 Warning은 결정 필요든 입력 변경 필요든 올리지 않는다. 그 Warning은 판정 3.2에 그대로 남는다. 범위 칸은 판정 지적에만 적용하고, 사람 요청·CQ 변경 행은 범위와 상관없이 다룬다. 앞 요청서에서 답을 받은 행은 범위와 상관없이 옮긴다(5장). 앞 요청서 3절에 답이 있는 Warning 행은 수정 범위와 상관없이 그 답대로 한다(고치라는 답이면 고치고, 의도한 것이라는 답이면 두고 주석)
- 판정 N차가 확정 가능이면(Error 0건) 초안 N+1차는 고칠 것이 1건 이상일 때만 만든다. 확정 가능 판정에는 다음 차수 초안을 두지 않기 때문이다. 기본 호출은 고칠 Error가 없으므로 초안 없이 결과 보고로 끝난다(7장)
- 일반 설계의 표기 `--cq`·`--ref`·`--style`·`--format`도 함께 받는다. 주면 앞 차수에 적힌 경로 대신 그것을 쓴다
- `--out`은 판정을 찾는 폴더로만 쓴다. N+1차 산출물과 수정 요청서는 늘 판정 N차가 있는 폴더에 쓴다. 다른 폴더에 쓰면 다음 차수 자동 찾기가 짝을 찾지 못한다
- 받는 것과 멈추는 경우는 검증만 모드와 같다([`verification-procedure.md`](verification-procedure.md) 5.2·5.4). 다만 사용자가 주는 것은 정의 문서가 아니라 판정이고, 주지 않아도 된다. 판정 N차의 짝(정의 문서·설계 리포트·검증 리포트 N차)과 입력 문서는 스킬이 찾아 읽는다

## 3. 지적의 세 갈래

| 갈래 | 뜻 | 스킬이 하는 일 |
|---|---|---|
| 스킬 수정 | 정의 문서만 고치면 풀리고, 고칠 내용을 지금 입력 문서로 정할 수 있음 | 다음 차수 초안을 고침. 설계 규칙(①~⑧)과 참고 문서를 그대로 따름. 개념·관계를 새로 더하는 수정은 결정 필요를 묻는 자리에서 함께 보여 주고 확인받음(4장) |
| 결정 필요 | 정의 문서를 고치면 풀리지만, 어느 쪽으로 고칠지 입력 문서만으로 정할 수 없음 | 선택지를 보여 주고 물음. 답하면 스킬 수정처럼 고침. 답하지 못하면 수정 요청서에 남김 |
| 입력 변경 필요 | 정의 문서만으로는 풀리지 않음. CQ 문서·원천 구조 문서·참고 문서·가이드를 바꿔야 함 | 고치지 않음. 어느 입력을 어떻게 바꿔 다시 부를지 수정 요청서와 결과 보고에 적음 |

**지적과 요청마다 갈래와 따로 성격을 가른다.** 성격은 고칠 자리가 설계 리포트인지, 정의 문서인지, 입력 문서인지를 정한다.

| 성격 | 뜻 | 스킬이 하는 일 |
|---|---|---|
| 설계 변경 | 요소를 더하거나 지우거나 설계 칸 값(개념·속성·관계의 더함·뺌·이름, 관계 방향·조인 속성, 원천 선택, 구조 꼴)을 바꿈 | 갈래가 스킬 수정이어도 정의 문서를 바로 고치지 않음. 설계 수정 차수에서 N+1차 설계 리포트를 먼저 고치고 다시 연 ⑥을 거쳐 ⑦~⑨로 정의 문서에 옮김(7.1) |
| 정비 | 고칠 값이 설계 리포트에 이미 있음(6절 조인 속성, 4.2절 근거 위치, 5.1절 식별 속성, 7.1절 MT 번호 등). 설계 칸은 그대로 두고 정의 문서를 설계 리포트·스타일 가이드·서식 가이드에 맞춤 | 정의 문서에서 고치고 설계 리포트 2절 '스킬 수정' 줄과 `## 스킬 수정 기록`(6장)에 남김 |
| 입력 변경 | 입력 문서를 바꿔야 풀림 | 고치지 않음. 갈래 '입력 변경 필요'처럼 알림 |

- 성격을 가리지 못하면 설계 변경으로 둔다
- 정의 쪽 칸(설계 리포트 5.1절 대표 표시 속성·7.2절 문서 타입)을 바꾸는 정비(DOC-04, GDE-01 C-16~C-18)는 설계 리포트의 그 칸을 먼저 고친 뒤 정의 문서에 옮긴다. ⑥은 다시 열지 않는다
- 설계 리포트 8절(확인 필요 사항)·10절(서식 미반영 항목) 행은 성격과 상관없이 바뀐 요소를 따라 고친다
- 규칙마다의 성격은 아래 규칙 표의 '성격' 칸에 있다

설계안 확인(⑥)에서 사람이 대화로 꺼낸 수정도 이 세 갈래로 가른다. 대상이 판정 지적이 아니라 사람의 요청이다. 생성 중 ⑥에서 입력 문서를 받으면 CQ 문서만 바뀌고 부합 조건을 모두 지날 때 설계 리포트만 고치고, 그 밖에는 ①부터 다시 한다. 판정 뒤 설계 수정 차수에서 다시 연 ⑥은 CQ 변경만 받고, 원천 구조 문서·참고 문서·가이드 변경은 받지 않고 아래 재생성 안내를 따른다([`design-report-review.md`](design-report-review.md) 4장).

입력 변경 필요를 다시 부르는 법은 바꿀 입력에 따라 갈린다.

- CQ 문서를 바꾸면 `--fix`로 다시 부른다. 스킬은 바뀐 CQ를 수정 요청서 대기 행(출처 'CQ 변경(CQ 번호)')으로 받아 설계 수정 차수에서 다시 연 ⑥을 거쳐 반영한다(아래 CQ 변경 줄, 7.1). 'CQ가 바뀐 차수' 규칙([`verification-procedure.md`](verification-procedure.md) 5.7)은 N+1차 설계 리포트의 설계 단계 판에 써서 ⑥에 보인다
- 원천 구조 문서·참고 문서·가이드를 바꾸면 재생성(설계 전체를 다시 수행)을 안내한다. 설계 리포트 3·6·11절의 판단이 그 문서들에 매여 있는데 검증만 모드는 그 판단을 새로 하지 않는다
- 재생성은 새 폴더(`--out`)로 부르라고 적는다. 같은 폴더로 부르면 1차 네 문서를 덮어쓰고, 남은 2차 이후 파일이 앞 차수 자동 찾기에 걸린다
- 다시 연 ⑥에서도 원천 구조 문서·참고 문서·가이드 변경은 받지 않는다. 바꾸려면 위처럼 새 폴더로 재생성한다

**규칙마다 갈래를 아래처럼 정한다.** 표에 적은 조건 밖에서는 갈래를 바꾸지 않는다. 같은 판정을 두 번 고쳐도 갈래가 실행마다 달라지지 않게 하기 위함이다. 조치 지침은 [`rule-catalog.md`](rule-catalog.md) 3절에 있다.

- 성격이 정해진 하위 경우도 설계 리포트에 맞는 값이 있는데 정의 문서에서만 어긋났으면 정비로 다룬다. 정비로 정한 하위 경우라도 고치면 설계 칸이 바뀌는 경우는 고치지 않고 대기 행으로 올린다(7.1 표 아래)
- 관계 방향 칸(→·←·↔) 값을 고르는 수정은 정비다. 설계 칸의 관계 방향은 출발·도착이 뒤바뀐 것만 뜻한다. 식별 속성을 고르거나 비우는 수정은 설계 변경이다(설계 리포트 5.1절 식별 속성 칸은 설계 칸)
- 이름이 틀린 지적은 공백과 허용되지 않는 글자를 뺀 꼴로 설계 리포트 행과 맞대고, 관계는 관계 이름으로 찾는다. 공백만 어긴 개념 이름은 스타일 가이드 S-03대로 고치는 정비다
- 정의 문서에 고칠 글자가 없는 지적(다시 변환, 확인 결과만 적음)은 정비로 센다
- 답에 따라 성격이 갈리는 지적은 답을 받기 전에는 '결정 필요'로 센다. 차수 갈래(7장 첫머리)는 답을 반영할 때 다시 센다. CQS-01~04의 미응답 사유 바로잡기는 설계 변경이고 다시 연 ⑥의 아래층에 '미응답 사유 정정' 항목으로 보이며 기본값은 승인이다(사전 지시가 있으면 그대로)
- 수정 요청서 성격 칸에는 가른 뒤 값(설계 변경·정비·입력 변경)만 적는다. '결정 필요'·'건마다 가름'은 성격 값이 아니라 가르기 전 상태다. 가르지 못하면 '설계 변경'으로 적는다
- 사람 요청은 성격을 건마다 가른다(맞댈 곳은 대상 키가 가리키는 설계 리포트 절)
- 사람이 이은 매핑은 1차부터 N차까지 설계 리포트 2절 `※ 외부 수정 n:` 줄 가운데 매핑 › 속성의 '더함'·'컬럼 바뀜' 줄로 가린다([`verification-procedure.md`](verification-procedure.md) 5.6 차례 3). 스킬이 수정 단계에서 더하거나 바꾼 것은 사람이 한 것이 아니다. 1차부터 N차까지 설계 리포트 12절에 '사람 수정'으로 적힌 요소와, 수정 요청서 '사람 요청' 행을 반영한 요소(반영 칸에 차수와 설계 리포트 12절 No.가 적힌 행)도 사람이 정한 요소로 본다
- 스타일 가이드가 막은 CQ인지는 N차 설계 리포트 11절에서 가린다
- MAP-01에서 뜻이 같은 컬럼을 먼저 찾는 까닭: 맞는 컬럼이 원천에 있는데 속성을 지우면 원천에 있는 값이 정의 문서에서 빠지고, 답할 수 있는 CQ가 응답 불가 CQ 보고에 잘못 오른다. 검증만 모드에는 이 손실을 잡는 규칙이 없다
- MAP-01을 맞는 컬럼으로 바꿔도 판정 문서의 조치 방안 칸에는 검사 규칙의 조치 지침('해당 매핑을 지움. 뜻이 같은 원천 컬럼이 같은 데이터 구조에 없으면 속성을 지우고 그 값을 쓰는 CQ를 검증 리포트 5.2절에 올림')이 그대로 나오고, 실제로 한 일은 기록 줄과 수정 요청서 5절에 남는다
- 구조를 더할 때도 일반 설계의 원칙을 따른다. CQ가 요구하고 원천 근거가 있을 때만 만든다. 근거는 일반 설계와 같은 원천 대조 규칙으로 확인한다([`source-match.md`](source-match.md), [`../SKILL.md`](../SKILL.md) ⑤·⑦). 근거가 없으면 입력 변경 필요로 넘긴다
- 판정 N차를 만든 뒤 CQ 문서가 바뀌었는지는 CQ 문서 해시를 N차 검증 리포트 수집 조건 줄과 맞대 가린다. 바뀌었으면 CQ 번호마다 문장 해시(SHA-256 앞 12자)를 N차 설계 리포트 4절 CQ 행의 번호별 해시와 맞대 더함·뺌·문장 바뀜·등급 바뀜을 가른다. 이 맞대기는 `scripts/check_design_report.py --stage 검증뒤`가 하고 모델이 해시를 셈하지 않는다. CQ 문서가 여럿이어도 CQ 번호별로 맞댄다. N차에 번호별 해시가 없으면(0.3.0·0.2.0 산출물) CQ 문서가 바뀌었을 때 모든 CQ를 '문장 바뀜 확인 필요' 대기 행으로 올린다. 수집 조건 줄에 CQ 문서 해시도 없으면(0.2.0 산출물) 바뀐 것으로 본다([`verification-procedure.md`](verification-procedure.md) 5.4). 가른 결과는 CQ 번호마다 수정 요청서 대기 행(출처 'CQ 변경(CQ 번호)')으로 적고, 설계 수정 차수에서 다시 연 ⑥을 거쳐 반영한다. CQ 문서 사본은 남기지 않는다. 빠진 CQ의 지적은 고치지 않고 결과 보고에 적는다. 필수 여부가 바뀐 CQ는 바뀐 필수 여부로 갈래를 정한다

## 4. 결정 필요를 받는 법

**묻는 자리는 다시 연 ⑥ 위층이다.** 설계 수정 차수에서는 답이 없는 결정 필요와 개념·관계를 더하거나 빼는 수정을 다시 연 ⑥ 위층에 모아 묻고, 답을 모두 받은 뒤 ⑦로 간다([`design-report-review.md`](design-report-review.md) 4장). 정비만 하는 차수는 ⑥을 열지 않으므로 고치기 전에 같은 꼴로 한 번에 묻는다.

- 묻기 전에 앞 수정 요청서 3절의 답(5장 '답은 이렇게 읽는다')과 N차 검증 리포트 4.1절의 `※ No.2 Warning 확인:` 주석을 읽는다. 이미 답이 있는 지적은 다시 묻지 않는다. 주석의 4.2절 No.로 검증 리포트 행을 찾아 지적 식별자로 판정 N차의 지적에 맞댄다
- 주석 가운데 줄 끝에 `(사용자 답)` 표시가 붙은 것만 묻지 않는 근거로 쓴다. 사용자가 의도한 것으로 답한 주석이기 때문이다. 그 SPC-02는 '의도한 것' 답을 받은 것과 같게 다룬다(5장). 표시가 없는 주석은 1차 ⑨에서 스킬이 스스로 판단해 적은 것이라, 그 SPC-02는 다른 결정 필요처럼 묻는다
- 묻는 꼴은 멈춤 질문 파일(JSON 원본)이고, 사람에게 보이는 글은 그 파일에서 만든다. 결정 필요 한 건은 4~6줄로 보이고 수정 범위 칸('Error'·'Warning 포함')을 함께 둔다. 답은 답 봉투(`--answers`)나 대화로 받는다. 수정 요청서 3절 답 칸은 파일로 답하는 다른 길로 남는다
- 묻기 전에 무엇을 왜 묻는지와 선택지마다 무엇이 달라지는지를 먼저 설명한다. 판정 지적 번호·규칙·위치·문제 설명을 함께 보여 준다
- 선택지마다 '답을 모름(나중에)'을 둔다. 이 답을 고른 물음과 대답하지 않은 물음은 수정 요청서 3절에 남긴다
- 정의 문서를 바꾸지 않는 답(SPC-02 '의도한 것', 구조 추가 '더하지 않음', 사람이 더한 요소·이은 매핑을 '그대로 둠')도 수정 요청서 3절에 답과 함께 남긴다. 파일에 남겨 두어야 다음 호출이 같은 것을 다시 묻지 않는다(5장)
- CQS-01·02의 선택지는 '구조를 더함'·'필수 CQ에서 뺌'·'답을 모름(나중에)'이다. '구조를 더함'에는 더할 구조를 함께 적는다. 이 답이 곧 더할 구조의 확인이다. '필수 CQ에서 뺌'을 고르면 입력 변경 필요로 옮겨 수정 요청서 4절에 적는다
- 개념·관계를 더하거나 빼는 수정은 다시 연 ⑥ 위층에서 확인받는다. 더할 개념(이름, 근거 CQ)과 관계(출발 → 도착, 조인 속성, 근거 CQ)를 보여 주고 '이대로 더함'·'더하지 않음'·'답을 모름(나중에)'을 둔다. '더하지 않음'이면 고치지 않고 수정 요청서 3절에 답과 함께 남기며 결과 보고에도 적는다
- 개념·관계를 더하지 않는 스킬 수정(서식·설명·매핑을 고치거나 쓰는 CQ가 없는 요소를 지우는 것)은 묻지 않는다

묻기 전에 보여 주는 설명은 이런 꼴이다. "Warning도 고쳐"로 부른 경우라 Warning인 DOC-08도 묻는다. 기본 호출이면 Warning-2는 묻지 않는다.

```
판정 지적 가운데 정해 주셔야 고칠 수 있는 것이 2건 있습니다.
답을 모두 받은 뒤 2차 초안을 고칩니다.

  1차 판정 Error-3   CQS-01   CQ-54   필수 CQ에 답할 경로가 없음
    1) 구조를 더함        개념 교육이수(CQ-54), 관계 교육이수 → 사원, 조인 사원번호(CQ-54)
                         원천 근거: hr.TB_교육수강내역(원천 구조 문서 해당 절). 근거가 없으면 이 선택지는 보이지 않음
    2) 필수 CQ에서 뺌      CQ 문서를 고쳐야 함. 수정 요청서에 적고 스킬은 고치지 않음
    3) 답을 모름(나중에)   수정 요청서에 남김

  1차 판정 Warning-2   DOC-08   데이터 구조 'hr.TB_교육수강'   원천 구조 문서에 없는 이름
    1) 원천 이름으로 고침   원천의 'hr.TB_교육수강내역'으로 바꾸고 매핑 제목도 함께 바꿈
    2) 매핑 테이블로 둠    기존 데이터로 만들 수 있을 때만. 설명에 MT 번호와 아직 없다는 표기를 넣음. 설계 리포트 7.1절에 오름
    3) 구조를 지움        그 구조와 구조를 쓰는 매핑을 지움. 쓰던 CQ는 검증 리포트 5.2절에 오름
    4) 답을 모름(나중에)   수정 요청서에 남김
```

**사전 지시로 '확인 없이 이어 가라'고 했으면 ⑥과 같게 한다.** 사전 지시는 호출 글·멈춤 답·입력 목록 파일의 사전 지시 칸(`run_directives`)에 적힌 것만 따른다. 개념·관계를 더하는 수정은 더할 구조를 보여 주고 반영한다. 결정 필요는 물을 수 없으므로 수정 요청서에 남긴다.

**사용자에게 물을 수 없는 환경**(평가 실행처럼 묻지 말라는 지시를 받은 실행)에서도 다시 연 ⑥은 답을 기다린다. 답 파일(`--answers`)이나 사전 지시가 있을 때만 ⑦로 간다. 정비만 하는 차수는 결정 필요를 수정 요청서 3절에 남기고 나머지 정비는 고친다.

- 다시 연 ⑥에도 사전 지시·`--answers`를 1차 ⑥과 같은 규칙으로 적용한다. 다만 위층(개념·관계 더함·뺌, 답 없는 결정 필요)은 사전 지시로 건너뛰지 못한다. 답 파일에 위층 답이 없으면 기다린다

## 5. 수정 요청서

수정 요청서는 판정 지적의 남은 일과 판정 뒤 설계 변경을 함께 모으는 자리다. 행 종류는 판정 지적·사람 요청·CQ 변경 셋이고, 칸은 아래 '칸마다 이렇게 적는다'에 있다.

- 자리는 N차 설계 리포트·정의 문서 밖이다. N차 파일에 적으면 판정 뒤에 N차 파일을 고치게 된다
- 받을 때는 요지만 적는다. 무엇을 어떻게 바꿀지의 확인은 다시 연 ⑥에서 한다
- 모으는 꼴(칸)과 적어 두기 호출(2장)은 스킬이 정한다. 요청서를 어디에 보관하고 어떤 화면으로 보일지는 스킬을 부르는 쪽이 정한다

**답을 받지 못한 결정 필요, 입력 변경 필요, 정의 문서를 바꾸지 않는 답, 상태가 '적용'·'적용 안 됨(대상이 사라짐)'이 아닌 6절 「사람 요청과 CQ 변경」 행(출처와 상관없이) 가운데 하나라도 있거나 적어 두기 호출이면 만든다.** 새로 물을 결정 필요·입력 변경 필요는 수정 범위(2장) 안에서만 센다. 앞 요청서에서 답을 받은 행은 범위와 상관없이 옮기고 센다. 모두 없으면 새로 만들지 않는다. 다만 같은 이름의 요청서가 이미 있으면 남은 것이 없어도 이번 결과로 다시 쓴다(아래). 확인받지 못한 구조 추가(4장)도 결정 필요로 센다.

- 적어 두기 호출을 받았는데 요청서가 없으면(1차 판정 뒤처럼 `--fix`가 아직 돌지 않음) 뼈대([`../assets/fix-request-skeleton.md`](../assets/fix-request-skeleton.md))를 복사해 `-N차` 요청서를 새로 만든다. N은 읽은 판정의 차수다
- 같은 이름의 요청서를 다시 쓰기 전에 앞 판을 작업 파일 사본으로 남긴다. 옮김 누락 검사(`scripts/check_design_report.py <N+1차 설계 리포트> --stage 검증뒤 --definition <N+1차 정의 문서> --fix-request <N차 요청서> <N+1차 요청서>`)는 그 사본과 새 판의 6절에서 옮겨야 할 행(출처와 상관없이 상태가 '적용'·'적용 안 됨'이 아닌 행)을 맞댄다. 앞 요청서(N차나 같은 이름의 앞 판 사본)가 없으면 옮길 행이 없으므로 이 검사를 부르지 않는다
- 파일 이름은 `<이름>-온톨로지-수정-요청-N차.md`다. N은 이 요청서를 만들 때 읽은 판정의 차수다. 1차 판정을 읽었어도 `-1차`를 붙인다. 짝이 되는 판정의 차수를 이름에서 바로 읽기 위함이다. 폴더는 판정과 같은 폴더다
- 3절에는 답을 받지 못한 결정 필요와, 정의 문서를 바꾸지 않는 답을 받은 결정 필요가 함께 있다. 뒤의 행은 답 칸에 그 답이 적혀 있다. 2절 '결정 필요'는 둘을 합한 3절 행 수 n이고, 답 칸이 채워진 행이 있으면 그 수 m을 붙여 `n건(답 있음 m건)`으로 적는다. 2절만 읽고도 아직 정할 것이 몇 건인지 알게 하기 위함이다
- 요청서 N차의 5절은 늘 정의 문서 초안 N+1차에 N+1차로 적은 기록 줄과 1:1이다. 예외는 검증이 종료 코드 2(입력 쪽 멈춤)나 3(스킬 쪽 실패)으로 멈춘 호출 하나다. 그 호출은 요청서를 쓰지 않아 앞 요청서가 다음 호출까지 남는다(7장)
- 같은 이름의 요청서가 이미 있으면(고친 것 없이 끝난 앞 호출이 남긴 요청서) 남은 것이 없어도 이번 결과로 다시 쓴다. 지우지 않는다. 그대로 두면 이미 고친 항목이 3절에 답할 일로 남고, 5절이 초안의 기록 줄과 맞지 않는다. 앞 요청서의 답은 그 전에 읽어 반영했다(7장 차례 4)
- 다시 쓰면 앞 요청서에 사용자가 적은 답은 이렇게 남는다. 그 답대로 고친 항목은 5절과 기록 줄의 고친 내용이 '사용자 답에 따라'로 시작하고(6장), '필수 CQ에서 뺌'은 4절 행으로, 정의 문서를 바꾸지 않는 답('의도한 것'·'더하지 않음'·'그대로 둠')은 3절 행의 답 칸으로 남는다. SPC-02의 '의도한 것'은 검증을 수행했으면 검증 리포트 `※ No.2 Warning 확인:` 주석에도 `(사용자 답)` 표시와 함께 남는다
- 앞 요청서 3절에서 정의 문서를 바꾸지 않는 답을 받은 행은, 그 지적이 판정 N차(검증을 수행했으면 N+1차)에 남아 있으면 수정 범위와 상관없이 새 요청서 3절에 답과 함께 옮긴다. 판정 지적 번호는 새 요청서의 대상 판정 번호로 고친다. 차수가 바뀌거나 "Warning도 고쳐" 호출 뒤에 기본 호출이 끼어도 같은 것을 다시 묻지 않기 위함이다
- 6절 표의 행은 출처와 상관없이 위 옮기기 규칙의 예외다. 상태가 '적용'·'적용 안 됨(대상이 사라짐)'이 될 때까지 차수를 넘어 새 요청서로 옮기고, No.는 앞 요청서의 번호를 이어 매기며 행을 지우지 않는다. 출처가 판정 지적인 행이 새 판정에서 풀렸으면 옮기되 상태를 '적용'으로 바꾸고 반영 칸에 풀린 차수를 적는다
- 뼈대는 [`../assets/fix-request-skeleton.md`](../assets/fix-request-skeleton.md)에 있다. 그 파일을 복사해 자리표시만 채운다. 문서의 꼴과 문체는 [`report-conventions.md`](report-conventions.md)를 따른다
- 판정과 겹치는 내용(위치·문제)을 줄이지 않는다. 받는 사람이 요청서만 펴고도 답할 수 있어야 한다
- 검증을 수행했으면 남은 판정 지적 행(3·4·5절)을 새 판정(N+1차)의 지적과 지적 식별자([`report-conventions.md`](report-conventions.md) 7장)로 맞대 본다. 짝이 없는 항목(이번 수정으로 함께 풀린 지적)은 요청서에 적지 않고 결과 보고에 적는다. 6절 행은 맞대지 않고 위 예외대로 옮긴다

**칸마다 이렇게 적는다.**

| 절 | 칸 | 적을 것 |
|---|---|---|
| 문서 정보 표 | 차수 | 읽은 판정의 차수. 파일 이름의 차수와 같음 |
| 문서 정보 표 | 대상 판정 | 읽은 판정 경로 |
| 문서 정보 표 | 정의 문서 초안 | 다음 차수 정의 문서 경로. 고친 것이 없어도 초안이 있으면 그 경로. 확정 가능 판정이라 초안을 만들지 않았으면 '해당 없음' |
| 2절 | 수정 범위 | 기본은 `Error`. "Warning도 고쳐"로 불렀으면 `Error·Warning` |
| 2절 | 스킬 수정 · 결정 필요 · 입력 변경 필요 | 5절·3절·4절 표의 행 수를 `n건`으로 적음. 0건이면 '해당 없음'. 결정 필요는 답 칸이 채워진 3절 행이 있으면 `n건(답 있음 m건)` |
| 2절 | 사람 요청 · CQ 변경 · 판정 지적 대기 | 6절 표에서 출처가 '사람 요청'인 행 수, 'CQ 변경(CQ 번호)'인 행 수, 판정 지적('판정 N차 Error-k(규칙)'·'판정 N차 Warning-k(규칙)')인 행 수를 각각 `n건`으로 적음. 0건이면 '해당 없음' |
| 3·4·5절 | 판정 지적 번호 | 읽은 판정의 지적 번호(Error-n·Warning-n). 사람이 판정을 펴 볼 때 쓰는 번호 |
| 3·4절 | 규칙 · 위치 | 읽은 판정 요약표의 규칙 번호와 위치를 그대로 옮김. 스킬이 답을 지적에 맞댈 때 쓰는 값 |
| 3절 | 정할 것 | 무엇을 정해야 하는지 한 문장 |
| 3절 | 선택지 | `1) …`, `2) …`처럼 번호를 붙여 한 칸에 이어 적음. '답을 모름'은 넣지 않음(답 칸을 비우면 됨). 구조를 더하는 선택지에는 더할 개념·관계를 적음 |
| 3절 | 선택지별 영향 | 선택지 번호마다 정의 문서와 판정에서 무엇이 달라지는지 |
| 3절 | 답 | 답을 받지 못했으면 비워 둠. 사람이 선택지 번호나 짧은 글로 채움. 정의 문서를 바꾸지 않는 답을 받았으면 스킬이 그 선택지를 '2) 의도한 것'처럼 번호와 이름으로 적음 |
| 4절 | 바꿀 입력 | CQ 문서, 원천 구조 문서, 참고 문서(문서 이름), 스타일 가이드, 서식 가이드 가운데 무엇인지. 작성자가 어느 쪽을 고칠지 정해야 하면 둘 다 |
| 4절 | 바꿀 내용 | 무엇을 어떻게 바꾸면 이 지적이 풀리는지 |
| 4절 | 바꾼 뒤 부르는 법 | CQ 문서를 바꾸면 `--fix`(바뀐 CQ는 CQ 변경 행으로 받음). 그 밖의 입력을 바꾸면 새 폴더로 재생성. 바꿀 입력이 둘이면 입력마다 적음 |
| 5절 | 위치 · 고친 내용 | 정의 문서 초안의 `## 스킬 수정 기록`에 이번 차수로 적은 줄의 요소와 고친 내용을 글자 그대로 옮김(6장). 행은 기록 줄과 1:1 |
| 사람 요청 행 | No.·출처 | 1부터 이어 매기고 지우지 않음. 반영 차례는 No. 차례. 출처는 '판정 N차 Error-k(규칙)'·'판정 N차 Warning-k(규칙)'·'사람 요청'·'CQ 변경(CQ 번호)' 가운데 하나 |
| 사람 요청 행 | 기준 | 항목을 올릴 때 본 설계 리포트의 차수와 해시 앞 12자. 답 봉투의 `design_report_sha12`와 같은 셈 |
| 사람 요청 행 | 대상 키 | CQ 번호·개념 이름·관계(이름, 출발 → 도착)·원천 '테이블.컬럼'. 정하지 못하면 '해석 필요' |
| 사람 요청 행 | 바꿀 내용 | 더함·뺌·이름 바꿈·관계 방향·조인 속성·구조 꼴·원천 선택 가운데 무엇을 어떻게. 사람 말은 요지만 |
| 사람 요청 행 | 성격 · 갈래 · 답 | 3장의 성격과 갈래, 결정 필요의 답. 답이 비면 다시 연 ⑥ 위층에서 물음 |
| 사람 요청 행 | 상태 | 대기·해석 필요·결정 대기·입력 변경 필요·적용·적용 안 됨(대상이 사라짐)·보류(다음 차수로) 가운데 하나 |
| 사람 요청 행 | 근거 | 사람이 밝힌 까닭. 없으면 '사람 요청(까닭 미기재)'. 스킬이 짐작해 채우지 않음 |
| 사람 요청 행 | 반영 | 반영한 차수와 설계 리포트 12절 No. 반영한 항목 하나가 N+1차 12절 행 하나 |

- 3·4·5·6절 표가 0건이면 절 첫머리 설명도 표도 없이 '해당 없음' 한 줄만 둔다
- 7절(후속 조치)에는 아래 줄 가운데 조건에 맞는 것만 이 차례로 둔다. 맞는 줄이 하나도 없으면 `- 해당 없음` 한 줄을 둔다. "Warning도 고쳐"로 불러 SPC-02에 '의도한 것'만 답해 고친 것이 없는 호출이 그렇다

| 조건 | 7절에 두는 줄 |
|---|---|
| 3절에 답 칸이 빈 행이 있고, 그 가운데 판정 지적 번호가 `Warning-n`인 행은 없음 | 3절 '답' 칸 기재 후 `--fix`로 수정 재수행 필요 |
| 3절에 판정 지적 번호가 `Warning-n`이고 답 칸이 빈 행이 하나라도 있음 | 3절 '답' 칸 기재 후 `--fix`에 "Warning도 고쳐"를 붙여 수정 재수행 필요 |
| 4절에 행이 있음 | 4절 입력 문서 변경 후 '바꾼 뒤 부르는 법' 칸대로 재수행 필요 |
| 검증을 수행함 | 고친 결과는 (다음 차수 구조 판정 경로) 6절(앞 판정 대조)에서 확인 필요 |
| 수정 범위가 Error이고 Warning 가운데 스킬 수정 갈래가 있음 | Warning 가운데 스킬 수정 대상 n건은 Warning까지 수정 요청 시 처리함 |

- 표의 첫 두 행은 둘 가운데 하나만 둔다. 답 칸이 빈 Warning 행이 있으면 "Warning도 고쳐"를 붙이라고 적는 까닭: 이어진 판정이 확정 가능이고 남은 결정 필요가 Warning이면, 기본 `--fix`는 고칠 Error가 없어 초안 없이 끝나고 적은 답이 반영되지 않는다(2장). 답이 채워진 Warning 행(앞 요청서에서 옮긴 '의도한 것' 같은 답)은 이미 반영된 답이라 다음 호출이 할 일이 없으므로 따지지 않는다

**답은 이렇게 읽는다.**

- 판정 N차에 `--fix`를 부르면 수정 요청서 N차가 있으면 그것을, 없으면 N-1차를 읽는다. 요청서 N차는 앞 호출이 고친 것 없이 끝나 검증을 건너뛰었을 때 생긴다. 그보다 앞 차수의 요청서는 읽지 않는다. 그 사이에 판정이 여러 번 바뀌어 답이 지금 지적과 맞지 않을 수 있다
- 3절 '답' 칸만 읽는다. 사람이 다른 칸을 고쳤어도 읽지 않는다
- 답을 지적에 맞댈 때 판정 지적 번호는 쓰지 않는다. 번호는 판정마다 새로 매겨진다. 요청서의 규칙과 위치로 지적 식별자를 만들어 판정 N차의 지적에 맞댄다. 식별자에 외부 코드가 드는 규칙(SPC-02)은 요청서의 대상 판정에서 그 지적 번호의 외부 코드를 가져와 더한다
- 짝이 없으면(이미 풀린 지적) 답을 쓰지 않고 결과 보고에 적는다
- 정의 문서를 바꾸지 않는 답은 고치지 않고 다시 묻지 않는다. 그 지적이 남아 있으면 새 요청서 3절에 답과 함께 옮긴다
- 답을 읽을 수 없으면(선택지에 없는 번호, 두 뜻으로 읽히는 글) 쓰지 않고 다시 묻는다. 답 칸이 빈 항목도 다시 묻는다
- '구조를 더함'으로 답했으면 그 행의 선택지 칸에 적은 구조를 더한다. 지금 초안에 이미 있는 것은 다시 더하지 않는다

## 6. 스킬 수정 기록

**스킬이 고친 목록은 두 곳에 남긴다.** 정의 문서 초안 맨 끝의 `## 스킬 수정 기록` 절과, 수정 요청서를 만들면 그 5절이다. 초안에 남기는 까닭은 둘이다. 검증만 모드가 이 절로 스킬이 고친 것과 사람이 고친 것을 가른다([`verification-procedure.md`](verification-procedure.md) 5.6). 검증이 멈춰 다시 부를 때도 기록이 파일에 있으므로 같은 수정을 다시 얹지 않는다.

- 이 절은 정비를 적는 자리다. 설계 리포트 2절 '스킬 수정' 줄과 짝이다
- 설계 수정 차수(7.1)에서 설계 변경으로 바뀐 요소의 블록은 이 절에 기록 줄을 남기지 않는다. 그 요소는 N+1차 설계 리포트 12절 이번 차수 행에 적히고, 앞 글 유지 확인 스크립트(`scripts/compare_definitions.py`)는 그 행에 이름이 있는 블록을 기록 없는 블록 변경으로 짚지 않는다
- 설계 리포트 12절 이번 차수 행에 이름이 없는 블록을 함께 고쳤으면(7.3 연쇄 대상 등) 이 절에 기록 줄을 적는다
- 네 절이 아닌 `##` 절이라 변환할 때 읽히지 않고 변환 결과가 바뀌지 않는다. 수집 조건의 정의 문서 해시에는 들어간다
- 절은 정의 문서 맨 끝에 둔다. 이미 있으면 그 절 끝에 줄을 더한다. 이번에 고친 것이 없으면 절을 새로 만들지 않는다
- `###` 제목과 표를 쓰지 않고 한 줄에 한 건을 적는다
- 줄의 꼴은 `- N차 · 규칙 · 요소 · 판정 지적 번호 · 고친 내용`이다. 칸은 ' · '(앞뒤를 띄운 가운뎃점)으로 나눈다

| 칸 | 적을 것 |
|---|---|
| N차 | 이 기록을 적은 초안의 차수. 2차 초안이면 `2차` |
| 규칙 | 규칙 번호 |
| 요소 | 위치 꼴([`report-conventions.md`](report-conventions.md) 7장)에서 줄 번호를 뺀 것. 고치면 줄이 밀리므로 줄 번호를 적지 않음. 요소를 이름으로 가리킬 수 없는 '정의 문서 n줄' 꼴만 읽은 판정의 위치를 그대로 둠(줄 번호를 빼면 가리킬 것이 남지 않음). 그 줄 번호는 판정 N차가 가리킨 N차 정의 문서의 줄이고 초안의 줄이 아님 |
| 판정 지적 번호 | 고칠 때 읽은 판정의 지적 번호(Error-n·Warning-n) |
| 고친 내용 | 무엇을 어떻게 고쳤는지 말로 적음 |

- 지적 하나와 요소 하나가 한 줄이다. 한 지적을 풀려고 요소 여럿을 바꿨으면 요소마다 한 줄을 적고 같은 지적 번호를 쓴다. 지웠으면 지운 요소를 적는다
- 결정 필요를 사용자 답대로 고쳤으면 고친 내용을 '사용자 답에 따라'로 시작한다. 그 자리에서 받은 답이든 요청서 답이든 같다. 요청서를 다시 쓰거나 판정이 바뀌어도 사람이 정한 수정인지 이 줄에서 가린다
- 고친 내용에 고치기 전 문구를 옮기지 않는다. 정의 문서 검사기는 DOC-02(조사 괄호 잔존)를 문서의 모든 줄에서 찾는다. 옛 문구 `사원이(가)`를 옮기면 기록 줄이 다시 Error로 잡힌다. '조사 괄호를 받침에 맞게 고침'처럼 적는다. 이름을 바꿨으면 앞 이름만 '앞 이름 …'으로, 매핑 컬럼을 바꿨으면 앞 컬럼만 '앞 컬럼 …'으로 적는다
- 다음 차수 초안은 이번 차수 정의 문서를 바이트 그대로 복사하므로 기록 절도 그대로 옮겨진다. 앞 차수 표시가 붙은 줄은 이력으로 남는다. 검증만 모드는 이번 차수 표시가 붙은 줄만 읽으므로 섞이지 않는다

```markdown
## 스킬 수정 기록

- 2차 · DOC-02 · 개념 '휴가신청' · Error-1 · 설명의 조사 괄호를 받침에 맞게 고침
- 2차 · MAP-01 · 매핑 '휴가신청 ← hr.TB_휴가신청내역' › 속성 '휴가 종류' · Error-2 · 뜻이 같은 원천 컬럼이 없어 매핑과 속성을 지움(쓰던 CQ는 검증 리포트 5.2절)
- 2차 · MAP-01 · 매핑 '휴가신청 ← hr.TB_휴가신청내역' › 속성 '신청자 이름' · Error-4 · 뜻이 같은 원천 컬럼 '신청자명'으로 바꿈(앞 컬럼 '신청자번호')
- 2차 · CQS-01 · 개념 '교육이수' · Error-3 · 사용자 답에 따라 CQ-54에 답할 개념을 더함
- 2차 · CQS-01 · 관계 '교육이수의 사원'(교육이수 → 사원) · Error-3 · 사용자 답에 따라 CQ-54에 답할 관계를 더함
```

## 7. 처리 흐름

부를 때마다 차수 갈래 하나를 고른다. 설계 변경 성격(3장)인 판정 지적·대기 행이 1건 이상이거나 CQ 변경 행이 1건 이상이면 설계 수정 차수(7.1), 0건이면 정비만 하는 차수(7.2), 사람 요청만 받고 반영을 청하지 않았으면 적어 두기(2장)다. 한 차수에는 한 길만 쓴다. 판정 뒤 쓰기는 모두 N+1차 이름 파일과 수정 요청서에만 하고 N차 파일은 고치지 않는다.

### 7.1 설계 수정 차수

| 차례 | 할 일 | 나오는 것 |
|---|---|---|
| 1 | 판정 N차(가장 높은 차수)와 그 짝(정의 문서·설계 리포트·검증 리포트 N차), 수정 요청서 N차나 N-1차의 대기 행, CQ 문서 해시를 읽는다. N+1차 정의 문서가 이미 있으면 여기서 멈춘다(차례 3 관문 1 `check_definition_absent`와 같은 조건. 사람이 지우거나 `--verify`로 받은 뒤 다시 부른다) | 입력 목록 |
| 2 | 대기 행과 판정 지적을 No. 차례로 정리한다. 대상 키를 N차 설계 리포트에 맞대고, 앞 항목이 바꾼 이름은 이름 대응표로 따라간다. 기준 해시가 N차 설계 리포트와 다르면 대상을 다시 맞대고, 찾지 못하면 상태를 '적용 안 됨(대상이 사라짐)'으로 둔다. 같은 대상에 어긋나는 두 항목은 결정 필요로 올린다. 함께 맞출 연쇄 대상(7.3 첫 줄)을 항목 밑에 적는다 | 항목 목록 |
| 3 | N차 설계 리포트를 N+1차로 복사하고 리포트 판을 '설계 단계', 2절 '설계안 확인'을 '확인 대기'로 되돌린다. 바뀐 요소의 7.2·10절 행과 5.1절 대표 표시 속성은 '정의 문서 작성 뒤 기재'로 둔다. 개념·관계 더하기·빼기가 아닌 스킬 수정만 미리 반영하고, 그 요소를 정한 단계(③~⑤, 원천 선택이면 ②-2)의 규칙으로 설계 절을 고치며 근거를 그 자리에 적는다. 12절에 행을 더하고 ⑥ 출력 앞 검사(관문 1)를 통과시킨다 | 설계 리포트 N+1차(설계 단계 판) |
| 4 | ⑥을 다시 연다. 이번 차수에 바뀐 것(적용·적용 안 됨·결정 대기·연쇄 건수)과 앞 판과의 차이를 보이고 답을 기다린다. 개념·관계 더하기·빼기와 답이 없는 결정 필요는 위층에서 정한다(4장). 입력 변경 필요는 반영하지 않고 알린다 | 확인된 설계 리포트 N+1차 |
| 5 | ⑦~⑨를 수행한다. 정의 문서는 부분 수정이다(아래). 바탕 파일은 N차 정의 문서 사본이다 | 정의 문서·검증 리포트·구조 판정 N+1차 |
| 6 | 수정 요청서 행의 상태·반영 칸을 고친다. 5장 조건에 맞으면 수정 요청서 N차를 쓴다. 결과를 보고한다(8장) | 수정 요청서 N차, 사용자 알림 |

- 차례 5의 정의 문서는 부분 수정이다. N차 정의 문서를 N+1차로 복사해 바탕으로 쓰고(N+1차 정의 문서가 이미 있으면 차례 1에서 멈추므로 여기 오지 않는다), 바뀐 설계 요소와 그 연쇄 대상 블록(7.3 첫 줄)만 고친다. 앞 차수 글을 옮기는 요소에 걸린 정비 지적은 ⑧에서 그 블록을 고친다
- ⑨ 걸음 2 앞(정의 문서 규모 표를 확인하는 자리)에서 앞 글 유지 확인 스크립트(`scripts/compare_definitions.py <N차 정의 문서> <N+1차 정의 문서> --design-report <N+1차 설계 리포트> --round <N+1>`)를 돌린다. 이 스크립트는 N차·N+1차 정의 문서를 개념·속성 표·관계·매핑 블록 단위로 비교해 기록 줄 없이 바뀐 블록, 이름 대응표의 옛 이름이 본문·매핑 제목·경고문·`[SQL]` 줄에 남은 자리, 지운 요소를 가리키는 관계·매핑 행을 지적한다. 설계 리포트 N+1차 2절 `※ 외부 수정 n:` 줄이 가리키는 블록은 기록이 있는 것으로 본다. 지적이 있으면 ⑧로 돌아가 고친 뒤 한 번 다시 돌린다. 다시 돌려도 지적이 있으면 더 되풀이하지 않고 지적을 사람에게 보이고 멈춘다. 스크립트는 지적이 있으면 종료 코드 1, 입력 쪽 문제(파일 없음·UTF-8 아님·개념 없음)면 2, 처리하지 못한 예외면 3, 표준 출력을 쓰지 못하면 4로 끝난다
- ⑨는 1차 규칙대로 하되 설계 리포트 12절 '사람 수정' 요소는 고치지 않고 판정에 남긴다. 판정 스크립트에는 `--design-report <설계 리포트 N+1차>`와 `--previous <앞 차수 구조 판정>`을 주어 앞 판정과 대조한다
- 설계 변경 항목이 0건이면 정비만 하는 차수로 간다(7.2). 정비 중에 설계 칸을 바꿔야 할 것이 드러나면 고치지 않고 수정 요청서에 대기 행으로 올린다
- 한 번 부르면 한 차수만 돈다. 새 판정이 다시 확정 불가여도 스스로 되풀이하지 않는다. 적어 두기 호출은 차수를 돌리지 않는다(2장)

### 7.2 정비만 하는 차수

| 차례 | 할 일 | 나오는 것 |
|---|---|---|
| 1 | 판정 N차(가장 높은 차수)와 그 짝(정의 문서·설계 리포트·검증 리포트 N차)을 찾는다. 입력 문서를 모으고 멈춤 조건을 확인한다([`verification-procedure.md`](verification-procedure.md) 5.2·5.4). 수정 요청서 N차나 N-1차가 있으면 읽는다(5장) | 입력 목록 |
| 2 | 사람이 복사해 둔 다음 차수 초안(정의 문서 N+1차)이 있는지 확인한다. 있으면 설계를 바꾸는 외부 수정이 없는지 `scripts/check_design_report.py --stage 검증뒤 --external`로 가린 뒤(1장) 그 파일을 작업본으로 쓴다. 없으면 N차 정의 문서를 바이트 그대로 복사해 만든다. 다만 판정 N차가 확정 가능이면 차례 5에서 고칠 것이 1건 이상일 때만 만든다 | 작업본 |
| 3 | 판정 3.1(기본) 또는 3.1·3.2(범위 'Warning 포함')의 정비 지적과 결정 필요를 세 갈래로 나눈다(3장) | 갈래 목록 |
| 4 | 수정 요청서의 답과, N차 검증 리포트의 `※ No.2 Warning 확인:` 주석 가운데 `(사용자 답)` 표시가 붙은 것을 지적에 맞대 먼저 반영한다. 아직 답이 없는 결정 필요와 개념·관계를 더하는 스킬 수정을 한 번에 묻는다(4장) | 답 |
| 5 | 정비와 답을 받은 결정 필요를 작업본에 고친다. 설계 규칙과 참고 문서를 그대로 따른다. `## 스킬 수정 기록`에 줄을 더한다(6장) | 정의 문서 N+1차 |
| 6 | 작업본을 받은 정의 문서로 삼아 검증만 모드를 수행한다([`verification-procedure.md`](verification-procedure.md) 5.6). 작업본이 N차 정의 문서와 바이트까지 같으면(고친 것이 없음) 검증을 건너뛴다. 초안을 만들지 않았으면 검증도 하지 않는다 | 설계 리포트·검증 리포트·구조 판정 N+1차 |
| 7 | 답을 받지 못한 결정 필요, 입력 변경 필요, 정의 문서를 바꾸지 않는 답, 상태가 '적용'·'적용 안 됨(대상이 사라짐)'이 아닌 6절 「사람 요청과 CQ 변경」 행(출처와 상관없이) 가운데 하나라도 있으면(5장 조건) 수정 요청서 N차를 쓴다. 요청서 N차가 이미 있으면 남은 것이 없어도 다시 쓴다(5장) | 수정 요청서 N차 |
| 8 | 결과를 보고한다(8장) | 사용자 알림 |

- 차례 2의 초안은 사람이 N차 정의 문서를 복사해 정비만 고쳐 둔 것이거나 멈춘 수정이 남긴 것이다. 판정은 초안을 만들지 않는다([`verification-procedure.md`](verification-procedure.md) 4장). 덮어쓰지 않고 그 위에서 고친다. 사람이 고친 요소는 검증만 모드가 외부 수정으로 적는다
- 판정 N차가 확정 가능이면 초안 N+1차가 없는 것이 정상이다(확정 가능 판정에는 다음 차수 초안을 두지 않음). 차례 5에서 고칠 것이 생겼을 때만 N차 정의 문서를 복사해 만든다. 고칠 것이 없으면 초안도 검증도 없이 결과 보고로 끝낸다. 남길 답이 있으면 수정 요청서는 5장대로 쓰고 '정의 문서 초안' 칸은 '해당 없음'이다
- 차례 3에서 작업본의 기록 절에 N+1차 줄로 이미 적힌 지적(멈춘 수정이 고친 것)은 다시 고치지 않는다. 그 기록 줄의 판정 지적 번호는 지금 읽는 판정 N차의 번호이므로 번호로 맞댄다
- 차례 6의 검증만 모드는 정의 문서를 더 고치지 않는다. 수정은 차례 5에서 끝났다
- 차례 6에서 검증을 건너뛰는 것은 같은 정의 문서로 N+1차 판정을 만들면 N차와 같은 판정이 한 벌 더 생기기 때문이다. 건너뛰어도 초안은 만들어 둔 그대로 둔다. 사람이 초안을 고쳐 두었거나 멈춘 수정이 고친 것이 있으면 바이트가 달라 검증을 수행한다
- 차례 6에서 수집·판정 스크립트가 종료 코드 2(입력 쪽 멈춤)나 3(스킬 쪽 실패)으로 멈추면 [`verification-procedure.md`](verification-procedure.md) 5.4대로 알리고 멈춘다. 수정 요청서는 쓰지 않는다. 앞 호출이 남긴 요청서 N차가 있으면 그대로 남고, 다시 불러 검증까지 마치면 5장대로 다시 쓴다. 고친 것은 작업본의 기록 절에 남아 있어 다시 부르면 그 위에서 이어 간다

### 7.3 두 차수에 함께 적용하는 것

- 차례 5에서 요소 하나를 고치면 그 요소를 가리키는 다른 줄도 함께 맞춘다. 이름을 바꾼 데이터 구조의 매핑 제목, 지운 개념의 관계와 매핑, 이름을 바꾼 개념을 가리키는 경고문, 매핑 컬럼을 바꾼 속성의 설명에서 옛 컬럼을 가리키던 줄(`[SQL]` 같은 것), 지운 속성을 가리키던 설명·경고문이 그렇다. 함께 고친 요소도 기록 줄을 적는다
- 차례 5에서 확인되지 않은 값은 지어내지 않고 '확인 필요'로 적는다. 규모 표는 고치지 않는다. 검증만 모드가 `--stats`로 갱신한다

## 8. 결과 보고

사용자에게 아래를 [`run-result-format.md`](run-result-format.md)의 공통 차례로 알리고, 같은 내용을 실행 결과 파일에 쓴다. 검증을 수행했으면 [`verification-procedure.md`](verification-procedure.md) 5.9의 항목을 함께 알리고, 겹치는 것은 한 번만 적는다.

1. 차수 갈래: 설계 수정 차수·정비만 하는 차수·적어 두기 가운데 무엇인지. 설계 수정 차수면 N+1차 네 경로(설계 리포트·정의 문서·검증 리포트·구조 판정)를 이번 실행에서 실제로 파일을 쓴 차례대로, 대기열 요약(적용·적용 안 됨·결정 대기·보류 건수)
2. 경고: 판정 뒤 CQ 문서가 바뀜, 사람이 고쳐 둔 초안 위에서 고침, 고친 것이 없어 검증을 건너뜀, 확정 가능 판정이라 초안을 만들지 않음, 검증이 멈춤(까닭), 설계를 바꾸는 외부 수정이 있어 멈춤(사람 요청 행 초안 n건, 외부 수정본 경로). 해당하는 것만
3. 고친 것: 스킬 수정과 답을 받은 결정 필요. 판정 지적 번호, 규칙, 요소, 고친 내용. 이미 풀린 지적이라 쓰지 않은 요청서 답도 함께
4. 남은 것: 수정 범위 안에서 답을 받지 못한 결정 필요와 입력 변경 필요, 정의 문서를 바꾸지 않은 답('의도한 것'·'더하지 않음'·'그대로 둠'. 앞 요청서에서 옮긴 답은 범위와 상관없음), 빠진 CQ라 고치지 않은 지적. 수정 요청서 경로
5. 기본(Error만)으로 불렀으면 Warning 가운데 스킬 수정 갈래의 건수와 "Warning도 고쳐"로 부르면 고친다는 안내
6. 새 판정: 확정 가능 또는 확정 불가, Error·Warning 건수, 앞 판정 대조 건수(해소·유지·신규·기준 변경·확인 불가)
7. CQ 문서가 바뀐 차수면 바뀐 CQ. 뺀 CQ가 있으면 그 CQ의 앞 판정 지적이 대조에서 해소로 셈해졌다는 것. 구조를 고쳐 풀린 것이 아니다([`structure-judgment-format.md`](structure-judgment-format.md) '알려진 한계')
8. 다음에 할 일: 수정 요청서 3절에 답을 적고 `--fix`(3절에 답 칸이 빈 Warning 행이 있으면 범위 'Warning 포함'), 이번 차수 정의 문서를 다음 차수 이름(`<이름>-온톨로지-정의-n차.md`의 n을 하나 올림. 1차 정의 문서는 이름에 차수가 없으므로 `-2차`를 붙임)으로 복사해 정비만 고친 뒤 `--verify <그 경로>`, 설계를 바꾸려면 수정 요청서에 사람 요청 행을 적고 `--fix`, CQ 문서를 바꿨으면 `--fix`(바뀐 CQ는 CQ 변경 행으로 받음), 원천 구조 문서·참고 문서·가이드를 바꿨으면 새 폴더로 재생성, 확정 가능이면 `graphio-ontology-converter`로 변환
