| 항목 | 내용 |
|---|---|
| 문서명 | 그래피오 구조 설계·설명 작성 가이드 |
| 용도 | 온톨로지 빌더가 개념·속성·관계를 생성할 때 참조하는 실행 기준 |
| 적용 대상 | 그래피오에 등록하는 모든 온톨로지 |
| 실행 환경 | 외부 모델과 온프레미스 소형 모델 모두에서 동작해야 한다 |

## 0. 이 가이드를 쓰는 방법

### 0.1 누가 읽는가

이 가이드는 사람과 모델이 함께 읽는다.

| 읽는 쪽 | 하는 일 |
|---|---|
| 온톨로지 빌더 | 개념·속성·관계를 만들 때마다 이 가이드의 규칙과 템플릿을 그대로 따른다 |
| 사람 | 결과를 검토하고 고친다. 규칙이 맞지 않으면 이 가이드를 고친다 |

그래서 규칙은 판단을 요구하지 않는 형태로 쓴다. "적절하게", "필요하면", "가능한 한" 같은 표현을 쓰지 않는다. 대신 조건과 결과를 짝지어 적는다.

### 0.2 왜 설명이 중요한가

그래피오 온톨로지는 설명이 그대로 임베딩되어 검색에 쓰인다. 설명의 품질이 검색 정확도를 직접 좌우한다.

| 대상 | 설명이 하는 일 | 부실하면 |
|---|---|---|
| 개념 | 질의를 어느 개념으로 보낼지 결정한다 | 엉뚱한 개념으로 간다 |
| 속성 | 조회문의 조건절을 만든다 | 개념은 맞는데 조건이 틀린다 |
| 관계 | 조회문의 연결 조건을 만든다 | 연결이 끊긴다 |

### 0.3 한 번에 하나씩 만든다

개념 하나를 만들고 검사한다. 통과하면 다음으로 넘어간다. 여러 개를 한 번에 만들지 않는다.

| 순서 | 하는 일 |
|---|---|
| 0 | 비정형 원천이면 먼저 문서 타입을 선언한다 (4장) |
| 1 | 개념 하나를 만든다 |
| 2 | 5.7의 검사 항목을 확인한다 |
| 3 | 통과하지 못하면 고친다 |
| 4 | 그 개념의 속성을 하나씩 만든다 |
| 5 | 속성마다 6.7의 검사 항목을 확인한다 |
| 6 | 개념이 모두 끝나면 관계를 하나씩 만든다 |
| 7 | 관계마다 7.5의 검사 항목을 확인한다 |

## 1. 절대 규칙

아래 아홉 가지는 예외가 없다. 하나라도 어기면 생성을 멈추고 사람에게 알린다.

| 번호 | 규칙 |
|---|---|
| R-01 | 원천 컬럼명을 개념·속성·관계의 **이름**으로 쓰지 않는다 |
| R-02 | 확인되지 않은 값을 지어내지 않는다. 모르면 `확인 필요`라고 적는다 |
| R-03 | 실제로 존재하는 것이 확인된 테이블과 컬럼만 `[SQL]`에 적는다 |
| R-04 | 한 칸에 여러 값이 담긴 컬럼을 속성으로 만들지 않는다 |
| R-05 | 판정 결과와 집계 결과를 속성으로 만들지 않는다 |
| R-06 | 검증질문이 요구하지 않는 속성을 만들지 않는다 |
| R-07 | 혼동되는 개념 쌍에는 **양쪽 모두**에 경고를 넣는다 |
| R-08 | 설명에 구체적인 데이터 값이나 건수를 예시로 적지 않는다 |
| R-09 | 템플릿의 표기 기호를 바꾸지 않는다. `⚠`, `[SQL]`, `[별칭]`, `[질문예시]`, `\|`를 그대로 쓴다 |

## 2. 이름 짓기

### 2.1 이름과 컬럼은 다른 층이다

| 층 | 무엇인가 | 어디에 적는가 |
|---|---|---|
| 이름 | 사람이 읽는 명칭 | 개념·속성·관계의 이름 칸 |
| 컬럼 | 실제 데이터가 있는 자리 | `[SQL]` 블록과 설명 본문의 괄호 안 |

이름은 사람이 읽는 것이고 컬럼은 데이터를 찾는 것이다. 이름 칸에 컬럼명을 쓰면 둘 다 망가진다.

설명 본문에는 컬럼을 병기한다. 형식은 `이름(원본컬럼)`이다. 조회문을 만들 때 근거가 되기 때문이다.

### 2.2 컬럼명을 그대로 쓸 수 없는 경우

아래 여섯 가지 중 하나라도 해당하면 컬럼명을 이름으로 쓰지 않는다.

| 번호 | 검사 | 예 |
|---|---|---|
| N-01 | 한 단어이고 무엇의 것인지 없다 | 상태, 명칭, 주소, 구분 |
| N-02 | 약어가 들어 있다 | OT대상여부, 평가hr |
| N-03 | 대소문자나 한글·영문이 섞여 있다 | 평가hr, 면담자_평가hr |
| N-04 | 다른 테이블에서 같은 대상을 다르게 부른다 | 명칭과 소속부서명 |
| N-05 | 한 칸에 값이 여럿이다 | 보유자격목록, 참여사원목록 |
| N-06 | 값이 아니라 판정이나 집계다 | 승진 대상 여부, 휴가 사용 일수 합계 |

N-05와 N-06에 걸리면 이름 문제가 아니다. **속성으로 만들면 안 된다.** N-05는 개념 분해가 필요하고, N-06은 구조에 넣지 않는다.

### 2.3 이름 짓는 형식

```
{무엇의} {무엇}
```

앞은 대상을 한정하고 뒤는 값의 종류를 말한다. 뒤만 있으면 대체로 부족하다.

| 값의 종류 | 뒤에 붙이는 말 |
|---|---|
| 시간 | 시점, 기간, 마감 시점 |
| 돈 | 금액, 비용 |
| 비율 | 비율, 율 |
| 참·거짓 | 여부 |
| 분류 | 구분, 방법, 종류, 상태 |
| 식별 | 번호, 식별번호, 코드 |
| 사람 이름 | 담당자, 대표자 |
| 조직 이름 | 부서, 회사 (그 조직을 부르는 말) |
| 긴 글 | 내용, 개요 |
| 인터넷 주소 | 주소 |

### 2.4 이름에 쓰지 않는 말

아래 단어를 단독으로 쓰지 않는다. 무엇을 뜻하는지 드러나지 않는다.

```
정보, 데이터, 값, 항목, 내용, 구분, 여부, 코드, 상태, 목록
```

앞에 한정어가 붙으면 쓸 수 있다. `내용`은 안 되고 `휴가 사유 내용`은 된다.

### 2.5 표기 규칙

| 번호 | 규칙 | 예 |
|---|---|---|
| W-01 | 띄어쓰기를 한다 | 기본급여액 → 기본 급여액 |
| W-02 | 약어를 풀어 쓴다. 원래 약어는 별칭에 넣는다 | OT → 연장 근무 |
| W-03 | 영문 약어가 업무에서 굳어졌으면 대문자로 통일한다 | hr → HR |
| W-04 | 밑줄과 특수문자를 쓰지 않는다 | 면담자_평가hr → 면담 담당 HR |
| W-05 | 같은 대상은 개념이 달라도 같은 이름을 쓴다 | 명칭과 소속부서명 → 부서명 |

### 2.6 바꾸기 예시

| 원천 컬럼 | 걸린 검사 | 이름 |
|---|---|---|
| 상태 | N-01 | 재직 상태 |
| 신청일시 | N-01 | 휴가 신청 시점 |
| 명칭 | N-01, N-04 | 부서명 |
| 기본급여액 | W-01 | 기본 급여액 |
| OT대상여부 | N-02 | 연장 근무 대상 여부 |
| 평가hr | N-02, N-03 | 평가 담당 HR |
| 면담자_평가hr | N-03, W-04 | 면담 담당 HR |
| 번호 | N-01 | 사원번호 |
| 진행구분명 | N-01 | 결재 진행 상태 |
| 자격만료일시 | W-01 | 자격증 만료 시점 |
| 프로필URL | N-02 | 사원 프로필 주소 |
| 보유자격목록 | N-05 | 속성으로 만들지 않는다. 개념으로 분해한다 |
| 참여사원목록 | N-05 | 속성으로 만들지 않는다. 이미 분해된 테이블을 쓴다 |

### 2.7 개념과 관계의 이름

| 대상 | 규칙 | 나쁜 예 | 좋은 예 |
|---|---|---|---|
| 개념 | 무엇의 집합인지 드러나는 명사구. 테이블 이름에 접두어가 붙어 있으면 빼고 짓는다 | TB_휴가신청내역 | 휴가신청 |
| 관계 | 출발이 도착에 대해 무엇을 하는지 드러나는 말. 조인 키 이름을 쓰지 않는다 | 휴가신청번호 | 이어진 휴가사용 |

### 2.8 이름 검사

- [ ] 원천 컬럼명을 그대로 쓰지 않았는가
- [ ] N-01부터 N-06까지 걸리는 것이 없는가
- [ ] 2.4의 금지어를 단독으로 쓰지 않았는가
- [ ] 띄어쓰기를 했는가
- [ ] 같은 대상을 다른 개념에서도 같은 이름으로 부르는가

## 3. 메타타입과 잇는 순서

속성 이름을 의미 있게 지어야 메타타입과 이을 수 있다. 순서를 지킨다.

| 순서 | 하는 일 |
|---|---|
| 1 | 검증질문이 요구하는 값을 확인한다 |
| 2 | 그 값에 2장의 규칙으로 이름을 붙인다 |
| 3 | 이름을 메타타입에 잇는다 |
| 4 | 메타타입을 실제 테이블과 컬럼에 잇는다 |

2번을 건너뛰고 1번에서 4번으로 바로 가면 컬럼 목록을 그대로 옮긴 결과가 된다. 구조는 생기지만 무엇을 뜻하는지 읽히지 않고 검색도 되지 않는다.

## 4. 비정형 문서의 문서 타입

정형 데이터는 원천 스키마에서 메타타입이 바로 만들어진다. 비정형 데이터는 **문서 타입을 먼저 선언**하고 그 모양대로 메타타입이 만들어진다. 만들어진 뒤에는 정형과 동일하게 쓰이므로, 개념·속성·관계의 이름과 설명 규칙은 앞 장들과 같다.

### 4.1 문서 타입이 하는 일

문서 타입은 문서를 가장 잘 검색할 수 있는 프로퍼티를 뽑기 위해 정의한다. 문서 원문을 그대로 담는 것이 아니라 **검색 조건으로 쓸 항목을 골라 구조로 선언**하는 일이다.

### 4.2 기본형 프로퍼티 6종

문서 타입에는 아래 여섯 개가 기본으로 있다. 새로 만들지 않는다.

| 프로퍼티 | 유형 | 담는 것 |
|---|---|---|
| page | INTEGER | 문서 안의 쪽 번호 |
| order | INTEGER | 조각의 순서 |
| embeddings | VECTOR | 임베딩 값 |
| raw_data_id | TEXT | 원본 문서를 가리키는 값 |
| content_id | TEXT | 조각을 가리키는 값 |
| content | TEXT | 조각의 본문 |

본문 전체는 `content`가 받고 임베딩은 `embeddings`가 받는다. 그래서 **사용자 정의 프로퍼티는 검색 조건으로 걸 항목만 만든다.** 본문을 다시 담는 프로퍼티를 만들지 않는다.

### 4.3 사용자 정의 프로퍼티 정하는 규칙

| 번호 | 규칙 |
|---|---|
| T-01 | 검증질문이 조건이나 답으로 쓰는 항목만 만든다 |
| T-02 | 본문 전체나 본문의 큰 덩어리를 담는 프로퍼티를 만들지 않는다. `content`가 받는다 |
| T-03 | 문서마다 값이 하나로 정해지는 항목을 우선한다. 발령 대상 부서, 발령 일자, 시행 기간 같은 것이다 |
| T-04 | 한 문서에 여러 건이 반복되는 항목은 문서 타입을 나눌지 판단한다 |
| T-05 | 표 구조가 여러 단으로 중첩된 값은 추출이 불안정하므로, 그 값에 의존하는 조건을 만들지 않는다 |
| T-06 | 이름은 2장의 규칙을 그대로 따른다. 문서의 항목 제목을 그대로 쓰지 않는다 |

### 4.4 문서 타입을 몇 개로 나누는가

정해진 규칙이 없다. 문서를 보고 판단한다. 아래를 기준으로 삼는다.

| 조건 | 판단 |
|---|---|
| 문서 안의 구획마다 검색 조건이 다르다 | 나눈다 |
| 구획마다 반복 건수가 다르다 | 나눈다 |
| 같은 역할인데 작성 부서마다 이름이 다르다 | 하나로 묶고 원래 이름은 별칭에 넣는다 |
| 구획이 나뉘어 있지만 조건이 같다 | 하나로 둔다 |

### 4.5 임베딩 필드 지정

사용자 정의 프로퍼티를 정의할 때 임베딩 필드를 선택할 수 있다.

| 번호 | 규칙 |
|---|---|
| T-07 | 검색어와 뜻으로 맞춰 볼 항목만 임베딩 대상으로 지정한다 |
| T-08 | 코드, 번호, 날짜, 금액은 임베딩 대상으로 지정하지 않는다. 조건으로 비교할 값이다 |
| T-09 | 기본형 `embeddings`와 중복되지 않게 한다. 본문 전체는 기본형이 받는다 |

### 4.6 설명 쓰는 법

문서 타입에서 만들어진 개념과 속성의 설명은 정형과 같은 형식을 쓴다. 다만 두 가지를 더 적는다.

| 번호 | 규칙 |
|---|---|
| T-10 | 개념 설명의 정의문에 **어느 문서에서 나온 것인지**를 적는다 |
| T-11 | 값이 문서에 없을 수 있으면 그 조건을 적는다. 문서 양식이 작성 부서마다 다르기 때문이다 |

`[SQL]` 줄은 문서 타입에서 만들어진 메타타입을 적는다. 형식은 정형과 같다.

### 4.7 문서 타입 검사

- [ ] 기본형 6종을 다시 만들지 않았는가
- [ ] 사용자 정의 프로퍼티가 모두 검증질문에 쓰이는가
- [ ] 본문을 다시 담는 프로퍼티를 만들지 않았는가
- [ ] 반복되는 항목을 속성에 밀어넣지 않았는가
- [ ] 임베딩 대상에 코드·번호·날짜·금액을 넣지 않았는가
- [ ] 개념 설명에 어느 문서에서 나온 것인지 적었는가
- [ ] 값이 없을 수 있는 조건을 적었는가

## 5. 개념 만들기

### 5.1 무엇을 개념으로 만드는가

| 조건 | 결과 |
|---|---|
| 검증질문의 답에 필요하다 | 개념으로 만든다 |
| 어느 검증질문도 쓰지 않는다 | 만들지 않는다 |
| 한 칸에 여러 값이 담긴 컬럼이 있고, 그 값 하나하나가 답에 필요하다 | 그 값들을 별도 개념으로 분해한다 |
| 판정이나 집계의 결과다 | 만들지 않는다 |

### 5.2 설명 형식

아래 네 줄을 순서대로 쓴다. 줄바꿈과 기호를 그대로 지킨다.

```
{정의문} {보유 항목문} {앵커문}⚠ {경고문}
[SQL] {스키마}.{테이블} | PK: {기본키} | SELECT: {대표 컬럼 5~6개}
[별칭] {별칭1}, {별칭2}, {별칭3}, ...
[질문예시] {질문1} | {질문2} | {질문3}
```

경고문이 없으면 `⚠`와 그 뒤를 통째로 뺀다. `⚠`만 남기지 않는다.

### 5.3 첫 줄 쓰는 법

**정의문.** 이 개념이 무엇을 담는 데이터인지 한 문장으로 쓴다.

```
{개념 이름}은(는) {무엇}을 담는 데이터다.
```

**보유 항목문.** 이 개념이 가진 주요 값을 적는다. 컬럼을 괄호로 병기한다.

```
{이름1}({컬럼1}), {이름2}({컬럼2}), {이름3}({컬럼3})을 가진다.
```

**앵커문.** 어떤 질문의 정답인지 못박는다. 이 문장이 검색의 기준점이다. 반드시 넣는다.

```
'{질문 유형1}', '{질문 유형2}', '{질문 유형3}' 질문의 정답 테이블이다.
```

질문 유형은 검증질문 목록에서 가져온다. 두 개에서 네 개를 적는다.

### 5.4 경고문 쓰는 법

라우팅이 틀리는 가장 큰 원인은 뜻이 가까운 개념을 헷갈리는 것이다.

**언제 넣는가.** 아래 축 중 하나에 해당하는 상대 개념이 있으면 넣는다.

| 축 | 무엇이 다른가 |
|---|---|
| 앞 단계와 뒤 단계 | 확정 전 정보와 확정 후 정보 |
| 정의와 발생 조건 | 무엇인지와 언제 어떻게 일어나는지 |
| 현재 값과 이력 | 지금 값과 바뀌어 온 기록 |
| 기본과 집계·결과 | 원자료와 세어 놓은 값 |
| 기본과 파생·뷰 | 원본과 조건을 걸어 뽑아 놓은 것 |
| 외부 기록과 내부 기록 | 공개 데이터와 자체 기록 |

도메인마다 헷갈리는 쌍이 다르다. 그 쌍은 용어 사전의 구분 목록에서 가져온다.

**형식.**

```
⚠ {이 개념}이(가) 아니라 {상대 개념}을 써야 하는 경우가 있다. {구분 기준}. {어떤 질문}은 {상대 개념}({상대 테이블})을 사용한다.
```

**양쪽에 넣는다.** 한쪽에만 넣으면 반대 방향 질의에서 그대로 틀린다. A에 "B를 쓰라"를 넣었으면 B에도 "A를 쓰라"를 넣는다.

### 5.5 나머지 세 줄 쓰는 법

**`[SQL]` 줄.** 실제로 있는 것만 적는다. 확인되지 않으면 `확인 필요`라고 적고 지어내지 않는다.

```
[SQL] {스키마}.{테이블} | PK: {기본키} | SELECT: {컬럼1}, {컬럼2}, {컬럼3}, {컬럼4}, {컬럼5}
```

`SELECT`에는 그 개념을 찾을 때 쓰는 식별 컬럼과 화면에 보여 줄 컬럼을 넣는다. 다섯에서 여섯 개가 적당하다.

**`[별칭]` 줄.** 사용자가 쓰는 표현을 모두 넣는다. 질의어가 이름과 달라도 잡히게 하는 장치다.

| 넣을 것 | 예 |
|---|---|
| 띄어쓰기 변형 | 휴가신청, 휴가 신청 |
| 줄임말 | 휴가계 |
| 업무에서 쓰는 다른 말 | 연차 신청 |
| 영문 표현 | 있으면 넣는다 |
| 여러 어절로 된 업무 구절 | 휴가 사용 신청 |

**`[질문예시]` 줄.** 이 개념이 정답이어야 할 질문 두세 개를 적는다. 헷갈리는 개념과 경계에 있는 질문을 하나 넣으면 변별에 도움이 된다.

### 5.6 완성 예시

**좋은 예**

```
휴가신청은 사원이 휴가를 쓰기 전에 올려 승인을 기다리는 신청 내용을 담는 데이터다. 신청 사원(신청자번호), 휴가 종류(휴가구분), 휴가 시작 시점(시작일시), 신청 사유 내용(사유)을 가진다. '누가 휴가를 신청했는지', '언제부터 쉬려는지', '승인을 기다리는 신청이 무엇인지' 질문의 정답 테이블이다.⚠ 휴가신청이 아니라 휴가사용을 써야 하는 경우가 있다. 휴가신청은 승인 전 단계이고 휴가사용은 실제로 쓴 기록이다. 실제로 며칠을 쉬었는지 묻는 질문은 휴가사용(hr.TB_휴가사용내역)을 사용한다.
[SQL] hr.TB_휴가신청내역 | PK: 휴가신청번호 | SELECT: 휴가신청번호, 신청자번호, 휴가구분, 시작일시, 종료일시, 결재상태
[별칭] 휴가신청, 휴가 신청, 휴가계, 연차 신청, 휴가 사용 신청
[질문예시] 이번 주에 휴가를 신청한 사원은 누구인가 | 승인을 기다리는 휴가 신청은 무엇인가 | 이 사원이 다음 달에 쉬려는 날은 언제인가
```

**나쁜 예와 이유**

```
휴가신청 정보
[SQL] TB_휴가신청내역
[별칭] 휴가신청
```

| 무엇이 잘못됐나 | 어겨진 규칙 |
|---|---|
| 무엇을 담는지 없다 | 5.3 정의문 |
| 어떤 질문의 정답인지 없다 | 5.3 앵커문 |
| 휴가사용과 구분하는 경고가 없다 | R-07 |
| 스키마와 기본키, 대표 컬럼이 없다 | 5.5 |
| 별칭이 하나뿐이다 | 5.5 |
| 질문예시가 없다 | 5.5 |

### 5.7 개념 검사

- [ ] 어느 검증질문이 이 개념을 쓰는지 말할 수 있는가
- [ ] 첫 줄에 정의문, 보유 항목문, 앵커문이 모두 있는가
- [ ] 앵커문에 "질문의 정답 테이블이다"가 있는가
- [ ] 보유 항목을 `이름(컬럼)` 형식으로 병기했는가
- [ ] 5.4의 축에 해당하는 상대 개념이 있는데 경고를 빠뜨리지 않았는가
- [ ] 경고를 상대 개념 쪽에도 넣었는가
- [ ] 경고에 상대 개념 이름과 테이블을 함께 적었는가
- [ ] `[SQL]`의 테이블·기본키·컬럼이 실제로 있는 것인가
- [ ] `[별칭]`에 세 개 이상을 넣었는가
- [ ] `[질문예시]`에 두 개 이상을 넣었는가
- [ ] 구체적인 데이터 값이나 건수를 적지 않았는가

## 6. 속성 만들기

### 6.1 무엇을 속성으로 만드는가

| 조건 | 결과 |
|---|---|
| 검증질문의 답에 쓰인다 | 속성으로 만든다 |
| 어느 검증질문도 쓰지 않는다 | 만들지 않는다 |
| 한 칸에 값이 여럿이다 | 만들지 않는다. 개념으로 분해한다 |
| 판정이나 집계의 결과다 | 만들지 않는다 |
| 뜻이 같은 컬럼이 여럿이다 | 하나만 고르고 나머지는 만들지 않는다 |

### 6.2 유형 정하기

먼저 유형을 정한다. 유형에 따라 설명에 넣을 것이 다르다.

| 값을 보고 판단 | 유형 |
|---|---|
| 정해진 몇 가지 값 중 하나다 | 코드·상태형 |
| 숫자이고 단위가 있다 | 수치형 |
| 날짜나 시각이다 | 시점형 |
| 참과 거짓 두 가지다 | 여부형 |
| 한 건을 집어내는 번호다 | 식별자형 |
| 사람이나 조직의 이름이다 | 명칭형 |
| 긴 글이다 | 본문형 |
| 인터넷 주소다 | 주소형 |

### 6.3 유형별 형식

**코드·상태형**

```
{무엇}을 나타내는 값({컬럼}). 실제 저장값은 {값1}({뜻1}), {값2}({뜻2}), {값3}({뜻3})이다. 질의의 '{표현1}'은 {값1}로, '{표현2}'는 {값2}로 바꿔 비교한다.
```

**수치형**

```
{무엇}({컬럼}). 단위는 {단위}이고 {자료형}으로 저장된다. '{표현}' 질의는 {변환식}으로 비교한다.
```

**시점형**

```
{무엇}({컬럼}). 형식은 {형식}이다. {주의}
```

**여부형**

```
{무엇}인지 여부({컬럼}). '{값1}'은 {뜻1}, '{값2}'는 {뜻2}다.
```

**식별자형**

```
{무엇}을 식별하는 값({컬럼}). {구성}. {일치 방식}으로 비교한다.
```

**명칭형**

```
{무엇}의 이름({컬럼}). {일치 방식}으로 비교한다.
```

**본문형**

```
{무엇}을 담은 글({컬럼}). {주의}
```

**주소형**

```
{무엇}을 볼 수 있는 주소({컬럼}). {주의}
```

### 6.4 유형별 규칙

| 유형 | 반드시 넣을 것 | 빠뜨리면 생기는 일 |
|---|---|---|
| 코드·상태형 | 실제 저장값, 각 값의 뜻, 한국어 표현을 값으로 바꾸는 규칙 | 조건절에 엉뚱한 값이 들어간다 |
| 수치형 | 단위, 변환식 | 만 원과 원을 혼동해 비교가 틀린다 |
| 시점형 | 저장 형식, 비슷한 시점 컬럼과의 구분 | 다른 시점으로 조회한다 |
| 여부형 | 두 값과 각각의 뜻 | Y와 N을 반대로 해석한다 |
| 식별자형 | 어떻게 구성된 값인지, 정확 일치인지 | 부분 문자열로 잘못 찾는다 |
| 명칭형 | 정확 일치인지 부분 일치인지 | 검색이 안 되거나 과하게 잡힌다 |
| 본문형 | 값이 비는 경우가 있는지 | 없는 값을 있다고 답한다 |
| 주소형 | 무엇으로 이어지는 주소인지 | 다른 문서를 가리킨다 |

추가 규칙 세 가지가 있다.

| 번호 | 규칙 |
|---|---|
| P-01 | 같은 개념 안에 단위나 형식이 다른 컬럼이 있으면 `⚠`로 구분을 적는다 |
| P-02 | 건에 따라 값이 비는 항목은 그 조건을 적는다. 속성을 없애지 않는다 |
| P-03 | 조건으로 쓰이지 않고 화면에만 보여 주는 값은 짧게 쓴다 |

### 6.5 완성 예시

| 속성 이름 | 유형 | 설명 |
|---|---|---|
| 재직 상태 | 코드·상태형 | 사원이 지금 어떤 상태인지 나타내는 값(상태). 실제 저장값은 재직(근무 중), 휴직(일시적으로 근무하지 않음), 퇴직(회사를 떠남)이다. 질의의 '다니는', '근무 중'은 재직으로, '그만둔'은 퇴직으로 바꿔 비교한다. |
| 기본 급여액 | 수치형 | 사원에게 매달 지급하는 기본 급여 금액(기본급여액). 단위는 원이고 정수로 저장된다. '만 원 단위' 질의는 10000을 곱해 비교한다. |
| 휴가 신청 시점 | 시점형 | 휴가 신청이 처음 올라온 시점(신청일시). 형식은 연월일 시분초다. ⚠ 휴가 시작 시점과 다른 시점이므로 섞어 쓰지 않는다. |
| 연장 근무 대상 여부 | 여부형 | 연장 근무 수당을 받는 대상인지 여부(OT대상여부). 'Y'는 대상, 'N'은 비대상이다. |
| 사원번호 | 식별자형 | 사원 한 명을 식별하는 값(번호). 입사 연도와 순번을 붙여 만든 값이다. 정확 일치로 비교한다. |

### 6.6 나쁜 예와 이유

| 설명 | 무엇이 잘못됐나 |
|---|---|
| 상태 | 이름을 그대로 옮겼다. 저장값도 뜻도 없다 |
| 급여 금액이다 | 단위가 없다. 변환식이 없다 |
| 신청한 날짜 | 형식이 없다. 다른 시점 컬럼과 구분이 없다 |
| 연장 근무인지 여부 | 두 값이 무엇인지 없다 |

### 6.7 속성 검사

- [ ] 어느 검증질문이 이 속성을 쓰는지 말할 수 있는가
- [ ] 이름이 2장의 규칙을 지켰는가
- [ ] 유형을 정하고 그 유형의 형식을 썼는가
- [ ] 코드형이면 실제 저장값과 뜻, 변환 규칙을 모두 적었는가
- [ ] 수치형이면 단위와 변환식을 적었는가
- [ ] 시점형이면 형식을 적었는가
- [ ] 같은 개념 안에 헷갈리는 컬럼이 있으면 `⚠`로 구분했는가
- [ ] 값이 비는 경우가 있으면 그 조건을 적었는가
- [ ] 컬럼을 괄호로 병기했는가
- [ ] 확인하지 못한 값을 지어내지 않았는가

## 7. 관계 만들기

### 7.1 언제 만드는가

| 조건 | 결과 |
|---|---|
| 검증질문의 답이 두 개념을 거쳐야 나온다 | 관계를 만든다 |
| 두 개념을 잇는 값이 실제로 있다 | 관계를 만든다 |
| 잇는 값이 없고 추정으로만 이어진다 | 만들지 않는다 |

### 7.2 채워야 하는 칸

설명이 좋아도 아래 칸이 틀리면 정답 개념이 후보에서 빠진다.

| 칸 | 무엇을 적는가 |
|---|---|
| 출발 개념 | 관계가 시작하는 개념 |
| 도착 개념 | 관계가 끝나는 개념 |
| 출발 속성명 | 출발 쪽 연결 키 |
| 도착 속성명 | 도착 쪽 연결 키 |
| 방향 | 관계의 방향 |
| 설명 | 7.3의 형식 |

### 7.3 설명 형식

```
{출발 개념}이(가) {도착 개념}에 대해 {무엇}을 {한다}. {어떤 질문}에 쓴다.
FK JOIN: {연결 명세}
```

연결 명세는 두 가지 형식 중 하나다.

```
직접  : {출발테이블}.{출발컬럼} = {도착테이블}.{도착컬럼}
경유  : {출발테이블}.{출발컬럼} = {중간테이블}.{키1}, {중간테이블}.{키2} = {도착테이블}.{도착컬럼}
```

방향과 두 개념은 위 칸에 이미 있으므로 설명 본문에 다시 쓰지 않는다.

### 7.4 완성 예시

```
휴가신청이 승인되어 실제로 쓴 휴가를 가리킨다. 신청한 휴가를 실제로 썼는지 확인하는 질문에 쓴다.
FK JOIN: hr.TB_휴가신청내역.휴가신청번호 = hr.TB_휴가사용내역.휴가신청번호
```

### 7.5 관계 검사

- [ ] 어느 검증질문이 이 관계를 쓰는지 말할 수 있는가
- [ ] 출발 개념과 도착 개념이 맞는가
- [ ] 이름이 연결 키 이름을 그대로 쓴 것이 아닌가
- [ ] 설명에 관계가 무엇을 하는지와 어디에 쓰는지를 적었는가
- [ ] `FK JOIN`을 직접 또는 경유 형식으로 적었는가
- [ ] 출발 속성명과 도착 속성명이 실제 연결 키와 같은가
- [ ] 방향을 정했는가

## 8. 모를 때의 행동

확인되지 않은 것을 채우면 구조는 완성된 것처럼 보이지만 반입 후에 답이 틀린다. 아래 규칙을 지킨다.

| 상황 | 무엇을 하는가 |
|---|---|
| 코드의 실제 저장값을 모른다 | `실제 저장값: 확인 필요`라고 적는다. 값을 추측해 적지 않는다 |
| 컬럼이 실제로 있는지 모른다 | `[SQL]`에 적지 않는다. `확인 필요`라고 적는다 |
| 단위를 모른다 | `단위: 확인 필요`라고 적는다 |
| 두 개념을 잇는 값이 있는지 모른다 | 관계를 만들지 않는다 |
| 검증질문과의 연결을 모른다 | 만들지 않는다 |
| 사람이 정해야 할 일로 보인다 | 만들지 않고 사람에게 묻는다 |

`확인 필요`가 하나라도 남아 있으면 그 개념·속성·관계는 완료로 표시하지 않는다.
