## 1. 먼저 알아 둘 것

**이 문서에 적은 것만 온톨로지가 된다.** 스크립트는 옮기기만 한다. 적지 않은 개념을 만들어 주지 않고, 적은 것을 빼지도 않는다. 빈 칸을 짐작해 채우지 않고, 어긋난 자리를 고쳐 주지도 않는다.

그래서 판단은 전부 작성자 몫이다. 무엇을 개념으로 둘지, 어떤 관계를 이을지, 어느 속성을 대표로 보일지 — 문서가 정한다.

| 작성자가 정하는 것 | 스크립트가 하는 것 |
|---|---|
| 어떤 개념을 둘지 | 적힌 개념을 규격 형식으로 옮긴다 |
| 어떤 관계를 이을지 | 적힌 관계를 옮긴다. 안 적은 관계는 만들지 않는다 |
| 속성의 데이터 타입 | 적힌 타입이 7종에 있는지 본다 |
| 대표 표시 속성·식별 속성 | 적힌 대로 표시한다 |
| 어긋난 자리를 고치는 일 | 몇 줄이 어긋났는지 알린다 |

**어긋난 자리가 하나라도 있으면 파일이 나오지 않는다.** 반쯤 옮긴 파일을 받으면 완성품으로 오해하기 때문이다. 알려 준 줄을 고쳐 다시 넣으면 된다.

## 2. 문서의 뼈대 — 네 절

절 넷이 있고, 앞의 둘만 필수다.

| 절 | 무엇을 적나 | 없으면 |
|---|---|---|
| `## Object Type` | 업무에서 다루는 개념과 그 속성 | **문서로 인정되지 않는다** |
| `## Link Type` | 개념 사이의 관계 | 관계 없는 온톨로지가 된다. 정상이다 |
| `## Meta Type` | 데이터가 실제로 어느 구조에서 오는지 | 개념·관계만 있는 온톨로지가 된다 |
| `## Object Mapping` | 개념의 속성과 데이터 컬럼을 잇기 | 같다 |

`## Object Type` 절만 있으면 문서가 성립한다. 관계를 적지 않으려면 절을 통째로 빼거나, 표 머리글만 남겨 두면 된다 — 둘 다 관계 0건으로 처리된다.

뒤의 두 절은 **같이 쓰거나 같이 뺀다.** Meta Type 만 적고 Object Mapping 을 적지 않으면 어느 속성이 어느 컬럼에서 오는지 알 수 없다. 반입은 되지만 적용이 막힌다.

절 순서는 지키는 편이 읽기 좋지만 스크립트는 순서를 보지 않는다.

---

## 3. 절 제목 적는 법

절 제목은 `##` 으로 시작한다. 스크립트는 제목을 읽을 때 **공백·하이픈·밑줄·가운뎃점·마침표를 무시하고 대소문자를 가리지 않는다.**

| 절 | 이렇게 적어도 된다 |
|---|---|
| Object Type | `## Object Type` `## object-type` `## OBJECT_TYPE` `## ObjectType` `## 오브젝트 타입` |
| Link Type | `## Link Type` `## link_type` `## 링크 타입` |
| Meta Type | `## Meta Type` `## meta-type` `## 메타 타입` |
| Object Mapping | `## Object Mapping` `## objectmapping` `## 오브젝트 매핑` |

**복수형은 받지 않는다.** `## Object Types` 라고 적으면 절을 찾지 못하고 "서식이 아닌 문서로 보인다"가 나온다. 가장 흔히 걸리는 자리다.

`###` 은 절 안의 항목이다. Object Type 과 Meta Type 은 개념·구조마다 `###` 을 하나씩 쓰고, Link Type 은 `###` 없이 표 하나만 쓴다.

## 4. Object Type 절 — 개념

개념 하나가 `###` 제목 하나다. 제목이 그대로 개념 이름이 된다.

```markdown
## Object Type

### 배송주문
- 설명: 고객이 요청한 배송 한 건
- 색: #4A90D9
- 공개: 예

| 속성 | 데이터 타입 | 설명 | PK | Title |
|---|---|---|---|---|
| 주문번호 | TEXT | 배송주문번호 | O | O |
| 수취인명 | TEXT | 받는 사람 이름 | | |
```

### 4.1 개념 이름

**형식이 정해져 있다.** 영문이나 한글로 시작하고, 그다음은 영문·숫자·한글·밑줄만 쓴다. 50자까지다. 공백·하이픈·마침표·괄호를 쓸 수 없다.

| 쓸 수 있다 | 쓸 수 없다 | 왜 |
|---|---|---|
| `배송주문` `Order` `협력사_2차` `A1등급` | `배송 주문` | 공백 |
| | `order-item` | 하이픈 |
| | `급여.명세` | 마침표 |
| | `상태(현재)` | 괄호 |
| | `2차_협력사` | 숫자로 시작 |

어긋나면 스크립트가 몇 줄인지 알린다. **고쳐 주지 않는다** — 이름은 뜻을 담은 것이라 대신 바꾸면 작성자가 모르는 이름이 파일에 들어간다.

이름은 문서 안에서 겹치면 안 된다.

### 4.2 제목 아래의 선택 줄

`###` 제목과 속성 표 사이에 `- 키: 값` 꼴로 적는다. 셋 다 선택이고, 빈 서식에는 `- 설명:` 만 들어 있다. 나머지 둘은 필요한 개념에만 손으로 더한다.

| 줄 | 뜻 | 적지 않으면 |
|---|---|---|
| `- 설명:` | 이 개념이 무엇인지. 5000자까지 | 설명 없이 만들어진다 |
| `- 색:` | 화면 표시 색. `#RRGGBB` 꼴 | 스크립트가 겹치지 않는 색을 준다 |
| `- 공개:` | `예` 면 공개, 비우거나 `X` 면 비공개 | 비공개 |

키 이름도 별칭을 받는다.

| 줄 | 이렇게 적어도 된다 |
|---|---|
| 설명 | `- 설명:` `- description:` |
| 색 | `- 색:` `- 색상:` `- colorCode:` `- color:` |
| 공개 | `- 공개:` `- 공개여부:` `- isPublic:` |

목록 기호는 `-` 과 `*` 둘 다 되고, 쌍점은 `:` 과 `：` 둘 다 된다. 이 줄들은 **`###` 제목과 표 사이에만** 적어야 읽힌다. 표 뒤에 적으면 읽히지 않는다.

**색에는 뜻이 없다.** 화면에 어떻게 보일지만 정하고 온톨로지의 뜻에 관여하지 않는다. 색으로 무언가를 구분하려 했다면 그 구분은 속성으로 적어야 남는다.

### 4.3 속성 표

**표의 행 순서가 화면에 보일 속성 순서가 된다.** 중요한 것을 위에 둔다.

칸 이름도 별칭을 받고, **칸 순서는 바꿔도 된다.** 스크립트가 머리글 이름으로 칸을 찾기 때문이다.

| 칸 | 이렇게 적어도 된다 | 없으면 |
|---|---|---|
| 속성 | `속성` `속성명` `이름` `property` `name` | 표를 읽지 못한다 |
| 데이터 타입 | `데이터 타입` `타입` `datatype` `type` | 표를 읽지 못한다 |
| 설명 | `설명` `description` `desc` | 설명 없이 만들어진다 |
| PK | `PK` `primary key` `식별` `식별 속성` | 식별 속성 없이 만들어진다 |
| Title | `Title` `title key` `대표` `대표 표시` | 대표 표시 속성이 0개가 되어 규격에 걸린다 |

속성 이름은 **형식 제약이 없다.** 개념 이름과 다르다. 공백이나 괄호를 써도 되고, 한 개념 안에서 겹치지만 않으면 된다. `직급 코드` `금액(원)` 같은 이름이 그대로 들어간다.

속성은 개념마다 **1개 이상** 있어야 한다. 표를 비워 두면 "속성 표가 없다"가 나온다. 빈 서식의 `| | | | | |` 줄은 빈 칸만 있어 건너뛰어지므로, 채우지 않은 개념은 이 오류로 걸린다.

### 4.4 데이터 타입 7종

이 일곱 중 하나를 적는다. 소문자로 적어도 대문자로 읽는다.

| 값 | 언제 | 원천 컬럼 예 |
|---|---|---|
| `TEXT` | 문자열 | text, varchar, char, uuid |
| `INTEGER` | 정수 | int, bigint, smallint |
| `FLOAT8` | 실수 | float, double precision, numeric, decimal |
| `DATETIME` | 날짜·시간 | date, timestamp, time |
| `BOOLEAN` | 참·거짓 | bool, bit |
| `VECTOR` | 임베딩 벡터 | vector, halfvec |
| `UNKNOWN` | 판별할 수 없을 때 | — |

7종에 없는 값을 적으면 몇 줄인지 알린다. 바꿔 주지 않는다. `VARCHAR` 를 `TEXT` 로 고치는 것도 작성자가 한다 — 어느 쪽인지 아는 사람은 작성자다.

`UNKNOWN` 은 **정말 판별할 수 없을 때만** 쓴다. 원천을 아직 못 봐서 비워 두는 자리로 쓰면, 받는 사람은 그것이 판별 결과인 줄 안다. 모르면 문서에 모른다고 적고 확정한 뒤 채운다.

`_yn` 으로 끝나는 컬럼이 `BOOLEAN` 인지 `TEXT` 인지는 스크립트가 짐작하지 않는다. 실제 데이터가 `Y`·`N` 문자면 `TEXT`, 참·거짓이면 `BOOLEAN` 이다.

### 4.5 PK 와 Title

둘은 성격이 다르다.

| | PK (식별 속성) | Title (대표 표시 속성) |
|---|---|---|
| 뜻 | 개체를 유일하게 가리키는 값 | 사람이 개체를 알아보는 표시값 |
| 개수 | 개념마다 0개 또는 1개 | 개념마다 **정확히 1개** |
| 예 | 고객번호, 주문번호 | 고객명, 상품명 |
| 없으면 | 정상 | 규격에 걸린다 (`GOS61006`) |
| 둘 이상이면 | 규격에 걸린다 (`GOS61008`) | 규격에 걸린다 (`GOS61007`) |

같은 속성에 둘 다 표시해도 된다. 주문번호처럼 식별자가 곧 표시값인 경우가 그렇다.

Title 은 개념마다 하나씩 반드시 정해야 한다. 화면에서 개체를 무엇으로 불러야 하는지 온톨로지가 알 수 없으면 적용이 막히기 때문이다.

### 4.6 참·거짓 칸에 적는 표기

PK·Title·`- 공개:` 가 참·거짓 칸이다.

| 참 | 거짓 |
|---|---|
| `O` `o` `예` `Y` `yes` `true` `V` `✓` `✔` `○` `●` | 빈칸 `X` `x` `×` `✕` `✗` `N` `no` `false` `아니오` `아니요` `아님` `부` `-` |

**`X` 는 거짓이다.** 한국어 표에서 `X` 는 "아니다"라는 뜻으로 쓰므로 그대로 읽는다. 비운 것과 같은 값이 된다.

**숫자 `0` 은 읽지 않고 알린다.** 영문 `O` 를 치려다 누른 것인지 "없음"의 뜻으로 적은 것인지 문서가 말하지 않기 때문이다. 표시하려면 `O`, 비우려면 빈칸으로 둔다.

## 5. Link Type 절 — 관계

**표 하나에 관계를 모두 적는다.** `###` 을 쓰지 않는다.

```markdown
## Link Type

| 관계 이름 | source | source 속성 | target | target 속성 | 방향 | 설명 |
|---|---|---|---|---|---|---|
| 배송품목_배송주문 | 배송품목 | 주문번호 | 배송주문 | 주문번호 | → | 품목이 딸린 주문 |
```

### 5.1 관계는 값이 같은지 보는 조인이다

`source 속성` 값과 `target 속성` 값이 같으면 두 개체가 이어진다. 그래서 **양쪽 조인 속성이 반드시 있어야 한다.** 관계 이름만 적으면 관계가 만들어지지 않는다.

```
배송품목.주문번호  ==  배송주문.주문번호
```

두 속성은 각각 그 개념의 속성 표에 실제로 있어야 한다. 없으면 규격 검증에서 `GOS61109`·`GOS61111` 로 걸린다.

**조인 속성이 없는 관계는 적지 않는다.** 없는 컬럼 이름을 적어 넣으면 반입은 되지만 실제 데이터에 그 컬럼이 없으므로 **언제나 빈 관계**가 된다. 잘 된 것처럼 보이면서 동작하지 않는 것이 가장 나쁘다. 이을 컬럼이 없으면 그 관계를 적지 말고, 원천에 컬럼을 만든 뒤 적는다.

`target 속성` 은 상대 개념의 식별 속성인 편이 좋다. 식별 속성이 아니면 값이 여러 개체에 반복되어 관계가 의도보다 넓게 퍼진다. 스크립트가 이 자리를 경고로 알린다.

### 5.2 여섯 칸은 다 채운다

**`설명` 만 비울 수 있다.** 나머지 하나라도 비면 그 관계를 만들지 않고 어느 칸이 비었는지 알린다.

칸 이름 별칭과 순서는 속성 표와 같은 규칙을 따른다.

| 칸 | 이렇게 적어도 된다 |
|---|---|
| 관계 이름 | `관계 이름` `이름` `관계` `name` |
| source | `source` `소스` `시작` |
| source 속성 | `source 속성` `소스 속성` `시작 속성` `sourceProperty` |
| target | `target` `타깃` `타겟` `도착` |
| target 속성 | `target 속성` `타깃 속성` `타겟 속성` `도착 속성` `targetProperty` |
| 방향 | `방향` `direct` |
| 설명 | `설명` `description` |

### 5.3 방향

방향은 셋 중 하나다. 그래프를 탐색하고 화면에 보일 때 쓰는 뜻 정보이고, 조인 자체는 방향과 무관하게 값이 같으면 성립한다.

| 규격 값 | 뜻 | 이렇게 적어도 된다 |
|---|---|---|
| `UNIDIRECTIONAL` | source → target | `→` `->` `-->` `=>` `⇒` `단방향` `정방향` `순방향` |
| `REVERSE_DIRECTIONAL` | target → source | `←` `<-` `<--` `<=` `⇐` `역방향` `반대방향` |
| `BIDIRECTIONAL` | 양방향 | `↔` `<->` `<-->` `<=>` `⇔` `양방향` `쌍방향` |

규격 이름은 소문자로 적어도 되고 하이픈을 써도 된다 — `unidirectional`, `reverse-directional` 이 모두 읽힌다.

읽을 수 없는 값을 적으면 그 관계를 만들지 않고 알린다.

### 5.4 관계 이름은 겹쳐도 된다

양끝이 다르면 같은 이름의 관계를 여러 개 둘 수 있다. `소속` 이라는 이름으로 사원→부서와 장비→부서를 따로 둬도 된다. 다만 읽는 사람이 구분하기 어려우니 `사원_부서` 처럼 양끝을 담은 이름을 권한다.

### 5.5 자기 참조는 쓸 수 없다

source 와 target 이 같은 개념일 수 없다. 규격이 막는다 (`GOS61106`).

조직→상위조직, 자산→상위자산 같은 계층은 **상위 식별자를 속성으로만 적는다.**

```markdown
### 부서
| 속성 | 데이터 타입 | 설명 | PK | Title |
|---|---|---|---|---|
| 부서코드 | TEXT | 부서 식별자 | O | |
| 부서명 | TEXT | 부서 이름 | | O |
| 상위부서코드 | TEXT | 상위 부서의 부서코드 | | |
```

### 5.6 다대다 관계는 가운데 개념이 필요하다

학생과 과목이 서로 여러 건으로 얽히면 관계 하나로 담을 수 없다. `수강` 같은 개념을 하나 더 적고 관계를 둘 적는다.

```markdown
### 수강
| 속성 | 데이터 타입 | 설명 | PK | Title |
|---|---|---|---|---|
| 수강번호 | TEXT | 수강 식별자 | O | O |
| 학번 | TEXT | 학생 | | |
| 과목코드 | TEXT | 과목 | | |
| 학기 | TEXT | 수강 학기 | | |

## Link Type
| 관계 이름 | source | source 속성 | target | target 속성 | 방향 | 설명 |
|---|---|---|---|---|---|---|
| 수강_학생 | 수강 | 학번 | 학생 | 학번 | → | 수강한 학생 |
| 수강_과목 | 수강 | 과목코드 | 과목 | 과목코드 | → | 수강한 과목 |
```

가운데 개념을 두는 편이 좋은 또 하나의 이유는, 관계 자신은 속성을 가질 수 없다는 것이다. 수강 학기나 성적처럼 이어짐에 딸린 값이 있으면 가운데 개념에 담는다.

**이 개념은 스크립트가 만들어 주지 않는다.** 문서에 적지 않으면 만들어지지 않는다.

## 6. Meta Type 절 — 데이터 구조

**Meta Type 은 대상 환경에 이미 있는 데이터 구조를 이름으로 가리키는 참조다.** 이 문서로 만들어지지 않는다. 이름이 대상 환경과 다르면 반입할 때 `GOS61014` 로 걸리고 새로 생기지 않는다.

데이터 원천이 아직 정해지지 않았으면 이 절과 Object Mapping 절을 통째로 뺀다. 개념·관계만 있는 온톨로지가 그대로 만들어진다.

```markdown
## Meta Type

### 배송주문원장
- 설명: 배송 주문 마스터 테이블
- 종류: CUSTOM

| 컬럼 | 데이터 타입 | 원천 컬럼명 | 설명 |
|---|---|---|---|
| ord_no | TEXT | ORD_NO | 배송주문번호 |
| rcv_nm | TEXT | RCV_NM | 수취인명 |
```

### 6.1 Meta Type 이름

**대상 환경에 게시된 이름과 정확히 같아야 한다.** 개념 이름과 달리 형식 제약은 없지만, 이름이 곧 참조 키라 한 글자도 달라선 안 된다. 문서 안에서 겹치면 안 된다 (`GOS61018`).

이름을 확인하는 일은 이 스킬이 하지 않는다. 대상 환경에서 Meta Type 목록을 보고 작성자가 적는다.

### 6.2 종류 3종

| 줄 | 별칭 |
|---|---|
| `- 종류:` | `- metaTypeKind:` `- kind:` |

| 값 | 언제 |
|---|---|
| `CUSTOM` | 정형 데이터 기반(테이블·CSV), 또는 사람이 직접 정의한 것 |
| `PARSING` | 비정형 문서를 파싱해 청크·임베딩 단위로 적재한 것 |
| `DOC_TYPE` | 문서 타입의 탐색·출력 속성에서 파생된 것 |

3종에 없는 값을 적으면 그 줄을 무시한다. 근거가 없으면 `CUSTOM` 으로 둔다 — 테이블·CSV 기반이 대부분이다.

### 6.3 컬럼 표

| 칸 | 별칭 | 뜻 |
|---|---|---|
| 컬럼 | `컬럼` `컬럼명` `이름` `column` `name` | Graphio 가 쓰는 컬럼 이름. Object Mapping 이 이 이름을 가리킨다 |
| 데이터 타입 | `데이터 타입` `타입` `datatype` `type` | 7종 중 하나. **필수다** |
| 원천 컬럼명 | `원천 컬럼명` `원천 컬럼` `raw` `rawDataPropertyName` | 원천 DB 의 컬럼명. 참고 정보 |
| 설명 | `설명` `description` | 1000자까지 |

속성 표와 달리 **데이터 타입을 비울 수 없다.** 7종에 없으면 그 줄을 건너뛰고 알린다.

컬럼 표 자체는 비워도 된다. 이름만 가리키고 컬럼은 대상 환경 것을 그대로 쓰겠다는 뜻이 된다. 다만 Object Mapping 에서 컬럼 이름을 가리켜야 하므로 대개 적는다.

이 절에 적을 수 없는 것이 있다. 연결 정보·스키마명·테이블명·워크플로·청킹 설정처럼 환경마다 다른 값은 반출·반입 어느 쪽에도 들어가지 않는다. 적어도 버려진다.

## 7. Object Mapping 절 — 개념과 데이터 잇기

"이 개념의 데이터는 이 구조에서 온다"를 정한다. 개념 하나와 Meta Type 하나의 짝이 항목 하나다.

```markdown
## Object Mapping

### 배송주문 ← 배송주문원장

| Object Type 속성 | Meta Type 컬럼 |
|---|---|
| 주문번호 | ord_no |
| 수취인명 | rcv_nm |
```

### 7.1 제목은 화살표로 두 이름을 잇는다

왼쪽이 개념 이름, 오른쪽이 Meta Type 이름이다. **왼쪽을 향하는 화살표만 받는다.**

| 쓸 수 있다 | 쓸 수 없다 |
|---|---|
| `← ` `<-` `<--` `<=` | `→` `-` `:` `~` |

`### 배송주문 ← 배송주문원장` 처럼 적는다. 화살표가 없거나 오른쪽 화살표를 쓰면 제목 꼴이 아니라고 알리고 그 연결을 만들지 않는다.

### 7.2 매핑 표

| 칸 | 별칭 |
|---|---|
| Object Type 속성 | `Object Type 속성` `개념 속성` `objectTypePropertyName` |
| Meta Type 컬럼 | `Meta Type 컬럼` `데이터 컬럼` `metaTypePropertyName` |

왼쪽은 그 개념의 속성 이름, 오른쪽은 그 Meta Type 의 컬럼 이름이어야 한다. 없는 이름을 적으면 규격 검증에서 `GOS61022`·`GOS61015` 로 걸린다.

**표가 비면 연결을 만들지 않는다.** 규격이 매핑 1건 이상을 요구한다.

### 7.3 짝을 여러 개 둘 수 있다

`(개념, Meta Type)` 짝만 겹치지 않으면 다음이 모두 정상이다.

| 꼴 | 예 |
|---|---|
| 한 개념이 여러 Meta Type 에서 온다 | 고객 ← CRM고객마스터 · 고객 ← 멤버십회원 |
| 한 Meta Type 을 여러 개념이 쓴다 | 주문 ← 주문상세 · 주문품목 ← 주문상세 |
| 여러 속성이 같은 컬럼을 가리킨다 | 등록일시 → reg_dtm · 최초확인일시 → reg_dtm |

한 연결 안에서 개념 속성 하나는 컬럼 하나에만 잇는다. 같은 속성을 두 줄에 적으면 `GOS61020` 으로 걸린다.

### 7.4 매핑이 없는 개념은 어떻게 되나

개념은 만들어지지만 데이터가 붙지 않는다. 적용하려면 대상 환경에서 Meta Type 을 연결해야 하고, 스크립트가 `GOS61017` 로 알려 준다. 데이터 원천이 아직 없다면 정상이다.

## 8. 서식 밖에 적는 것

**네 절이 아닌 `##` 절은 그냥 무시된다.** 배경·검토 의견·미확정 항목 같은 것을 문서에 함께 적어도 된다.

```markdown
# 배송관리 온톨로지 정의

## 배경                          ← 무시된다

물류팀 요청으로 2026년 3분기에 정리했다.

## 확인이 필요한 것              ← 무시된다

- 배송기사 개인정보를 온톨로지에 담을지 법무 확인 중

## Object Type                   ← 여기서부터 읽는다
```

`###` 제목도 네 절 안에 있을 때만 항목으로 읽힌다. 무시되는 절 안의 `###` 은 함께 무시된다.

`<!-- 주석 -->` 도 쓸 수 있다. 표 안이 아니라면 어디에 둬도 읽히지 않는다.

**이 자리를 적어 두는 편이 좋다.** 규격이 담지 못하는 것을 문서 밖으로 버리지 말고 무시되는 절에 남기면, 문서가 근거를 함께 지닌다.

## 9. 스크립트가 채우는 것과 알리는 것

### 9.1 채우는 값은 하나뿐이다

`colorCode` 만 채운다. 규격이 필수로 요구하는데(`GOS61004`) 문서가 적지 않을 수 있고, 온톨로지의 뜻에 관여하지 않기 때문이다.

- `- 색:` 이 있으면 그 값을 쓴다
- 없으면 **문서에 나온 순서대로 서로 겹치지 않게** 준다
- 문서가 이미 쓴 색은 건너뛴다
- 개념이 몇 개가 되어도 같은 색이 두 번 나오지 않는다

그 밖에 정하는 것은 없다. `orderNo` 는 표의 행 순서를 읽는 것이고, `isPublic`·`description` 은 선택이라 없으면 키를 넣지 않는다.

### 9.2 어긋난 자리는 줄 번호로 알린다

| 무엇이 어긋났나 | 어떻게 되나 |
|---|---|
| 개념 이름이 형식을 어긴다 | 줄 번호를 알린다 |
| 속성 이름이 비었다 | 그 줄을 건너뛰고 알린다 |
| 데이터 타입이 7종에 없다 | 그 줄을 건너뛰고 알린다 |
| 참·거짓 칸에 읽을 수 없는 값이 있다 | 거짓으로 두고 알린다 |
| 참·거짓 칸에 숫자 `0` 이 있다 | 거짓으로 두고 알린다 |
| 관계의 칸이 비었다 | 그 관계를 만들지 않고 알린다 |
| 방향을 3종으로 읽을 수 없다 | 그 관계를 만들지 않고 알린다 |
| 색이 `#RRGGBB` 꼴이 아니다 | 스크립트가 준 색으로 대신하고 알린다 |
| Object Mapping 제목이 화살표 꼴이 아니다 | 그 연결을 만들지 않고 알린다 |
| 매핑 표가 비었다 | 그 연결을 만들지 않고 알린다 |
| `## Object Type` 절이 없다 | 서식이 아닌 문서로 본다 |

**오류가 하나라도 있으면 파일을 쓰지 않는다.** 알려 준 줄을 고쳐 다시 넣는다.

### 9.3 서식은 지켰지만 규격을 어기는 자리

파일이 만들어진 뒤 규격 검증이 한 번 더 돈다. 흔한 것들이다.

| 코드 | 무엇이 어긋났나 | 문서에서 무엇을 고치나 |
|---|---|---|
| `GOS61006` | 대표 표시 속성이 0개다 | `Title` 칸에 `O` 를 하나 |
| `GOS61007` | 대표 표시 속성이 2개 이상이다 | 하나만 남긴다 |
| `GOS61008` | 식별 속성이 2개 이상이다 | 하나만 남긴다 |
| `GOS61010` | 한 개념에 같은 속성 이름이 둘 있다 | 이름을 구분한다 |
| `GOS61106` | 자기 참조 관계다 | 관계를 지우고 상위 식별자를 속성으로 적는다 |
| `GOS61107` | source 개념이 문서에 없다 | 개념을 적거나 이름을 맞춘다 |
| `GOS61109` | source 조인 속성이 그 개념에 없다 | 속성을 적거나 이름을 맞춘다 |
| `GOS61111` | target 조인 속성이 그 개념에 없다 | 같다 |
| `GOS61018` | Meta Type 이름이 겹친다 | 이름을 구분한다 |
| `GOS61022` | 매핑의 개념 속성이 그 개념에 없다 | 속성을 적거나 이름을 맞춘다 |

**이것도 문서를 고칠 일이다.** 파일을 손으로 고쳐 검증을 통과시키면 문서와 파일이 갈려, 다음에 문서를 다시 넣었을 때 다른 결과가 나온다.

### 9.4 대상 환경에서 마무리할 것

오류가 아니라 사람이 이어서 할 일이다.

| 코드 | 내용 |
|---|---|
| `GOS61017` | 데이터 연결이 없는 개념이 있다. 적용하려면 대상 환경에서 Meta Type 을 연결한다 |
| `GOS61014` | Meta Type 은 반입으로 만들어지지 않는다. 같은 이름으로 대상 환경에 먼저 있어야 한다 |

## 10. 규격이 담지 못하는 것

문서에 적었더라도 파일에 담기지 않는 것들이다. **문서에서 지우지 말고 서식 밖 절에 남겨 둔다.** 그 결정이 왜 그렇게 됐는지 아는 사람이 문서 작성자뿐이다.

| 담고 싶은 것 | 왜 담기지 않나 | 어떻게 하나 |
|---|---|---|
| 복합키 (주문번호 + 순번) | 식별 속성이 개념마다 1개까지다 | `PK` 를 비우고 두 속성은 그대로 적는다. 조인은 식별 속성을 요구하지 않으므로 관계는 만들 수 있다 |
| 계산값 (월평균 고장률) | 저장된 속성이 아니다 | 원천에 컬럼이 있으면 속성으로 적고, 화면에서 계산하는 값이면 적지 않고 서식 밖에 남긴다 |
| 관계에 딸린 값 (수강 학기) | 관계는 속성을 가질 수 없다 | 가운데 개념을 하나 두고 그 개념의 속성으로 적는다 |
| 자기 참조 계층 | 규격이 막는다 | 상위 식별자를 속성으로만 적는다 |
| 속성의 값 목록 (상태: 접수·배송중·완료) | 규격에 값 제약 칸이 없다 | 속성 `설명` 에 적거나, 코드 개념을 따로 두고 관계로 잇는다 |
| 필수 여부·기본값·길이 제한 | 규격에 해당 칸이 없다 | `설명` 에 적는다 |
| 조회 요구 ("기사별 월 배송 건수") | 온톨로지 구조가 아니다 | 서식 밖 절에 남겨 둔다. 그 조회가 되는지 확인하는 근거가 된다 |

## 11. 자주 걸리는 자리

| 증상 | 원인 | 고치는 법 |
|---|---|---|
| "서식이 아닌 문서로 보인다" | 절 제목이 `## Object Types` 처럼 복수형이거나 `#` 개수가 다르다 | `## Object Type` 으로 적는다 |
| "속성 표가 없다" | 빈 서식의 `\| \| \| \| \| \|` 줄을 채우지 않았다 | 속성을 적거나 그 개념을 지운다 |
| 속성 표를 읽지 못한다 | 표 머리글이 별칭에도 없다 | `속성`·`데이터 타입` 머리글을 그대로 쓴다 |
| `- 색:` 이 반영되지 않는다 | 표 뒤에 적었다 | `###` 제목과 표 사이로 옮긴다 |
| 관계가 만들어지지 않는다 | 여섯 칸 중 하나가 비었다 | `설명` 을 뺀 다섯 칸을 채운다 |
| Object Mapping 이 만들어지지 않는다 | 제목에 화살표가 없거나 `→` 를 썼다 | `←` 로 적는다 |
| `GOS61006` 이 계속 나온다 | `Title` 칸에 `O` 가 없다 | 개념마다 정확히 하나 표시한다 |
| PK 를 지정했는데 반영되지 않는다 | `X` 나 `0` 을 적었다 | 표시하려면 `O`, 비우려면 빈칸 |
| 관계가 의도보다 많이 이어진다 | `target 속성` 이 상대의 식별 속성이 아니다 | 식별 속성으로 잇거나 그대로 두고 근거를 남긴다 |
| 같은 문서인데 색이 달라진다 | 개념을 표 중간에 끼워 넣었다 | 색에는 뜻이 없다. 고정하려면 `- 색:` 을 적는다 |

---

## 12. 돌리는 법

```bash
# ① 서식을 graphio JSON 으로 옮긴다
python3 scripts/build_graphio_json.py 배송관리-온톨로지-정의.md -o 배송관리-ontology.json

# ② 규격을 확인한다
python3 scripts/validate_graphio_json.py 배송관리-ontology.json
```

①에서 오류가 나오면 **파일이 만들어지지 않는다.** "파일이 없다"는 실패가 아니라 의도한 동작이다. 알려 준 줄을 고쳐 다시 돌린다.

②는 서식은 지켰지만 규격을 어기는 자리를 찾는다. 오류·경고·보류 세 등급으로 나온다.

| 등급 | 무엇을 하나 |
|---|---|
| 오류 | 문서를 고친다 |
| 경고 | 확인만 한다 |
| 보류 | 대상 환경에서 마무리한다 |

같은 문서를 몇 번 넣어도 같은 파일이 나온다. 문서만 바뀌지 않았다면 결과도 바뀌지 않는다.
