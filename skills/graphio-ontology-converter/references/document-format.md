# 온톨로지 정의 서식

`scripts/build_graphio_json.py` 가 읽는 Markdown 서식이다. 빈 서식은 [`assets/온톨로지-정의-서식.md`](../assets/온톨로지-정의-서식.md) 에 있다.

이 서식이 있는 이유는 하나다. **문서에 적힌 것과 파일에 담긴 것이 정확히 같게 하기 위해서다.** 서식이 정해져 있으면 스크립트가 옮기므로 해석이 끼어들지 않는다. 같은 문서를 몇 번 넣어도 같은 파일이 나오고, 문서에 없는 것은 스크립트가 만들 방법이 없다.

## 1. 절 제목

`##` 제목으로 네 절을 가른다. 제목이 아래 이름과 맞지 않는 절은 **읽지 않는다** — 설명이나 메모를 자유롭게 적어도 파일에 섞이지 않는다.

| 절 제목 | 받는 이름 | 필수 |
|---|---|---|
| `## Object Type` | `오브젝트 타입` | 필수 |
| `## Link Type` | `링크 타입` | 관계가 있으면 |
| `## Meta Type` | `메타 타입` | 데이터 구조를 적을 때만 |
| `## Object Mapping` | `오브젝트 매핑` | Meta Type 을 적었을 때만 |

`## Object Type` 절이 없으면 스크립트가 "서식이 아닌 문서로 보인다"고 알리고 멈춘다.

## 2. Object Type 절

`###` 제목 하나가 개념 하나다. 제목이 곧 `name` 이다.

```markdown
### 배송주문
- 설명: 고객이 요청한 배송 한 건
- 색: #4A90D9
- 공개: 예

| 속성 | 데이터 타입 | 설명 | PK | Title |
|---|---|---|---|---|
| 주문번호 | TEXT | 배송주문번호 | O | O |
| 수취인명 | TEXT | 받는 사람 이름 | | |
```

| 서식 | graphio JSON | 없으면 |
|---|---|---|
| `### 제목` | `name` | 개념이 만들어지지 않는다 |
| `- 설명:` | `description` | 키를 넣지 않는다 |
| `- 색:` | `colorCode` | 스크립트가 채운다 (7절) |
| `- 공개:` | `isPublic` | 키를 넣지 않는다 (반입 시 `false`) |

`- 색:` 과 `- 공개:` 는 **빈 서식(`assets/온톨로지-정의-서식.md`)에 없는 줄이다.** 개념마다 두 줄이 거의 늘 빈칸으로 남기 때문이다. 정하고 싶은 개념에만 더해 적는다. 있으면 읽고 없으면 위 표대로 처리한다.
| 표의 행 순서 | `orderNo` 1, 2, 3 | — |
| `속성` 칸 | `properties[].name` | 그 행을 건너뛰고 알린다 |
| `데이터 타입` 칸 | `properties[].dataType` | 그 행을 건너뛰고 알린다 |
| `설명` 칸 | `properties[].description` | 키를 넣지 않는다 |
| `PK` 칸 | `isPrimaryKey` | `false` |
| `Title` 칸 | `isTitleKey` | `false` |

데이터 타입은 7종만 받는다 — `INTEGER` `TEXT` `DATETIME` `FLOAT8` `BOOLEAN` `VECTOR` `UNKNOWN`. 소문자로 적어도 대문자로 읽는다. 7종에 없는 값은 **바꾸지 않고** 그 행이 몇 줄인지 알린다.

## 3. Link Type 절

표 하나에 관계를 모두 적는다. `###` 제목을 쓰지 않는다.

```markdown
| 관계 이름 | source | source 속성 | target | target 속성 | 방향 | 설명 |
|---|---|---|---|---|---|---|
| 배송품목_배송주문 | 배송품목 | 주문번호 | 배송주문 | 주문번호 | UNIDIRECTIONAL | 품목이 딸린 주문 |
```

| 서식 | graphio JSON |
|---|---|
| `관계 이름` | `name` |
| `source` / `target` | `sourceObjectTypeName` / `targetObjectTypeName` |
| `source 속성` / `target 속성` | `sourcePropertyName` / `targetPropertyName` |
| `방향` | `direct` |
| `설명` | `description` |

**여섯 칸 가운데 `설명` 만 비울 수 있다.** 나머지 하나라도 비면 스크립트가 그 관계를 만들지 않고 어느 칸이 비었는지 알린다. 규격이 관계에 양쪽 조인 속성과 방향을 요구하기 때문이다(`GOS61108`·`GOS61110`·`GOS61103`).

방향은 셋 중 하나다. 규격 이름 대신 화살표나 한글로 적어도 된다.

| 규격 값 | 뜻 | 이렇게 적어도 된다 |
|---|---|---|
| `UNIDIRECTIONAL` | source → target | `→` `->` `=>` `⇒` `단방향` `정방향` `순방향` |
| `REVERSE_DIRECTIONAL` | target → source | `←` `<-` `<=` `⇐` `역방향` `반대방향` |
| `BIDIRECTIONAL` | 양방향 | `↔` `<->` `<=>` `⇔` `양방향` `쌍방향` |

별칭은 **뜻을 정해 주는 것이 아니다.** 문서가 이미 적은 방향을 규격 이름으로 옮기는 것뿐이다. 셋으로 옮길 수 없는 값은 바꾸지 않고 몇 줄인지 알린다.

관계는 **값 기반 조인**이다. `source 속성` 값과 `target 속성` 값이 같으면 두 개체가 이어진다. 그래서 양쪽 속성이 각각 그 개념에 실제로 있어야 한다 — 없으면 검증기가 `GOS61109`·`GOS61111` 로 잡는다.

## 4. Meta Type 절

데이터 원천 구조를 적을 때만 쓴다. 적지 않으면 이 절과 Object Mapping 절을 통째로 지운다.

```markdown
### 배송주문원장
- 설명: DLV 스키마 원천 테이블
- 종류: CUSTOM

| 컬럼 | 데이터 타입 | 원천 컬럼명 | 설명 |
|---|---|---|---|
| ord_no | TEXT | ORD_NO | 배송주문번호 |
```

| 서식 | graphio JSON |
|---|---|
| `### 제목` | `name` |
| `- 설명:` | `description` |
| `- 종류:` | `metaTypeKind` — `CUSTOM` `PARSING` `DOC_TYPE` |
| `컬럼` 칸 | `properties[].name` |
| `데이터 타입` 칸 | `properties[].dataType` |
| `원천 컬럼명` 칸 | `properties[].rawDataPropertyName` |
| `설명` 칸 | `properties[].description` |

**여기 적는 이름은 Graphio 에 이미 등록된 Meta Type 과 컬럼의 이름이다.** 이 파일이 Meta Type 을 만들지 않는다. 이름이 대상 환경과 다르면 반입할 때 `GOS61014`(Meta Type 없음)·`GOS61015`(컬럼 없음)·`GOS61023`(동명 2건)으로 걸리고, 그때 고칠 것은 이 문서다.

스크립트는 그 이름이 대상 환경에 있는지 **확인하지 않는다.** 확인할 방법이 없고, 문서가 적은 이름이 작성자의 뜻이기 때문이다.

## 5. Object Mapping 절

`###` 제목에 두 이름을 화살표로 잇는다. `←`, `<-`, `<--` 를 모두 받는다.

```markdown
### 배송주문 ← 배송주문원장

| Object Type 속성 | Meta Type 컬럼 |
|---|---|
| 주문번호 | ord_no |
| 수취인명 | cust_nm |
```

| 서식 | graphio JSON |
|---|---|
| 화살표 왼쪽 | `objectTypeName` |
| 화살표 오른쪽 | `metaTypeName` |
| 왼쪽 칸 | `objectTypePropertyName` |
| 오른쪽 칸 | `metaTypePropertyName` |

표가 없으면 그 연결을 만들지 않고 알린다 — 규격이 속성 매핑을 1건 이상 요구한다(`GOS61016`).

한 개념을 여러 Meta Type 에 잇거나 한 Meta Type 을 여러 개념이 참조하는 것은 정상이다. `### 개념 ← Meta Type` 절을 여러 개 적으면 된다. 같은 짝이 두 번 나오면 검증기가 `GOS61019` 로 잡는다.

**양쪽 이름이 같으면 매핑이 아무 일도 하지 않는다.** `주문번호 ← 주문번호` 처럼 적으면 개념 층과 데이터 층이 같아져, 규격이 둘을 나눠 둔 뜻이 사라진다. 개념 속성은 업무 용어, Meta Type 컬럼은 물리 컬럼명으로 적는 것이 이 서식이 기대하는 모습이다.

## 6. 칸 이름 별칭

표 머리글은 **이름으로 찾으므로 칸 순서를 바꿔도 된다.** 공백·하이픈·밑줄·점은 무시하고 대소문자를 가리지 않는다.

| 뜻 | 받는 머리글 |
|---|---|
| 속성 이름 | `속성` `속성명` `이름` `property` `name` |
| 데이터 타입 | `데이터 타입` `타입` `dataType` `type` |
| 설명 | `설명` `description` `desc` |
| 식별 속성 | `PK` `primary key` `식별` `식별 속성` |
| 대표 표시 속성 | `Title` `title key` `대표` `대표 표시` |
| 관계 이름 | `관계 이름` `관계` `이름` `name` |
| 시작 개념 | `source` `소스` `시작` |
| 시작 속성 | `source 속성` `소스 속성` `시작 속성` |
| 도착 개념 | `target` `타깃` `타겟` `도착` |
| 도착 속성 | `target 속성` `타깃 속성` `도착 속성` |
| 방향 | `방향` `direct` |
| Meta Type 컬럼 | `컬럼` `컬럼명` `column` `name` |
| 원천 컬럼명 | `원천 컬럼명` `원천 컬럼` `raw` |

**참·거짓 칸** (`PK`·`Title`·`- 공개:`) 은 아래를 받는다.

| 참 | 거짓 |
|---|---|
| `O` `o` `Y` `예` `true` `V` `✓` `○` `●` | 빈칸 `X` `x` `×` `N` `false` `아니오` `아니요` `부` |

`X` 는 **거짓**이다. 한국어 표에서 `X` 는 "아니다"라는 뜻으로 쓰므로 그대로 읽는다. 비운 것과 같은 값이 된다.

숫자 `0` 은 읽지 않고 알린다. 영문 `O` 를 치려다 누른 것인지 "없음"의 뜻으로 적은 것인지 **문서가 말하지 않기** 때문이다. 그 밖의 값도 읽지 않고 알린다.

## 7. 스크립트가 채우는 값

규격이 필수로 요구하는데 문서가 적지 않을 수 있는 칸은 하나다.

**`colorCode`** — 화면 표시 색이다. 온톨로지의 뜻에는 관여하지 않지만 없으면 `GOS61004` 로 적용이 막힌다.

- 문서에 `- 색:` 이 있으면 그 값을 쓴다
- 없으면 스크립트가 준다. **문서에 나온 순서대로, 서로 겹치지 않게** 준다
- 앞 12개는 색상환을 30도 안팎으로 나눈 값이고, 13번째부터는 황금각(137.508도)으로 색상을 돌려 만든다. 개념이 몇 개가 되어도 같은 색이 두 번 나오지 않는다
- 문서가 이미 쓴 색은 건너뛴다

채운 자리는 스크립트가 모두 알리고, 리포트 3절에 적는다.

`orderNo` 는 표의 행 순서라 채우는 것이 아니라 읽는 것이다. `isPublic` 과 `description` 은 선택 항목이라 없으면 키를 넣지 않는다.

## 8. 스크립트가 알리는 것

스크립트는 **문서를 고치지 않는다.** 어긋난 자리가 몇 줄인지, 무엇을 적어야 하는지 알리고 멈춘다. 고칠 사람은 문서 작성자다.

| 알리는 것 | 무엇을 뜻하나 |
|---|---|
| `## Object Type` 절이 없다 | 서식이 아닌 문서다 (10절) |
| 개념 이름이 규격 형식을 어긴다 | 공백·하이픈·점·괄호가 있거나 숫자로 시작하거나 50자를 넘는다 |
| 속성 표가 없다 | 규격이 속성을 1건 이상 요구한다 |
| 데이터 타입이 7종에 없다 | 그 행을 건너뛴다 |
| 관계의 칸이 비었다 | 그 관계를 만들지 않는다 |
| 방향이 3종에 없다 | 그 관계를 만들지 않는다 |
| 참·거짓 칸에 숫자 `0` 이 있다 | 거짓으로 두고 알린다 (영문 `O` 와 가릴 수 없다) |
| 참·거짓 칸의 값을 읽을 수 없다 | 거짓으로 두고 알린다 |
| 색이 `#RRGGBB` 꼴이 아니다 | 스크립트가 준 색으로 대신하고 알린다 |
| Object Mapping 제목이 화살표 꼴이 아니다 | 그 연결을 만들지 않는다 |

문서 오류가 하나라도 있으면 **JSON 파일을 쓰지 않는다.** 반쯤 옮긴 파일을 남기면 그것이 완성품으로 오해된다.

문서 오류가 없으면 `validate_graphio_json.py` 로 규격을 확인한다. 서식은 지켰지만 규격을 어기는 자리가 남을 수 있다 — 대표 표시 속성이 0개나 2개인 개념, 자기 참조 관계, 조인 속성 이름이 상대 개념에 없는 관계가 그렇다.

## 9. 규격이 담지 못하는 것

문서 작성자가 미리 알아야 할 것들이다. 서식에 적어도 파일에 담기지 않으므로 리포트에 남는다.

| 문서에 적고 싶은 것 | 왜 담기지 않나 | 어떻게 하나 |
|---|---|---|
| 계산 값 (월평균 고장률, 지급률) | 속성은 저장된 데이터 컬럼이고 계산식을 담지 못한다 | 속성으로 적지 않는다 |
| 복합키 (주문번호 + 순번) | 식별 속성이 개념마다 1개까지다 | `PK` 를 비운다. 두 속성은 그대로 적는다. 조인은 식별 속성을 요구하지 않으므로 관계는 그대로 만들 수 있다 |
| 자기 참조 관계 (조직 → 상위조직) | 규격이 막는다 (`GOS61106`) | 관계로 적지 않고 상위 식별자를 **속성으로만** 적는다 |
| 상위·하위 개념 관계 (회원 → 개인/법인) | 규격에 상속이 없다 | 항목이 다르면 하위마다 개념을 적고, 구분값이면 개념 하나에 구분 속성을 적는다. 상위 개념을 따로 적지 않는다 |
| N:N 관계 (설비 ↔ 부품) | 관계 하나가 N:N 을 담지 못한다 | 가운데 개념을 하나 더 적고 관계를 두 개 적는다 |
| 조회 요구·질의 목록 | 온톨로지 구조가 아니다 | 서식 밖에 적는다. 파일에 섞이지 않는다 |

---

## 10. 서식을 벗어난 문서

`## Object Type` 절이 없으면 서식이 아니다. 이때 **문서를 해석해 개념을 뽑아내지 않는다.** 산문에서 개념을 찾아내는 일에는 판단이 끼어들고, 그렇게 만든 온톨로지는 문서 작성자가 확인할 수 없다.

두 갈래로 처리한다.

| 사용자가 원하는 것 | 어떻게 하나 |
|---|---|
| 이 문서로 온톨로지를 만들어 달라 | 서식([`assets/온톨로지-정의-서식.md`](../assets/온톨로지-정의-서식.md))을 건네고, 이 서식으로 적어 주면 옮긴다고 알린다 |
| 이 문서를 서식으로 옮겨 달라 | **문서에 적혀 있는 것만** 서식 칸에 옮긴다. 문서가 말하지 않은 칸은 **빈 칸으로 남긴다.** 채워 넣지 않는다. 그 초안을 작성자가 채워 확정한 뒤 파일로 옮긴다 |
